# Этап 6.2 — предпроверка файлов без снятия карантина

**Статус:** минимальный безопасный инкремент. В системе **нет антивируса, CDR,
песочницы, OCR, распознавания аудио, автоматического извлечения или LLM**.
Не использовать реальные медицинские данные в текущем MVP.

## Границы и конфликты

- **Источник истины:** `medical_attachments` в PostgreSQL содержит исходный SHA-256,
  размер, MIME и `storage_key`; байты лежат отдельно в `ATTACHMENTS_DIR`.
  `attachment_security_reviews` — одна текущая запись предварительного осмотра;
  отсутствие записи для старого вложения означает `quarantined`.
  `attachment_security_events` — отдельный аудит чтения и попыток предпроверки.
- **Контракты:** существующие upload/list/download и поле `extraction_status`
  не меняются и остаются `quarantined`. 6.1 `evidence-drafts` не пересматривается.
  Новый API только добавляется под `/api/v1`.
- **Расширение:** в 6.2 не существует состояния, допускающего парсер. Будущий
  AV/CDR worker должен иметь отдельную изолированную среду, собственную схему
  подтверждения **реального** сканирования, версионированную политику и
  повторную привязку к SHA-256 исходных байтов. Нельзя истолковывать
  `prechecked_quarantined` как AV-чистый файл.

## Конечный автомат

| Состояние | Значение | Допустимые переходы |
|---|---|---|
| `quarantined` | Нет записи предварительной проверки; в том числе все старые файлы | → `prechecked_quarantined` или `rejected` |
| `prechecked_quarantined` | Размер, SHA-256, заявленный MIME и сигнатура сошлись в момент чтения | → `prechecked_quarantined` при повторной проверке; → `rejected` при обнаружении несоответствия |
| `rejected` | Проблема целостности, типа или хранения | Только → `rejected`; сброса в API нет |

Для всех состояний: `antivirus_status="not_scanned"`,
`processing_allowed=false`, `quarantine_active=true`.
`require_processing_clearance()` ВСЕГДА отказывает. Создания `released`
или `approved` в БД/HTTP нет. Попытка записать неизвестный статус
ограничена PostgreSQL `CHECK`; SQL CHECK не может удостоверить факт AV.

При предпроверке:
1. Права пользователя и актуальность пациента проверяются до получения
   `storage_key`. Для POST берётся `FOR UPDATE` на строку вложения,
   сериализующий параллельные предпроверки.
2. Валидируются расширение, MIME из метаданных, SHA-256 (строгий нижний hex),
   длина и непрозрачный ключ. Символические ссылки и выход из корня отклоняются.
3. Открытый файловый дескриптор считывается не более чем на 20 МиБ, сверяются
   размер, SHA-256, информация о модификации и сигнатура (для DOCX — ZIP
   central directory, ограничение количества записей и заявленного размера,
   запрет traversal, макросов, symlink/шифрованных записей и грубой zip bomb).
4. Текущий статус и событие аудита сохраняются в одной транзакции.
   Невозможность чтения хранилища даёт HTTP 503, событие `error` и
   **не переводит** файл в `prechecked_quarantined`. Недостающий/испорченный
   файл получает `rejected`. Повтор `rejected` не разблокирует файл.

**Важные пределы:** проверка сигнатур не доказывает структурную корректность
всех форматов и не защищает от макросов, эксплойтов или полиглотов. Прочитанный
файл не становится безопасным. Даже после `prechecked_quarantined` байты
могут быть подменены до будущей обработки. Путь к файлу локальный:
нужно обеспечивать ACL Windows на каталог, запрет изменения файлов
посторонними процессами, защищённое хранилище и неизменяемое snapshot/
CAS-хранилище перед открытием будущим парсером.

## Новые HTTP-операции

- `GET /patients/{patient_id}/attachments/{attachment_id}/security` —
  статус, доступен связанному врачу и администратору, с аудитом чтения.
- `POST /patients/{patient_id}/attachments/{attachment_id}/security/precheck` —
  предпроверка **только администратором**; повтор разрешён,
  изменения блокируются на PostgreSQL-строке вложения.

Общее: bearer auth; `401` без аутентификации, `403` при недопустимой роли,
`404` для чужого/отсутствующего/удалённого пациента либо вложения другого
пациента, `409` если исходный `extraction_status` не карантинный или имеется
`extracted_text_ref`, `503` при операционной ошибке открытия.
Данные возвращаются только после успешного коммита аудита; `Cache-Control:
private, no-store`. В JSON нет содержимого файла, выдержек и путей хранилища.

При успешной записи нет превращения вручную введённых выдержек этапа 6.1 в
клинические факты. Context Builder и PostgreSQL snapshots по-прежнему
исключают все вложения независимо от их security-статуса. Существующий
авторизованный **download** остаётся неизменным, но скачанный файл опасен:
клиенту нельзя автоматически открывать его, запускать macros или парсер.

## Проверка Windows / PowerShell

Команды из корня репозитория после замены всех файлов ZIP.

```powershell
.\.venv\Scripts\Activate.ps1
docker compose up -d postgres
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini heads
# До применения ожидается head = aiextract_v2_20261018, current = aiextract_v1_20261018
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check
python -m ruff check backend
python -m pytest backend/tests/test_attachment_security_unit.py -v
# Использовать только ОТДЕЛЬНУЮ локальную пустую БД *_test!
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_attachment_security_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

Тестовую БД `aidoctor_test` следует заранее создать администратором СУБД
(например, `docker compose exec postgres createdb -U aidoctor aidoctor_test`).
Если у вас изменён пароль в `.env`, замените пароль в строке на актуальный.
Фикстура PostgreSQL **удаляет и пересоздаёт все таблицы** целевой
`*_test` БД. Нельзя использовать боевую или содержащую данные БД.
`SKIPPED` не доказывает интеграционную проверку.

После миграции ожидается `aiextract_v2_20261018 (head)`. 6.2 не
считается завершённым до зелёного Ruff, полного pytest без пропуска PG
и `alembic check` на Windows.
