# 6.3.1 — локальный ClamAV INSTREAM, технические отчёты

## Границы и источник истины

- `attachment_security_reviews`: статус предварительной проверки.
- `attachment_av_scans`: хронология ответов сканера, не разрешение на обработку.
- `attachment_security_events`: аудит `scan_input` и `av_scan`.
- Оригиналы — в закрытом файловом хранилище; в БД не записываются байты.
- `require_processing_clearance` ВСЕГДА запрещает парсинг и Context Builder не
  читает непроверенные выдержки/вложения.
- Проверяются доступ администратора к активному пациенту, связь файла с
  пациентом, размер/хеш/сигнатура и состояние карантина до и после сканирования.

## Интеграция ClamAV

Рекомендуется установить и самостоятельно администрировать ClamAV `clamd`
в отдельном ограниченном контейнере/процессе с ручным обновлением сигнатур.
**Этот архив ClamAV не устанавливает и не запускает.**

Клиент подключается **только к `127.0.0.1:3310`**, без возможности выбрать
внешний host. ClamAV protocol `zINSTREAM\0` отправляет длины блоков в формате
unsigned big-endian и завершает поток нулевой длиной; затем выполняется
отдельный запрос `zVERSION\0`. Оба ответа ограничены по длине и времени.
Нет передачи путей, имён пациентов или текстовых данных в системные журналы.

`clamd` TCP **не аутентифицирован и не шифруется**: localhost не обеспечивает
изоляцию от иных процессов на хосте. Без отдельного доверенного контейнерного
окружения, ограничения порта и ACL результат `clean_reported` остаётся
**только диагностическим**. Ни статус, ни версия не подтверждают актуальность
баз. Настроить `StreamMaxLength >= 20M`, `MaxScanSize`, `MaxFileSize`,
лимиты CPU/RAM/времени и расписание обновления баз — самостоятельная
операционная работа. Нельзя считать выключенный или недоступный сканер AV.

## Ручной запуск на Windows/PowerShell

Включать только когда **реальный локальный clamd уже запущен**, а порт 3310
доступен на loopback, с контролируемыми сигнатурами и журналами.

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini heads
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check

python -m ruff check backend

# Подставить реально существующие UUID администратора, пациента и вложения.
$env:ATTACHMENT_CLAMD_ENABLED = "true"
$env:PYTHONPATH = (Resolve-Path .\backend).Path
python -m app.workers.attachment_clamd_once --once `
  --actor-id "UUID_ADMIN" --patient-id "UUID_PATIENT" --attachment-id "UUID_ATTACHMENT"
Remove-Item Env:ATTACHMENT_CLAMD_ENABLED
Remove-Item Env:PYTHONPATH
```

Если локального clamd нет, **не включать** настройку. Допускается
проверять unit/PG-тесты без ClamAV — они симулируют протокол, а не AV.

```powershell
python -m pytest backend/tests/test_attachment_clamd_unit.py -v
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_attachment_av_scan_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

Тестовая фикстура **удаляет и создаёт таблицы**: запускать исключительно
на отдельной пустой локальной БД `*_test`; `SKIPPED` не считать успехом.
Здесь нет EICAR и никаких реальных вредоносных образцов. Фактический
ClamAV-сервис и его базы проверяются отдельно. Результаты тестов,
даже полностью зелёные, **не разрешают** обработку клинических файлов.

## Конфликты архитектуры

1. **Владение:** Postgres хранит только оценки/аудит; storage остаётся владельцем
   байтов, снимок однократный; изменение файла между проверками вызывает ошибку.
2. **Контракты:** ни старый HTTP API, ни extraction_status, ни предшествующие
   миграции не меняются. Есть новая таблица и дополнительный тип события аудита.
3. **Эволюция:** будущий worker для полного AV/CDR должен отделить доступы ОС,
   ограничить ресурсы, доказуемо проверить источник сканирования, свежесть сигнатур
   и вердикт для конкретного SHA-256 до рассмотрения нового статуса допуска.

## Известные риски

- localhost TCP не обеспечивает подлинность daemon; локальный злоумышленник
  может вернуть `stream: OK`.
- Параллельные попытки допускаются, результаты привязаны к разным снимкам,
  но PostgreSQL сериализует запись последствий по вложению.
- Между проверкой файла и любым будущим парсером возможна подмена со
  стороны другого локального процесса: парсинг здесь полностью выключен.
- Нет проверки свежести баз, CDR и гарантий удаления вредоносных файлов.
- При падении записи аудита результат не считается сохранённым.
