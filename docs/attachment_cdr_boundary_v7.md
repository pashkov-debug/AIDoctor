# AIDoctor 6.4.0 — подготовка кандидата для изолированного CDR

**Статус:** техническая граница (без санитизации). **НЕ выпуск документа из
карантина, НЕ разрешение парсинга или клинической обработки.**

## Контракт

Внутренняя функция
`app.services.attachment_cdr_boundary.prepare_quarantined_cdr_candidate`
принимает `Session`, UUID пациента, вложения и администратора, а также
`AttachmentStorage`. Публичного HTTP API, CLI, worker или планировщика нет.

Функция может вернуть только `QuarantinedCDRCandidate`, содержащий
копию оригинальных **недоверенных** байтов с SHA-256, MIME и ID
технического AV-отчёта. `processing_allowed=False`. Кандидат не является
результатом CDR, входом Context Builder или безопасным PDF/DOCX.
Само наличие и даже повторное чтение кандидата не открывает парсер.

Разрешённые типы снимка: `.pdf` (`application/pdf`) и `.docx`
(`application/vnd.openxmlformats-officedocument.wordprocessingml.document`).
DOC, изображения, аудио и другие форматы не принимаются на вход будущего
CDR в этой версии. Это ограничение на вход, а не утверждение, что PDF/DOCX
безопасны.

## Порядок проверки

1. Проверка `admin`, существования пациента без soft-delete и точной
   принадлежности вложения; строки блокируются в PostgreSQL.
2. Требуется `extraction_status=quarantined`, `extracted_text_ref IS NULL`.
3. Последняя запись `attachment_security_reviews` должна иметь состояние
   `prechecked_quarantined` и совпадающий SHA-256/размер/пациента.
4. Берётся **последний**, а не произвольный прежний `attachment_av_scans`
   по `created_at DESC, id DESC`. Он обязан сообщать `clean_reported`,
   соответствовать файлу, иметь `engine_name=clamd`, строку VERSION,
   возраст не более 24 часов и быть созданным после предпроверки.
5. Файл повторно считывается из карантина через действующие ограничения
   путей, размера, сигнатуры и SHA-256, без запуска интерпретатора.
   При подмене текущая оценка становится терминальной `rejected`.
6. Перед возвратом байтов фиксируется событие `cdr_input` в
   `attachment_security_events`. Ошибка commit запрещает выдачу снимка.
   При отсутствии условий пишется `outcome=error`, без содержимого файла.

**Ограничение достоверности AV:** отчёт `clean_reported` исторически мог быть
записан и прямым низкоуровневым вызовом, без гейта 6.3.3.
БД не содержит криптографической аттестации работы ClamAV. Поэтому даже
успешный отбор — только кандидата для будущего *недоверенного* sandbox, а не
подтверждение безопасного файла или разрешение запуска CDR. В production
нужна явная версия политики сканирования, удостоверение доверенного пути
и отдельный контракт происхождения результатов.

## Конфликты и ответственность

- **Владение:** PostgreSQL — источник статусов, AV-отчётов и аудита;
  файловое хранилище — оригинал; снимок живёт только в памяти локального
  процесса и не хранится в БД.
- **Контракты:** существующие HTTP-маршруты, `require_processing_clearance`,
  `extraction_status`, Context Builder и миграции 6.1–6.3.3 не меняются.
- **Эволюция:** будущая CDR-среда обязана принимать копию байтов, а не путь;
  отдельно нужны ограничение CPU/RAM/времени/сети, защита от паразитных
  форматов, проверка и повторное AV-сканирование выхода, отдельная запись
  происхождения санитизированного артефакта, авторизация доступа и
  независимый клинический допуск. Ничего из этого пока не реализовано.
- **TOCTOU:** фиксированный буфер защищает от последующей смены файла по пути,
  но не от компрометации процесса, PostgreSQL или доступа администратора к
  хранилищу. Внутренний интерфейс не предназначен для использования в
  незащищённых процессах.

Новая миграция `aiextract_v5_20261019` после `aiextract_v4_20261018`
меняет только CHECK для действия `cdr_input`; автоматический downgrade
намеренно запрещён из-за риска потери аудита. Новых Python-зависимостей нет.

## Установка на Windows / PowerShell

В корне проекта после замены файлов:

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini heads
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini check
python -m ruff check backend
python -m pytest backend/tests/test_attachment_cdr_boundary_unit.py -v
```

PostgreSQL-тесты создают и удаляют SQL-таблицы. Только выделенная
`aidoctor_test` **без медицинских или других ценных данных**:

```powershell
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_attachment_cdr_boundary_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

Затем проверить `docker compose -f compose.yaml -f compose.av.yaml --profile av ps`
и при необходимости повторить существующий EICAR smoke-test. Однако даже
`healthy` и EICAR не делают CDR проверенным.

## Критерии готовности

1. Единственный Alembic head `aiextract_v5_20261019`, миграция применена
   и `alembic check` без ошибок.
2. Ruff и все unit/PG тесты пройдены без неожиданных пропусков.
3. Успешный снимок возвращается исключительно админу, с последним
   подходящим отчётом AV и обязательным успешным аудитом.
4. Подмена, устаревший AV, запрещённый формат и смена статуса блокируются;
   при подмене сохраняется терминальный `rejected`.
5. Карантин, `require_processing_clearance` и Context Builder неизменны.

## Риски / следующий шаг

**Не реализованы:** настоящий CDR, изоляция парсера, проверка его выходов,
доверенная аттестация сканера, получение клинических данных, OCR/LLM,
обработка персональных данных на production.

Следующий кандидат — 6.4.1: согласовать и испытать реальный изолированный
движок CDR для ограниченных форматов на синтетических файлах и с
необратимым запретом прямой обработки оригиналов. Любые тяжёлые
зависимости/контейнеры требуют отдельного согласования.
