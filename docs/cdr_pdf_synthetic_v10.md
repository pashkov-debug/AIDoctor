# AIDoctor — 6.4.2a: настоящий PDF CDR на синтетических данных

## Назначение

Выполняется **настоящая** последовательность `PDF -> JPEG страниц -> новый PDF`
в одноразовом Docker-контейнере. Poppler (`pdfinfo`, `pdftoppm`) рендерит
страницы, `img2pdf` пересобирает PDF только из растровых изображений.
Docker нужен только для демонстрационного запуска. Это **не** Dangerzone,
не gVisor и не сертифицированная CDR-система для пациентов.

Единственный доступный публичный Python-метод запуска:
`run_synthetic_pdf_cdr(image_id=...)`. У него **нет** параметра для
передачи произвольных файлов, путей, медкарт, DOCX, PDF пациентов или
содержимого из PostgreSQL. Источник формируется в памяти функцией
`synthetic_pdf()` и содержит только текст
`AIDoctor synthetic CDR test only`. В приложение не добавлены маршруты,
worker по расписанию, настройки автоматического запуска, ORM-модели или
способы снятия карантина.

Взаимодействие с контрактами 6.4.1a/1b:
- `UnexecutedCDRPlan` используется лишь как форма **синтетического**
  потока и команда с теми же ограничениями Docker. Это НЕ аудированный
  `QuarantinedCDRCandidate` и не разрешение использовать настоящее вложение.
- `capture_untrusted_cdr_output` принимает результат как `UntrustedCDROutput`.
  `processing_allowed=False`, `sanitized=False`, `trusted=False`.
- Технические AV-отчёты и EICAR не меняют эту политику.

## Зависимости (опционально)

Образ собирается *вручную*, только при согласии пользователя на
скачивание базового Python-образа и установку Debian-пакетов
`poppler-utils` и `img2pdf` **внутри контейнера**. В Python `.venv`
пакеты не устанавливаются. Процедура получает внешние пакеты из Docker Hub
и репозиториев Debian; используйте только доверенную сеть.
Версии базового образа и системных пакетов в этом прототипе НЕ зафиксированы
по digest, значит воспроизводимость/подлинность сборки пока не доказана.
Для production необходимы SBOM, сканирование образа, обновления и pin по
digest, контроль происхождения, а также stronger sandbox (например gVisor).

Сборка не читает корневой каталог проекта: **контекст сборки ровно
`backend/cdr_image`**. `.dockerignore` позволяет отправить в Docker
только Dockerfile и worker.py. Нельзя собирать `docker build .`:
в корне могут оказаться медицинские файлы и `.env`.

## Windows PowerShell

Из корня AIDoctor:

```powershell
python -m ruff check backend
python -m pytest backend/tests/test_cdr_synthetic_execution_unit.py -v -rs
python -m pytest backend/tests/test_cdr_pdf_worker_unit.py -v -rs
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check

# Явная ОПЦИОНАЛЬНАЯ установка CDR-зависимостей внутрь Docker:
docker build -f backend/cdr_image/Dockerfile -t aidoctor-cdr:synthetic backend/cdr_image

# Полный локальный content-addressed ID (не tag).
$imageId = docker image inspect aidoctor-cdr:synthetic --format '{{.Id}}'
$imageId

$env:PYTHONPATH = (Resolve-Path .\backend).Path
python -m app.workers.cdr_synthetic_once --run-synthetic --image-id $imageId
Remove-Item Env:PYTHONPATH
```

Ожидается `PASS: синтетический PDF перестроен ... обработка
медицинских вложений ЗАПРЕЩЕНА`.

Если Docker отсутствует, системные пакеты недоступны или образ не
собрался, реальный CDR **не проверен**. Нельзя записывать «CDR выполнен»
или разрешать Context Builder.

## Ограничения и безопасность

Контейнер запускается по полному локальному `sha256:<64 hex>` ID
(никаких тегов и подстановок). `docker run`: `--rm`, `--network=none`,
`--ipc=none`, rootfs read-only, непривилегированный UID/GID 65534,
`--cap-drop=ALL`, `no-new-privileges`, лимит 1 ГиБ памяти, 1 CPU,
64 процесса, `/tmp` на отдельном tmpfs (64 MiB), без монтирования файлов,
без сетевых портов, без Docker-логов. Стандартный вход/выход — двоичные
потоки, stderr не логируется. Процесс получает ограниченный stdin,
хост ограниченно считывает stdout (20 MiB) с таймаутом; при завершении
пытается принудительно удалить конкретный контейнер по случайному имени.

Worker ограничивает исходник 20 MiB, число страниц 8, отказывает при
шифровании, ограничивает размер результата, а Docker запрещает сетевое
подключение. DOCX и остальные форматы отвергаются. На Windows необходима
корректная конфигурация Docker Desktop/Linux containers.

**Не является гарантией безопасности:** у Poppler возможны уязвимости,
Docker daemon — отдельная привилегированная доверенная граница,
контейнеры не равны VM/gVisor, базовый Dockerfile не закреплён digest,
JPEG/PDF выход требует повторной проверки и AV, а преобразование
уничтожает исходную текстовую семантику. Восстанавливать медицинский текст
без OCR нельзя; OCR и LLM не включены. Выход нельзя показывать врачу как
санитизированный, класть в основное хранилище или использовать в
Context Builder.

## Проверки и конфликты

1. **Владение данными:** PostgreSQL и исходное файловое хранилище
   остаются источниками статусов/оригиналов. Демо не записывает туда данные.
2. **Контракты:** не меняются модели/HTTP API/Alembic/AV/Context Builder.
   Используется существующий недоверенный выход.
3. **Эволюция:** реальное подключение файлов пациентов потребует отдельного
   сервиса с правами, блокировками, аудитом входа и результата, новым
   форматом доверия к AV и sandbox, а также DOCX через самостоятельный
   конвертер. Использовать этот CLI для клинических файлов запрещено.

### Критерии готовности

- Все unit-тесты, Ruff, Alembic check и полная регрессия проходят.
- Docker-образ собирается только из узкого контекста.
- Smoke-test по ID созданного образа выводит `PASS` и не содержит PHI.
- Состояние карантина и клинические API не меняются.
- Никакого значения «sanitized/processing_allowed=True» нет.
