## 1. Что уже работает и что не реализовано

**Реализовано и проверено:**

1. Врач `doctor_ui1` работает с пациентами в AIDoctor.
2. Врач создаёт AI-запрос; он сохраняется в PostgreSQL с идентификаторами врача, пациента и хешами снимков.
3. Агент ChatGPT **«Для Тани»** через Site и MCP-инструменты `get_demo_patient` / `get_demo_context` читает **действительный** контекст AIDoctor, а не встроенные фиктивные JSON.
4. Сервер Site проверяет подтверждённый Site user ID до выбора персонального ключа врача; сам ключ берётся из защищённого серверного runtime-secret.
5. AIDoctor v2 независимо проверяет ключ, роль врача, принадлежность AI-запроса, действующую связь с пациентом и синтетический характер данных.
6. Агент выполнил один вызов `submit_demo_analysis`, который сохранил `draft_requires_review`. Сообщён результат **HTTP 201**.
7. Врач видит полученный анализ в истории AI-запросов («Посмотреть черновик AI-анализа»).

**Пока не реализовано:**

- Кнопка «Сохранить запрос и контекст» **не вызывает модель**. Для текущей связки анализ запускается **из чата ChatGPT**, а не из AIDoctor.
- ChatGPT/MCP **не добавляет автоматически** записи в историю, тесты или назначения. Ответ хранится отдельно в `ai_demo_analyses`.
- Действующий `aidoctor_demo_analysis.v1` содержит текстовое резюме, гипотезы, лекарственные **риски**, недостающие сведения, рекомендуемые обследования, источники и ограничения; **нет структурированного контракта назначения** (dose_value, dose_unit, frequency_per_day и т. п.).
- Полноценная изоляция **двух одновременно работающих врачей в Site** пока не подтверждена отдельным сквозным тестом; у первого врача привязка работает.
- Передача **реальных** медицинских данных не разрешена в текущем публичном демо.
- Предложенный впоследствии ZIP `AIDoctor_PRESENTATION_ANXIETY_AVIANDR_NO_API_2026-10-25.zip` **не устанавливался**. AI-2 с 20-минутным разрешением также **не устанавливался**. Не считать их частью действующего сервера.

## 4. Три MCP-инструмента действующего Site

| MCP-инструмент | Назначение | Действие на сервере Site |
|---|---|---|
| `get_demo_patient` | Получить данные синтетического пациента | После проверки пользователя выбрать ключ врача, получить разрешённые данные через AIDoctor v2 |
| `get_demo_context` | Получить сохранённый контекст конкретного AI-запроса | Проверка того же врача и пары `patient_id`/`request_id`, v2 GET, возврат `ai_agent_context.v1` |
| `submit_demo_analysis` | Передать готовый AI-разбор для просмотра врачом | Повторная проверка пользователя, UUID и SHA, серверный POST v2 с персональным ключом врача |

**Нельзя:** подменять текущий источник статическими JSON при 401/403/404; принимать `doctor_id` модели как основание выбора ключа; отдавать секрет через MCP-ответ/HTML/JavaScript; использовать один ключ сразу для нескольких врачей.

Если ChatGPT не видит `submit_demo_analysis`, в настройках существующего подключения/плагина обновить список инструментов и проверить, что write-инструмент опубликован в `tools/list`. Такое обновление однажды потребовалось проверить, но к моменту первого теста **все три инструмента уже были доступны**.

## 5. Реальные API AIDoctor

Все маршруты ниже имеют префикс `/api/v1`.

### 5.1 Текущая интеграция AI-3 — использовать именно её

**Чтение:**

```http
GET /api/v1/integrations/site-builder/v2/agent-context?patient_id={patient_id}&request_id={request_id}
X-AIDoctor-Doctor-Key: <персональный секрет, только сервер Site>
```

Успех: `200`, объект `ai_agent_context.v1`. AIDoctor проверяет врача, пациента, сохранённый AI-запрос и актуальность снимка. Сведения включают `question`, `patient_context`, `doctor_context`, `orders_review`, `orders_sha256`, `excluded_attachments`. В `orders_review` утверждённые назначения **отдельно** от черновых.

**Запись:**

```http
POST /api/v1/integrations/site-builder/v2/analyses
Content-Type: application/json
X-AIDoctor-Doctor-Key: <тот же персональный секрет врача>
```

Успех: `201 Created`, формат `aidoctor_demo_analysis.v1`, статус только `draft_requires_review`. Результат пишется в отдельную таблицу `ai_demo_analyses`.

**Просмотр врачом через браузер (обычная врачебная сессия AIDoctor):**

```http
GET /api/v1/patients/{patient_id}/ai-requests/{request_id}/demo-analysis
Authorization: Bearer <врачебный токен, не Site-ключ>
```

Если ответа нет — `404`, текст «AI-анализ ещё не поступил». Это значит, что кнопка просмотра отработала, но черновик отсутствует у данного запроса.

**Обычная подготовка запроса врачом:**

```http
POST /api/v1/patients/{patient_id}/ai-requests
GET  /api/v1/patients/{patient_id}/ai-requests
GET  /api/v1/patients/{patient_id}/ai-requests/{request_id}/agent-context
```

Последний GET требует обычную врачебную авторизацию; его **не** используют на сервере Site с паролем врача. Для Site применяется v2 GET с отдельным ключом.

### 5.2 Устаревший общий канал AI-1

```http
POST /api/v1/integrations/site-builder/demo-analyses
X-AIDoctor-Bridge-Token: <старый общий секрет>
```

Режим ограничен `doctor_ui1` и синтетическими данными. Этот маршрут **не нужен работающей v2-интеграции**, и его рекомендуется держать выключенным: `AIDOCTOR_DEMO_CALLBACK_ENABLED=0`. Старый `AIDOCTOR_SITE_BRIDGE_TOKEN` не требуется в новой версии Site. Не удалять сам маршрут/таблицу без отдельной задачи: это обратная совместимость.

### 5.3 Хеши

- `context_sha256` — **исходное** `patient_context.content_sha256` сохранённого AI-запроса.
- `orders_sha256` — отдельное поле `orders_sha256` объекта `ai_agent_context.v1`.
- Нельзя вычислять один SHA-256 от всего HTTP JSON или самостоятельно пересериализовать ответ в JavaScript. Значения берутся **как есть**.
- Сервер AIDoctor сравнивает хеши со снимком запроса и проверяет актуальность клинического контекста/назначений. При несовпадении — отказ, обычно `409`.
- Если после создания запроса карта или назначения изменились, безопасный путь — **создать новый AI-запрос**, а не изменять хеши вручную.

## 6. Схемы обмена

**Чтение:** `ai_agent_context.v1`. Точная схема в `docs/ai_agent_context.v1.schema.json`.

**Запись:** `aidoctor_demo_analysis.v1`. Точная MCP JSON Schema в `docs/site_builder_submit_demo_analysis.schema.json`; серверная модель — `backend/app/schemas/ai_demo_bridge.py`.

Обязательные поля POST:

```json
{
  "schema_version": "aidoctor_demo_analysis.v1",
  "request_id": "<UUID из текущего GET>",
  "patient_id": "<UUID из текущего GET>",
  "context_sha256": "<64 lowercase hex из patient_context.content_sha256>",
  "orders_sha256": "<64 lowercase hex из orders_sha256>",
  "status": "draft_requires_review",
  "summary": "<от 20 до 4000 символов>"
}
```

Выше **шаблон, не готовое тело HTTP**: литералы в угловых скобках необходимо заменить реальными значениями внутри защищённого Site. Не передавать из чата секреты.

Необязательные массивы и ограничения действующей backend-схемы:

| Поле | Максимум | Состав |
|---|---:|---|
| `hypotheses` | 10 | `title`, `rationale`, `confidence` |
| `medication_risks` | 12 | `medication`, `risk`, `severity` |
| `missing_information` | 12 | строки |
| `suggested_examinations` | 12 | `name`, `rationale` |
| `sources` | 15 | `title`, `url` HTTP(S), `relevance` |
| `limitations` | 10 | строки |

Перечисления: `confidence ∈ {low, medium, high, uncertain}`; `severity ∈ {low, moderate, high, critical, unknown}`. Поля, отсутствующие в схеме, сервер запрещает.

**Чего нет в POST-схеме:** отдельных структурированных полей *назначения* (`active_ingredient`, `dosage_form`, `strength`, `dose_value`, `dose_unit`, `frequency_per_day`, `times_local`, `duration_days`). Действующий первый пример ответа фиксировал **превышение дозы сертралина 300 мг/сут**, но это было предупреждение в анализе, а не запись/заполнение назначения. Для будущего UI потребуется новый контролируемый контракт предложений с подтверждением врача.

Отдельно смотрим `enabled`, `expires_at`, `revoked_at`. **`revoked_at IS NULL` не означает, что ключ активен**: CLI при отзыве устанавливает `enabled=false`. Срок ключа — 90 суток с выдачи.

## 9. Контрольный сквозной тест (повторять только на НОВОМ AI-запросе)

### Уже подтверждённый пример (25.10.2026)

- Врач: `doctor_ui1`.
- Пациент UUID: `7ede85ab-c0a5-476b-83e0-d12a71cdef15`.
- AI-запрос UUID: `d2016eda-612c-4042-ab9e-5777b14761cf`.
- Чтение двумя MCP-инструментами через v2: **200**, оба SHA совпали.
- Запись через `submit_demo_analysis`: **201**, один POST, `draft_requires_review`.
- Анализ содержал замечание о дозе сертралина и требовал врачебной проверки; назначения не изменены.
- Другой запрос того же пациента `3cae26af-dd14-400f-8169-6cf993d4fe5f` не становится автоматически обработанным.

**Не отправлять иной JSON на уже завершённый request_id**: сервер вернёт `409`, если для него имеется отличный AI-черновик. Для новой демонстрации создать новый AI-запрос (желательно актуальный контекст и вопрос).

### Шаги для нового теста

1. Войти в AIDoctor под нужным врачом. Выбрать его синтетического пациента.
2. В рабочей области AI сохранить **новый** вопрос/запрос. Скопировать новые `patient_id` и `request_id`.
3. Открыть **ChatGPT с агентом «Для Тани»**, подключённым к существующему Site. Убедиться, что доступны `get_demo_patient`, `get_demo_context`, `submit_demo_analysis`.
4. Попросить агента прочитать **только эту пару UUID**, проверить `doctor_id`, `schema_version`, `context_sha256`, `orders_sha256`; подготовить анализ и **один раз** отправить структурированный JSON со статусом `draft_requires_review`.
5. Зафиксировать HTTP: для чтения **200**, для первой записи **201**. При таймауте/неопределённом исходе **не делать слепой повтор POST**, сначала проверить наличие черновика.
6. В AIDoctor открыть **того же пациента и тот же запрос**, нажать «Посмотреть черновик AI-анализа». Убедиться, что он сохранён в истории и не утвердил никакие назначения.

### Что сказать агенту для нового запроса

> Получи свежий контекст AIDoctor по patient_id=… и request_id=… через действующие MCP-инструменты. Проверь подтверждённого врача и хеши из API. Подготовь структурированный демонстрационный разбор без выдуманных фактов и источников. Отправь результат через submit_demo_analysis ровно один раз, только как draft_requires_review. Не изменяй назначения. При ошибке, 409 или неопределённом результате не повторяй POST и сообщи код.

## 10. Диагностика ошибок

| Симптом / код | Вероятная причина | Проверка / действие |
|---|---|---|
| `401` при чтении в Site | Не выбрана привязка Site user ID, отсутствует runtime-secret, ключ неверный/истёк/отозван или обновлён Site не той ревизией | На Site проверить серверную проверку `oai-authenticated-user-id`, наличие 4 переменных и действующую публикацию; на VDS — `enabled`, `expires_at`; не печатать ключ |
| `404` при v2 GET | Пара `patient_id`/`request_id` не принадлежит этому врачу, нет связи врача с пациентом или пациента | Сверить точные UUID нового AI-запроса в интерфейсе/БД, не подбирать чужие |
| `403` при v2 GET/POST | Пациент несинтетический и нет разрешённого режима | Для демо использовать синтетического пациента; не выставлять `synthetic=true` у реального пациента |
| `409` при чтении | Старый/повреждённый снимок контекста, изменились данные/назначения или запрос создан до нужного формата | Создать новый AI-запрос из текущей карты пациента |
| `409` при записи | Контекст устарел или для request_id уже записан **другой** черновик | Проверить GET просмотра черновика; не отправлять новый JSON поверх существующего |
| `422` при POST | Неверная схема: ограничения строк/массивов, UUID, регистр hex или дополнительные поля | Сверить с `docs/site_builder_submit_demo_analysis.schema.json`, особенно лимиты 10/12/15 |
| `HTTP 201`, а кнопка показывает «нет анализа» | Открыт другой пациент/AI-запрос или браузер не обновил страницу | Сверить `request_id`, повторно загрузить страницу, проверить запись SQL из §8.7 |
| «Черновик недоступен: AI-анализ ещё не поступил» | Кнопка работает, **но для данного request_id ещё нет результата** | Провести POST для этого конкретного запроса; старые запросы не обрабатываются сами |
| В ChatGPT нет третьего инструмента | MCP список устарел или Site опубликовал не ту версию | Проверить `tools/list`, обновить инструменты подключения, перезапустить чат |
| Таймаут POST / сеть оборвалась | Результат **неизвестен**: сервер мог сохранить его до обрыва | Сначала проверить наличие черновика; не создавать повторную запись |
| После перезапуска VDS нет переменных | Переменные изменены в `.env.test`, но контейнер не пересоздан | `up -d --no-deps --force-recreate --wait app` |
| Вновь TLS/DNS NXDOMAIN | Использовано локальное имя `pashkovnpc.clodocd.com` | Использовать действующий `185-200-179-238.sslip.io` или публичный собственный домен |

## 11. Безопасность, несколько врачей, реальные случаи

**Защиты в текущей реализации AIDoctor:**

- Выделенный ключ врача в Site, в PostgreSQL хранится только SHA-256 ключа.
- Ключ действует до **90 дней**, может быть отозван или перевыпущен.
- Site должен сначала подтвердить пользователя (`oai-authenticated-user-id`) и выбрать соответствующий ключ **сервером**, а не аргументом модели.
- AIDoctor независимо проверяет роль `doctor`, принадлежность AI-запроса врачу и связь `DoctorPatient`.
- Внешний результат — отдельный `draft_requires_review`, **не** медицинское назначение.
- В таблице `site_doctor_access_audit` сохраняются действия `read_context` и `submit_draft`.
- Перенаправления, запись секретов в логи и автоматические повторы POST на стороне Site запрещены проектным контрактом.

**Для второго врача:** создать учётную запись и пациента, выпустить новый ключ, зарегистрировать отдельную подтверждённую Site-user привязку; затем провести отрицательный тест доступа к запросу **другого** врача. Не публиковать Site для общего доступа до проверки изоляции.

**Для случая жюри:** безопасный путь — **новый вымышленный пациент**, а не три старых seed-пациента. Не маркировать реальные данные как синтетические. В коде для несинтетических случаев предусмотрена комбинация `AIDOCTOR_SITE_ALLOW_NON_SYNTHETIC=1` и `external_ai_consent=true`, но эти технические флаги **не доказывают** согласие, безопасность или правовое основание передачи медицинских данных. На текущем публичном тестовом VDS оставить режим **выключенным**.

**Приватность файла:** этот runbook содержит технические адреса, пример UUID и Site user ID, но **не содержит ключей, паролей, cookies или Bearer-токенов**. Если выкладываете его в публичный GitHub, предварительно удалите Site user ID и идентификаторы живых запросов.

## 12. Изменения проекта и исходники для проверки

Код AIDoctor (по актуальному предоставленному архиву):

- `backend/app/api/routes/site_doctor_bridge.py` — v2 GET и POST.

- `backend/app/api/routes/ai_workspace.py` — подготовка и чтение AI-запросов.

- `backend/app/services/ai_agent_context.py` — снимок назначений, их хеши.
- `backend/app/schemas/ai_demo_bridge.py` — фактические ограничения выходного JSON.
- `backend/app/models/ai_demo_bridge.py` — таблица `ai_demo_analyses`.
- `backend/app/models/site_doctor_credential.py` — ключи и журнал обращений.

- `docs/site_builder_submit_demo_analysis.schema.json` — MCP JSON-схема.

На стороне Site исходники/настройки хранятся **в самом Site Builder**, а не в Git-архиве AIDoctor. Поэтому восстановление только из Git-репозитория **не восстановит** Site-адаптер и runtime-secrets. По сообщениям Site Builder последний опубликованный вариант — **версия 4**, доступ **только владельцу**; реальный POST позже подтвердил работу этого варианта.

## 13. Что важно для следующей сессии разработки

**Цель следующего этапа:** собрать единый интерфейс «врач → карта пациента → вопрос AI → AI-ответ → предложения → одобрение → история / назначения / тесты» в одном рабочем пространстве.

**Условия:**

1. Работать **по новому приложенному архиву** актуального исходного кода, а не по старым ZIP из переписки.
2. Сохранить работающую v2-интеграцию Site Builder и все существующие черновики.
3. Сначала согласовать архитектуру интерфейса и контракты; **не вносить патчи до согласования**.
4. Пока **не подключать платный LLM API** и не имитировать живой вызов. Анализ из ChatGPT с MCP — действующий вариант.
5. Приём AI-анализов не равен импорту в историю/назначения/тесты. Для переноса нужны отдельные структуры, сравнение «было → предлагается», права врача и аудит.
6. Для презентации использовать **один вымышленный клинический кейс**. Остальных пациентов **не удалять** до отдельного разрешения; при необходимости скрыть их в интерфейсе.
7. Не применять ZIP `AIDoctor_PRESENTATION_ANXIETY_AVIANDR_NO_API_2026-10-25.zip`: пользователь прямо сообщил, что эти изменения пока не вносит.

**Конфликты, которые нужно предотвратить:**

- **Владение данными:** PostgreSQL — единственная клиническая истина; AI создаёт отдельное предложение, а не скрыто меняет карту.
- **Контракты:** сохранять `ai_agent_context.v1` и `aidoctor_demo_analysis.v1`, новые поля назначений/тестов вводить версионированно и только по согласованию.
- **Эволюция:** каждый запрос всегда связан с `doctor_id + patient_id + request_id`; добавление врачей, пациентов или нового LLM-провайдера не должно смешивать записи.

**Критерии готовности будущего этапа:** запрос и результат видны рядом с картой одного пациента; предложения можно принять/отклонить поштучно; доза, единицы и кратность помещаются в реальные поля после явного действия врача; сохраняется история правок; MCP и обратный POST остаются совместимыми.
