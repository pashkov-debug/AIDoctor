# UI-2B — две постоянные синтетические карточки и видимые визиты

## Назначение

UI-2B продолжает UI-2A поверх исходных моделей `Patient`, `DoctorPatient`,
`Encounter`, `HistoryEvent`, `MedicalObservation` и существующего Context Builder.
Новых таблиц, миграций, зависимостей или AI-провайдера нет.

**Важное различие:**
- Врач `doctor_ui1` видит **только разрешённые** карточки, их визиты,
  внутренние события, субъективные наблюдения и Digest.
- Пациент `patient_ui1` видит только данные собственного аккаунта:
  псевдоним, номер и дату создания карточки. Это намеренно ограниченный
  серверный контракт, а не отсутствие данных в БД.
- Пациент **не видит** неутверждённые черновики, внутренние заметки,
  наблюдения, Context Builder или AI-предложения. Отдельная система
  публикации врачебно утверждённых фактов будет создана на следующих этапах.
- Администратор управляет ролями и привязками, но не получает доступ к
  внутренним клиническим GET-маршрутам врача.

## Где в интерфейсе визиты

1. Войти как `doctor_ui1` на http://127.0.0.1:8000/app.
2. В разделе «Обзор» найти блок «Пациенты». У каждой карточки
   есть кнопка **«Визиты и история →»**.
3. Откроется страница с быстрыми переходами «Визиты», «История»,
   «Наблюдения», «Context Builder». Счётчик в заголовке показывает число
   загруженных строк; все визиты читаются из `GET /api/v1/patients/{id}/encounters`.
4. Для повторной загрузки используйте «Обновить карточку».
   Если записи не появились, сначала проверьте, что выполнен `--apply`,
   затем посмотрите сообщение ошибки на странице и серверный вывод FastAPI.

## Две истории в постоянной локальной aidoctor

Команда `python -m backend.scripts.seed_ui2b_synthetic` по умолчанию
**ничего не меняет**. Флаг `--apply` выполняет одну транзакцию:

- Первый пациент — уже привязанный к `patient_ui1`, сценарий тревоги/сна.
  Сохраняет UI-2A (4 визита, 6 событий, 3 наблюдения) и добавляет
  ещё 6 визитов, 10 событий, 7 наблюдений.
- Второй пациент — `Синтетическая С-002 — сниженное настроение`.
  Карточка создаётся один раз, доступ предоставляется `doctor_ui1`.
  Добавляется 9 визитов, 13 событий, 9 наблюдений.
- Все истории вымышленные, с временной глубиной 57–65 дней.
  Значения `0–10` — **невалидированные субъективные учебные оценки**.
  Это не PHQ-9, не GAD-7 и не диагнозы; лекарств и утверждённых назначений нет.
- Для каждого факта есть `seed_key` или `source_ref`, поэтому
  повторный `--apply` не дублирует записи. Уже существующие записи не заменяются.
  При конфликте одноимённой или несинтетической карточки команда отказывает.
- Команда допускается только при `APP_ENV=local`,
  локальном PostgreSQL и реальной БД `aidoctor`. На `aidoctor_test`,
  удалённой БД и в production работа seed запрещена.
- У второй карточки **нет автоматически созданного пользовательского
  аккаунта**: пароли не встраиваются в seed. Для её пациентского кабинета
  создайте `patient_ui2` и привяжите его в UI администратора.

### Команды Windows PowerShell

Из корня проекта, активированная `.venv`:

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini upgrade head
$env:PYTHONPATH = "backend"
python -m backend.scripts.seed_ui2b_synthetic
python -m backend.scripts.seed_ui2b_synthetic --apply
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

Если нужен отдельный вход второго пациента, **один раз**:

```powershell
python -m backend.scripts.create_user patient_ui2 patient
```

Затем войти как `admin_ui1` и на странице «Администрирование» связать
`patient_ui2` со второй карточкой (не менять привязку `patient_ui1`).
Далее два пациентских входа независимы.

### Проверки без пересоздания БД

```powershell
python -m ruff check backend
python -m ruff format --check backend
node --check backend/app/web/assets/app.js
python -m pytest backend/tests/test_ui2b_unit.py -v
python -m alembic -c alembic.ini check
```

**Автоматические тесты только на отдельной `aidoctor_test`:**

```powershell
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_ui2b_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

Внутренняя фикстура `pg_engine` делает `drop_all/create_all`:
категорически запрещено указывать `TEST_DATABASE_URL` на основную
`aidoctor`. Основная БД продолжает хранить долгоживущую историю.

## Критерии готовности

1. У `doctor_ui1` в «Пациентах» две синтетические карточки.
2. Кнопка «Визиты и история» открывает явный раздел с датами и счётчиком.
3. Для заполненной первой карточки видно не меньше 10 визитов,
   16 событий, 10 субъективных наблюдений.
4. Для второй карточки — не меньше 9 визитов, 13 событий, 9 наблюдений.
5. Повторный `--apply` ничего не дублирует.
6. `patient_ui1` не видит врачебных внутренних записей, API возвращает 403.
7. `ruff`, `pytest` на `aidoctor_test`, Alembic проверены локально.

## Конфликты, риски и границы

**Владение:** PostgreSQL — источник истины. Клинические draft-визиты
принадлежат врачебному workflow; пациент не получает их автоматически.

**Контракты:** модель и API сохранены; frontend обращается к уже имеющимся
маршрутам `/encounters`, `/history-events`, `/context`, `/context/digest`.
Нет изменения миграций или существующих записей.

**Эволюция:** отдельная политика публикации позволит позднее показывать
пациенту разрешённые сведения без расширения текущего внутреннего API.
Аудит, Safety Alerts и безопасность вложений не обходятся.

**Ограничения:** UI-2B не назначает препараты, тесты, лечение и не
отправляет запросы AI. Посев учебных данных не заменяет автоматические
регрессионные проверки. Использовать только синтетические данные.
