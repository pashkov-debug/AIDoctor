# Этап 5.5 — безопасные маршруты внутренних уведомлений

## Область
Только **in_app** для учётной записи врача; **email, SMS, push и фактическая
доставка не реализованы**. Существующий worker этапа 5.4 по-прежнему
не запускается автоматически и через CLI умеет только показывать статусы.
Новая маршрутизация намеренно **не подключена** к `process_one`: интеграция
контракта маршрутов с реальным провайдером — этап 5.6.

В PostgreSQL добавлены таблицы:
- `safety_notification_routes`: единственный маршрут на
  `(patient_id, recipient_user_id, channel)`, `enabled`, `confirmed_at`;
- `safety_notification_route_events`: журнал включения/отключения с actor_id.

Внешние адреса и медицинские факты не сохраняются в маршрутах. Установка
`confirmed_at` означает только согласие авторизованного врача использовать
**собственный внутренний аккаунт**. Это **не верификация email/телефона**,
**не согласие пациента** и не факт доставки.

## HTTP API
Относительно `/api/v1`:

| Метод | Путь | Поведение |
|---|---|---|
| GET | `/patients/{patient_id}/safety-notification-route` | Собственная настройка врача или `null` |
| PUT | `/patients/{patient_id}/safety-notification-route` | Идемпотентно включить/отключить собственную настройку |

Пример тела PUT: `{"channel":"in_app","enabled":true}`.
При включении врач подтверждает внутренний аккаунт текущей bearer-сессией.
Повтор того же значения не создаёт новое событие журнала.
`channel` можно опустить: по умолчанию `in_app`.
Отсутствие прав: `401` без сессии, `403` для пациента/администратора,
`404` для врача без связи DoctorPatient и удалённого пациента.
Публичного API настройки чужого получателя нет.

## Политика маршрутизации
`eligible_routes(session, patient_id=...)` возвращает только технические ID
маршрута и получателя. Условия **все одновременно**:
- маршрут включён и подтверждён владельцем внутренней учётной записи;
- пользователь существует и имеет роль `doctor`;
- существует действующая связь `DoctorPatient` с данным пациентом;
- пациент не удалён (soft-delete);
- канал `in_app`.

Если любого условия нет, список пуст. Настройки маршрута сами по себе
не меняют `SafetyOutbox.status`, не создают события Outbox и не
открывают сетевые соединения. В 5.6 **обязательно** проверять эту
политику непосредственно перед попыткой доставки и повторно после
потенциально долгого ожидания — не считать текущий флаг безусловным
правом на отправку в будущем.

## Конфликтный анализ
1. **Владение данными:** связь DoctorPatient и роль пользователя —
   источник истины для доступа; таблица маршрутов хранит только opt-in.
2. **Контракты:** старые `/safety-alerts`, Outbox и `process_one` не
   меняются. Добавлены только новые API и таблицы.
3. **Эволюция:** email/SMS требуют отдельной проверки адреса, согласий
   и хранения секретов. Не добавлять их в эту таблицу без новой миграции.

В integration-тестах **не должно быть `SKIPPED`**.
Fixture удаляет и создаёт схему в `*_test` БД.

## Границы
Ни real-time inbox, ни patient consent, ни проверка внешнего контакта,
ни SLA, ни гарантии доставляемости, ни фонового scheduler нет.
Не использовать с реальными клиническими данными до аудита безопасности.
