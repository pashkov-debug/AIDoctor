# AI-3 — постоянные врачебные подключения Site Builder (без AI-2)

## Назначение

Это самодостаточное дополнение к уже установленному AI-1. **AI-2 устанавливать не нужно**.
Убираем зависимость от 20-минутных разрешений и кнопки в кабинете.
Вместо них сервер хранит **хеш отдельного ключа для каждого врача**.
Один врач не получает данные другого через общий Bridge-токен.

Никакие реальные медицинские данные автоматически не открываются. Новый вымышленный
случай можно создать под любым врачом, не ограничиваясь С-001/С-002/С-003.

## Новые API

- `GET /api/v1/integrations/site-builder/v2/agent-context?patient_id=UUID&request_id=UUID`
- `POST /api/v1/integrations/site-builder/v2/analyses`

Оба метода требуют заголовок `X-AIDoctor-Doctor-Key`, который
**сервер Site добавляет сам**. Значения этого заголовка нельзя включать в
MCP-аргументы, URL, браузерный JavaScript или общий prompt.

GET возвращает `ai_agent_context.v1`; POST принимает `aidoctor_demo_analysis.v1`
и сохраняет только `draft_requires_review`. `patient_id` и `request_id`
обязательны; сервер проверяет принадлежность запроса врачу из ключа,
актуальную связь DoctorPatient, наличие пациента и хеши контекста/назначений.
Все успешные чтения и передачи результатов аудитируются.

Прежние синтетические API AI-1 сохранены для обратной совместимости.
После перехода Site на v2 рекомендуется выключить старый callback, если он
больше не нужен.

## Включение на VDS (после локальных проверок и зелёного push)

В `.env.test`, права 0600, **не в Git**, добавьте:

```text
AIDOCTOR_SITE_MULTI_DOCTOR_ENABLED=1
AIDOCTOR_SITE_ALLOW_NON_SYNTHETIC=0
```

Выполните:

```bash
cd /opt/aidoctor/git-checkout
docker compose --env-file .env.test -f deploy/compose.test.yaml \
  up -d --no-deps --force-recreate --wait app
```

Новый врач должен быть уже создан администратором и иметь роль `doctor`.

### Выпустить ключ врача (однократно, на VDS)

```bash
cd /opt/aidoctor/git-checkout
docker compose --env-file .env.test -f deploy/compose.test.yaml \
  exec -T app python -m backend.scripts.site_doctor_keys issue doctor_ui1
```

Команда выведет секрет **один раз**, заменит предыдущий ключ этого врача,
положит в БД только SHA-256; срок ключа — 90 суток. Храните ключ в
защищённом Site runtime secret, соответствующем только этому врачу.

**Не выводите ключ в чат, GitHub, скриншоты или логи.**

Чтобы отозвать доступ:

```bash
docker compose --env-file .env.test -f deploy/compose.test.yaml \
  exec -T app python -m backend.scripts.site_doctor_keys revoke doctor_ui1
```

Для второго врача измените `doctor_ui1` на его логин и создайте
**отдельный** Site secret. Пароли AIDoctor не используйте.

## Требование к Site Builder — принципиально важно

Site Builder должен определить личность пользователя по проверенным данным
платформы, не по произвольному `doctor_id` из аргументов модели.

`verified_site_user -> configured doctor credential`

Никакого пользовательского выбора чужого ключа, общей переменной,
неограниченного доступа по одному Bridge-токену или доверия входному
`doctor_id`. Привязка ключей к врачам возможна лишь когда Site действительно
позволяет надёжно определить вызывающего пользователя на сервере.

**Если Site не поддерживает подтверждённую идентичность и её серверное
сопоставление с врачом**, нельзя публиковать общий много-врачебный
инструмент. Вариант для презентации: один приватный Site только для
одного врача; другим врачам — отдельные приватные подключения.

Два старых MCP-инструмента чтения должны быть переведены с
`built_in_fictional_demo` и статических JSON на v2 GET.
Инструмент `submit_demo_analysis` должен использовать v2 POST.
Это настройки Site Builder, они **не включены в ZIP проекта**.

## Не синтетический случай / кейс жюри

Новый **вымышленный кейс**, введённый жюри, не обязан быть одним из трёх
seed-сценариев: врач может создать его с `demographics.synthetic=true`,
создать AI-запрос, и Site будет читать его по персональному ключу врача.

Для несинтетических данных предусмотрен двойной защитный барьер:
`AIDOCTOR_SITE_ALLOW_NON_SYNTHETIC=1` **и**
`patient.demographics.external_ai_consent=true` у пациента, к которому
врач имеет подтверждённый доступ.

**Это технические флаги, а не доказательство юридически действительного
согласия.** На публичной тестовой VDS включать их для реальных медицинских
данных нельзя без проверки правового основания, информированного согласия,
политики хранения данных, разрешения на передачу сторонней модели,
аудита и независимых испытаний безопасности. Для презентации рекомендуется
вымышленный кейс без идентификаторов.

## Конфликты, готовность и ограничения

- Данные: PostgreSQL — источник истины; ключ привязан к врачу; назначений AI не меняет.
- Контракты: AI-1 оставлен, новые маршруты версионированы `/v2/`.
- Эволюция: другой врач получает свой ключ, не меняя API.
- До 90 дней один ключ врача может читать любой его **разрешённый**
  клинический AI-запрос без кнопки и без одноразовой выдачи.
- **Модель не запускается автоматически из кабинета**: анализ остаётся
  ручным вызовом существующего ChatGPT-агента.
- Первый реальный вызов Site ещё НЕ проверен. Ожидаем GET 200 и POST 201.
- Старый рабочий каталог БД, Docker-тома и тестовые пациенты не удаляются.
- Ограничение: проверенное соответствие Sites-пользователь ↔ врач должно
  быть реализовано и подтверждено на стороне Site до общей публикации.
