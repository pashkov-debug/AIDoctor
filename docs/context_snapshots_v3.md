# Context Snapshots v3 — контракт и ограничения

## Зачем

v2: клиент присылает baseline в `POST .../context/delta`. SHA-256 подтверждает
только внутреннюю целостность и может быть пересчитан клиентом.

v3: baseline хранится **на сервере** в PostgreSQL JSONB, привязан к пациенту,
автору и UUID снимка. Клиент знает только `snapshot_id`. Это повышает
доверие к происхождению сравниваемых версий, но не заменяет журнал аудита.

## Действующие маршруты

Все — под `/api/v1/patients/{patient_id}/context` и требуют роли врача
или администратора плюс доступа к пациенту:

- `POST /snapshots`: сохранить текущий Context, возвращает `201` + метаданные.
- `GET /snapshots`: 50 последних метаданных (без полного тела).
- `GET /snapshots/{snapshot_id}`: метаданные и оригинальный сохранённый JSON.
- `POST /snapshots/{snapshot_id}/delta`: серверная Delta относительно текущего Context.

Старые `/context`, `/context/digest`, `/context/delta` остаются без изменения.

Ошибки: `401` — нет авторизации; `403` — роль не врач/администратор;
`404` — нет доступа либо снимок отсутствует у данного пациента;
`409` — повреждённый/неполный/слишком крупный Context.

## PostgreSQL и миграция

Таблица `context_snapshots`: UUID записи, пациент, автор, дата создания,
версия схемы, SHA-256, число фактов, JSONB контекста.
Ни оригиналов вложений, ни API-ключей LLM в JSONB быть не должно.

После распаковки из корня проекта:

```powershell
python scripts/create_context_snapshots_migration.py
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini check
```

`down_revision` вычисляется один раз из текущей локальной Alembic-головы,
поэтому не создаётся независимая ветка миграций. При двух головах
генератор завершится ошибкой. Автоматический downgrade запрещён,
поскольку иначе удалились бы медицинские снимки.

## Гарантии и ограничения

- Снимки не обновляются и не удаляются через HTTP API.
- Текущий контекст должен быть неусечённым, с правильным SHA-256,
  без дубликатов `kind + record_id`, не более 400 фактов и 512 КиБ.
- После сохранения последующие события пациента не изменяют старый снимок.
- До сериализации доступ проверяет `require_doctor` + `require_patient`.
- `snapshot_id` всегда проверяется вместе с `patient_id`, без IDOR.
- JSONB-строка хранит персональные данные. Не выводить payload в логи,
  не показывать в публичной документации реальные примеры.
- Нет retention, шифрования на уровне приложения и аудита скачивания.
- Context Builder получает данные несколькими SQL-запросами, поэтому на фоне
  конкурентных правок возможна несогласованность среза.

## Smoke-test

1. Создать синтетического пациента, привязать врача.
2. Сделать POST `/snapshots`, получить UUID и 201.
3. Проверить GET `/snapshots`, GET `/snapshots/{uuid}`.
4. Добавить событие истории, вызвать POST `/snapshots/{uuid}/delta`.
5. Проверить `added[0]` и неизменный оригинальный снимок.
6. Попробовать под другим врачом: все маршруты возвращают 404.

Тесты:

```powershell
python -m pytest backend/tests/test_context_snapshots_unit.py -v
python -m pytest backend/tests/test_context_snapshots_api.py -v -rs
```
