# UI-2C — подтверждение факта, публикация пациенту, контракт будущего AI-решения

## Архитектурная фиксация

Существующий `history_events` хранит исходную внутреннюю клиническую историю.
Новые `clinical_publications` и `clinical_publication_audit` хранят **решение врача о
подтверждении** одного конкретного `HistoryEvent` и отдельную опубликованную
*проекцию* (`patient_text`). Это не копия исходного `fact_json` и не назначение.

- Источник истины о клиническом событии: `HistoryEvent`, включая `supersedes_id`.
- Источник истины о видимости: `ClinicalPublication.status == published`.
- Журнал: `ClinicalPublicationAudit` (подтверждение, публикация, отзыв; версия и автор).
- PostgreSQL и FastAPI проверяют права, статусы и версии; frontend только отображает.
- Patient API возвращает **только** `{id, text, published_at}`, без исходных полей.
- События, замещённые `supersedes_id`, исключаются из опубликованных данных,
  даже если публикация ранее была выполнена. Повторное разрешение требует проверки
  новой исправленной версии события.
- Передача AI ещё не реализована. Контракт `doctor_context` и настройка РКИ
  остаются без изменений.

## Шаги в интерфейсе

1. Врач открывает «Визиты и история» у доступного пациента.
2. У события нажимает «Подтвердить запись»: появляется объект со статусом `confirmed`.
   Пациент **ничего нового не видит**.
3. Нажимает «Подготовить публикацию пациенту», вводит **отдельный текст**.
   Исходный `fact_json` не вставляется в поле автоматически.
4. Подтверждает флажок и сверяет содержимое окна подтверждения.
5. «Опубликовать выбранный текст в БД» переводит запись в `published`.
   Пациент видит её в разделе «Опубликованные врачом сведения».
6. «Отозвать публикацию» с причиной переводит запись в `revoked`.
   Исходный факт не удаляется, текст остаётся доступен врачу в аудируемой записи.

### Запись в БД — точно

| Действие | Мутация в транзакции | Видно пациенту |
|---|---|---|
| Подтвердить | INSERT `clinical_publications` version=1 status=confirmed + INSERT audit | Нет |
| Опубликовать | UPDATE status=published version=2 patient_text=... + INSERT audit | **Только patient_text** |
| Отозвать | UPDATE status=revoked version=3, reason, time + INSERT audit | Нет |
| Исправить HistoryEvent | Существующее событие не меняется; новая запись с `supersedes_id` | Старый опубликованный текст скрывается |

Нельзя бесшумно переписать `patient_text`: после публикации повторное
редактирование и повторная публикация запрещены. Для новой редакции нужен
отдельный исходный факт/корректирующее событие и новое подтверждение.

### HTTP API

| Метод | Маршрут | Роль |
|---|---|---|
| GET | `/api/v1/patients/{patient_id}/clinical-publications` | Связанный врач |
| POST | `/api/v1/patients/{patient_id}/history-events/{event_id}/confirm` | Связанный врач |
| POST | `/api/v1/patients/{patient_id}/clinical-publications/{id}/publish` | Связанный врач |
| POST | `/api/v1/patients/{patient_id}/clinical-publications/{id}/revoke` | Связанный врач |
| GET | `/api/v1/patients/me/clinical-publications` | Только текущий пациент |

Для публикации нужен JSON:

```json
{
  "expected_version": 1,
  "patient_text": "Согласованное с врачом сообщение.",
  "confirm_patient_visibility": true
}
```

Для отзыва:

```json
{
  "expected_version": 2,
  "reason": "Врачебное уточнение"
}
```

409 — конфликт версии, повторное подтверждение, попытка повторной
публикации, исправленный источник. 403 — не та роль. 404 — нет доступа
к карточке или источнику.

## Что именно будет утверждаться из будущего ответа AI — UI-4

AI-ответ будет **структурированным и версионированным черновиком**, а не
потоком SQL или свободным текстом с кнопкой «Записать всё».

### Обязательные кнопки в будущей AI-рабочей области

- **«Уточнить»**: новый AI-запрос и версия черновика, без изменения назначений.
- **«Отклонить»**: решение врача, причина и аудит; никаких назначений.
- **«Одобрить выбранное»**: доступна только после предварительного
  просмотра **каждого выбранного элемента**, редактирования полей врачом
  и вторичного подтверждения. Действует на уровне **элементов**, а не
  всего AI-текста.
- **«Просмотр изменений БД»**: перечень таблиц/типов сущностей и операций,
  источник данных, привязка к пациенту, конфликт версий контекста,
  индивидуальные флажки выбора. Пока нет корректных серверных контрактов,
  такой кнопки на UI-2C нет, чтобы не создавать ложную функциональность.

### Предварительная матрица будущего применения

| Тип предложения AI | После врачебного одобрения | Что увидит пациент |
|---|---|---|
| Лекарство | Нормализованное лекарственное назначение: действующее вещество, форма, доза, единицы, путь введения, частота, часовой пояс, расписание, срок, противопоказания | Только утверждённое действующее назначение |
| Обследование | Заказ обследования с исполнителем/параметрами | Назначенное обследование |
| Психологический тест | Назначение из версионированного проверенного каталога | Назначенный тест |
| Комментарий/гипотеза | Остаётся внутри AI-черновика / врачебного решения | Ничего автоматически |
| Сводка для пациента | Не публикуется автоматически. Только отдельный согласованный текст по будущему контракту публикации | Проверенный текст |
| Safety Alert | Отдельный контур безопасности, без автоматического закрытия | По правилам Safety Alerts, не по кнопке одобрения |

Названия будущих таблиц пока не фиксируются: сначала проверить существующие
модели/ORM/API в UI-3 и использовать их вместо создания дубликатов.
Не выдумывать дозировки и схемы, не переводить гипотезы в подтверждённые факты.
`doctor_context` (включая РКИ — российские клинические рекомендации Минздрава)
передаётся отдельно от пациентского контекста, применимость проверяется.

### Серверный контракт будущего approve

Обязательные проверки в одной атомарной транзакции:
1. Врач уполномочен и связан с пациентом.
2. Черновик относится к нужному пациенту, его версия актуальна.
3. Каждый элемент выбран и отредактирован с полной проверкой типа,
   полей и бизнес-ограничений (доза, единицы, расписание, источники).
4. Context Builder/digest и doctor_context версии совместимы с
   утверждаемой версией, либо явное повторное согласование.
5. Идемпотентный ключ операции, защита от повторной публикации и конкуренции.
6. Запись нормализованных назначений и врачебного решения с аудитом.
7. Только после COMMIT пациентские API возвращают новые записи.

Никакого автономного назначения, скрытого изменения рецепта,
массового одобрения без проверки конкретных элементов или снятия
Safety Alerts.

## Команды PowerShell (Windows, корень проекта)

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini check
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

В **другом** терминале для тестов:

```powershell
$env:PYTHONPATH = "backend"
python -m ruff check backend
python -m ruff format --check backend
node --check backend/app/web/assets/app.js
python -m pytest backend/tests/test_ui2c_unit.py -v
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_ui2c_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL -ErrorAction SilentlyContinue
python -m alembic -c alembic.ini check
```

**ВНИМАНИЕ:** pytest с `pg_engine` удаляет и создаёт таблицы.
`TEST_DATABASE_URL` допустим только для `aidoctor_test`.
На рабочей локальной БД `aidoctor` оставить постоянных синтетических
пациентов; не выполнять `down -v`, `drop_all`, восстановление фикстур.

## Три конфликта / границы

1. **Владение**: `HistoryEvent` — факт, `ClinicalPublication` — решение об
   утверждении и видимости, не новый клинический факт.
2. **Контракты**: прежние внутренние API, Context Builder и Safety Alerts
   не изменяются; добавлен только самостоятельный API публикаций и миграция.
3. **Эволюция**: новые типы раскрываемых сущностей потребуют расширения
   allowlist/версионированного контракта; нельзя пропускать их через `fact_json`.

Недостающие возможности UI-2C: отдельное создание/исправление клинических
фактов врачом, нормализованные назначения, каталог тестов, AI-workflow,
полная оценка нормативной применимости и тестирование в браузере.
**Нельзя использовать для реальных пациентов до клинической и ИБ-проверки.**
