# AIDoctor UI-1B — безопасная минимальная карточка пациента

Дата: 2026-10-22. Разработано поверх UI-1A из переданного архива
`AIDoctor_UI-1A_doctor_only_2026-10-22.zip`. Локальная разработка
**только на синтетических данных**.

## Границы функционального инкремента

- Врачебный кабинет UI-1A, обе вкладки, РКИ и versioned `doctor_context` не менялись.
- В интерфейс добавлена авторизация `patient`, роль после входа проверяется
  по `/auth/me`, отображается отдельная навигация и карточка пациента.
- Пациентская карточка загружается по `GET /api/v1/patients/me/portal`.
  Backend берёт идентификатор пользователя **из bearer-сессии**, не из
  параметров клиента, возвращает только `patient_id`, `alias`, `created_at`
  и `schema_version = patient_portal.v1`.
- Пациент не может использовать новый эндпоинт для чтения чужой карточки;
  удалённые карточки игнорируются. При отсутствии привязки — 404.
  Без авторизации — 401, для врача/администратора — 403.
- Создание и привязка пациента **повторно использует** существующие
  `/patients` и `/access/patient-account`. Новых SQL-таблиц и миграций
  нет, тяжёлых зависимостей нет.
- Никакие клинические данные, `demographics_json`, лекарства, визиты,
  результаты опросников, черновики или внутренние заметки **не входят
  в новый контракт**. Нет фиктивных кнопок назначения/тестирования.

ВНИМАНИЕ: некоторые **старые** API (`encounters`, `history-events`,
`questionnaires`) ещё используют широкое правило `require_patient`.
Их полный аудит и отдельные политики пациентской публикации необходимы
до работы с реальными данными. UI-1B их не вызывает и не меняет,
поскольку изменение старых контрактов должно быть отдельным проверяемым
этапом. Конфиденциальность всех существующих API не сертифицирована.

## Применение на Windows

Распакуйте ZIP UI-1B **поверх уже установленного UI-1A**, сохранив
структуру каталогов. ZIP содержит только новые или изменённые файлы,
в том числе полный корневой `README.md`.

Не нужно выполнять `alembic upgrade head` для UI-1B: миграций нет.
Для контроля текущего состояния можно выполнить:

```powershell
python -m alembic -c alembic.ini current
python -m alembic -c alembic.ini check
$env:PYTHONPATH = "backend"
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

### Подготовка синтетического пациента

Не создавайте повторно уже существующего пользователя. При необходимости
создайте **пациентскую** и **административную** учётные записи:

```powershell
$env:PYTHONPATH = "backend"
python -m backend.scripts.create_user patient_ui1 patient
python -m backend.scripts.create_user admin_ui1 admin
```

Врач `doctor_ui1` уже существует после UI-1A.
Пароли задаются отдельно, не включены в репозиторий.

В новом окне PowerShell (при запущенном FastAPI) выполните:

```powershell
.\scripts\setup_ui1b_demo.ps1
```

Скрипт по очереди запросит пароли пациента, врача и администратора,
проверит роли через действующий API, затем **только если пациент не
привязан** создаст **одну синтетическую карточку** с
`demographics.synthetic = true` от имени врача и привяжет её от
имени администратора. Команда предназначена только для loopback-адреса
разработки и не требует прямого SQL-доступа; использует существующие
backend-проверки. Если привязка не удалась после создания карточки,
выведет её ID для ручного исправления, не удаляя данные.

Адрес в браузере: http://127.0.0.1:8000/app .
Войдите как `patient_ui1` с установленным вами паролем. Будут видны
только обозначение, идентификатор и дата создания карточки.
Врач по `doctor_ui1` продолжает видеть прежнюю панель.

Для проверки авторизации без учётной записи:

```powershell
.\scripts\smoke_ui1.ps1
.\scripts\smoke_ui1b.ps1
```

### Тестирование

```powershell
python -m ruff check backend
python -m ruff format --check backend
python -m pytest backend/tests/test_ui1_unit.py backend/tests/test_ui1b_unit.py -v
python -m alembic -c alembic.ini check
```

**Только на отдельной тестовой PostgreSQL `aidoctor_test`:**

```powershell
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_ui1_pg.py backend/tests/test_ui1b_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

Фикстура `pg_engine` делает `drop_all/create_all`.
**Никогда не выполняйте этот набор на основной или production БД**.

## Конфликты и безопасность

1. **Владение данными.** `patients.user_id` — единственная действующая
   связь пациента с его учётной записью, источник истины PostgreSQL.
   Запрос пациента не может передать `patient_id` для выбора другой карточки.
2. **Совместимость.** UI-1A сохраняется без изменения URI или форматов.
   Новая проекция `patient_portal.v1` не содержит ранее не согласованных
   медицинских полей; старые API не переписываются.
3. **Эволюция.** Отдельная будущая схема опубликованных врачом фактов,
   решений и назначений должна управлять доступом пациента. Необходимо
   серверное разграничение полей, версий, статусов, аудита и оснований
   публикации, а не проверка только в JavaScript.

**Возможные риски:** HTTP-токены существуют 8 часов, logout закрывает
все сессии аккаунта; frontend хранит bearer-токен только в памяти
вкладки. Старые клинические API пока требуют отдельного review.
Данный этап не предназначен для медицинской эксплуатации.

## Критерии готовности UI-1B

1. Врач входит, видит прежнюю панель и сохраняет обе вкладки.
2. Пациент входит, видит только свою карточку после её привязки.
3. Врач и администратор получают 403 на `/patients/me/portal`;
   анонимный запрос — 401.
4. Без привязки, при soft-delete карточки — 404; чужие данные не возвращаются.
5. Администратор может связать пациента только существующим API,
   повторный запуск seed не создаёт вторую запись после успешной привязки.
6. Ruff, Alembic check, модульные и PostgreSQL-тесты на `_test` проходят;
   регрессия UI-1A отсутствует.
