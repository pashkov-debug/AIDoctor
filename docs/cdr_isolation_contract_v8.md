# Этап 6.4.1a — контракт изоляции CDR (19.10.2026)

## Статус

Это **подготовительный, исполняемый в Python контракт** будущего CDR-контейнера,
а не подключённый CDR-движок. Нет образа, исполняемого worker, парсера PDF/DOCX,
сохранения результата, снятия карантина или нового HTTP API.

Владелец оригинала и статуса — прежние `MedicalAttachment`/PostgreSQL.
Точка получения байтов — **только**
`prepare_quarantined_cdr_candidate(...)` этапа 6.4.0, с проверкой прав,
последнего AV-отчёта, целостности и PostgreSQL-аудитом `cdr_input`.
`build_unexecuted_cdr_plan(...)` дополнительно сверяет длину и SHA-256
**именно полученного снимка**. Эта функция **не повторяет авторизацию и
не гарантирует свежесть** ранее выданного снимка. После будущего исполнения
потребуется ещё одна проверка статусов и файла до любого результата.

## Публичный внутренний контракт

`app.services.cdr_isolation_contract.build_unexecuted_cdr_plan(candidate,
image_by_digest=...) -> UnexecutedCDRPlan`.

Параметр `candidate` должен быть экземпляром `QuarantinedCDRCandidate`;
запрещены повреждённые метаданные, несовпадение SHA-256, нулевые и
некорректные размеры, типы кроме PDF/DOCX. Не путать проверку MIME в
снимке с полной разборкой файла: её здесь **нет**.

`image_by_digest` принимает только канонический OCI-образ вида
`registry.example/namespace/image@sha256:<64 lowercase hex>` — тег
или произвольный аргумент командной строки не принимается.
Это только пример формата, а **не предложенный рабочий реестр или образ**.

Объект содержит кортеж `docker_argv` с неизменяемыми ограничениями:
- нет сети (`--network=none`) и IPC;
- корневая ФС только для чтения, `/tmp` — ограниченный `tmpfs`;
- непривилегированный UID/GID 65534, сброшенные capabilities и no-new-privileges;
- CPU 1, память 1024 МиБ без увеличенного swap, не более 64 процессов;
- нет томов, пробросов портов и логирования stdout в Docker;
- `--pull=never`: запрещена неявная загрузка контейнера;
- входные данные передаются **не через argv, env, путь или том**.

Worker-путь `/usr/local/bin/aidoctor-cdr-worker` — **будущий контракт**.
Образ с этим исполняемым файлом не предоставляется. Функция
**не выполняет ни subprocess, ни сетевой вызов, ни Docker** и не
передаёт ни одного байта за пределы Python-процесса.

`executed == False`, `sanitized == False`,
`processing_allowed == False` — всегда. `stdin_payload` содержит
опасные байты; его запрещено печатать, логировать, отдавать пользователю,
парсеру или клиническому Context Builder.

## Конфликты архитектуры

1. **Владение данными**: источник истины PostgreSQL и закрытое
   хранилище; план не устанавливает статус санитизации и не хранит файлы.
2. **Совместимость**: прежние модели, Alembic, API, 6.4.0 и политики
   `require_processing_clearance` не затронуты.
3. **Эволюция**: движок, его запуск, формат результата и проверка output
   появятся за отдельной границей. До этого *не существует* безопасного
   выходного документа.

## Выбор реального CDR (нужно согласовать отдельно)

**Рекомендовано для оценки:** Dangerzone, поскольку он пересобирает
PDF/DOCX в PDF из пикселей с изоляцией декодеров.
Однако на Windows использует собственный Podman/WSL, требует отдельных
образов и не является лёгкой Python-зависимостью.
Без OCR текст итогового PDF не будет пригоден для поиска и надёжного
извлечения в Context Builder — OCR в данном инкременте запрещён.

**Альтернатива:** собственный контейнер LibreOffice/PDF-рендера с
ограниченными входом/выходом, но требуется отдельный аудит безопасности,
модели угроз, версий и формата результата. Сам по себе LibreOffice
не является CDR-гарантией.

Вариант «просто извлечь текст» **не является CDR**.

## Риски и границы

**Нет реальной изоляции**, пока команда не выполнялась. Флаги Docker
сами по себе не гарантируют безопасность окружения. Фиксация образа
по digest не подтверждает издателя и не проверяет уязвимости образа.
Снимок из оперативной памяти может устареть после возвращения из
PostgreSQL-транзакции. Контроль лимитов stdout/stderr, времени исполнения,
выходных байтов и повторная аттестация AV/CDR ещё не реализованы.

Не запускать вручную `docker_argv` из плана на реальных вложениях.
**Следующий шаг:** явно согласовать конкретный CDR-движок, режим
Windows/Docker и сохранение клинического текста. Только после этого
проектировать исполняемый адаптер и проверку настоящего output.
