# Патч AIDoctor: доступ к пациентам и Context Builder 1.0

## Изменённые контракты

- `POST /api/v1/patients`: только роли `doctor` и `admin`.
  Если пациента создаёт врач, запись в `doctor_patients` создаётся атомарно,
  одновременно с пациентом. Администратор создаёт запись без автоматической
  привязки; затем назначает врача через `/access/link`.
- `GET /api/v1/patients`: список и поиск **только среди доступных** пациенту
  или врачу карточек. Для администратора — все неудалённые.
- `GET /api/v1/patients/{id}`: `401` без bearer, `404` для отсутствующей
  или чужой карточки. Удалённые записи исключены.
- `GET /api/v1/patients/{id}/context`: только прикреплённый врач или
  администратор (`patient` получает `403`; чужой врач — `404`).
  Выход: `ClinicalContext` версии `1.0` с `content_sha256`, `items`,
  `truncated_sources`, `excluded_attachments_count`.

**Обратная совместимость:** публичные адреса и поля существующих ответов
пациента сохраняются. Запросы без авторизации теперь намеренно отвергаются,
а список пациента намеренно фильтруется. Это изменение политики доступа.

## Что такое контекст

Контекст читает с PostgreSQL визиты, нескорректированные события истории,
наблюдения и ответы на шкалы. Исходные факты не интерпретируются.
Данные содержат `record_id`, дату, категорию, `source_ref` и `payload`.

В каждой коллекции — не более 100 новейших записей. При превышении лимита
устанавливается соответствующий флаг `truncated_sources`. Потребитель обязан
рассматривать неполный контекст как неполный; медицинские решения без
дозагрузки принимать нельзя.

Файлы медицинских исследований НЕ входят в контекст, даже если статус
`ready`: антивирусная проверка, извлечение текста и политика доверия
будут реализованы отдельно. `excluded_attachments_count` — только счётчик.
Контекст не отправляется внешним сервисам и не содержит медицинских
рекомендаций.

`content_sha256` вычисляется из канонического JSON с фактами, версией
контракта, ID пациента и индикаторами усечения. `generated_at` в хэш не
входит. Это идентификатор содержимого, **не криптографическая подпись**.

## Установка

Перед заменой файлов зафиксируйте локальные изменения (`git status`,
`git diff`) и проверьте изменения против ваших файлов в PyCharm.
Полные файлы в пакете основаны на опубликованном `master`; если локальная
ветка ушла вперёд, переносите изменения выборочно.

Скопируйте файлы из архива в корень репозитория, не заменяя `main.py`.
Запустите **один раз**:

```powershell
python scripts/register_context_router.py
```

Скрипт добавляет только импорт и регистрацию `context_router` в уже
имеющемся `main.py`, не затрагивая регистрацию файлового маршрута.
До изменений он создаёт `backend/app/main.py.context-backup`.

Затем:

```powershell
python -m ruff check backend
python -m pytest backend/tests -v -rs
python -m alembic -c alembic.ini check
python -m pytest backend/tests/test_patient_access_patch.py -v -rs
python -m pytest backend/tests/test_context_builder_patch.py -v -rs
```

Тесты PostgreSQL используют только отдельную `TEST_DATABASE_URL`
с суффиксом `_test`; фикстура очищает таблицы, **не запускать на БД с данными**.
`SKIPPED` означает, что интеграция НЕ проверена.

## Конфликты и безопасность

1. Владение данными: SQL-фильтрация проходит по PostgreSQL; `DoctorPatient`
   является источником права врача. Веб-слой вызывает проверки для ID-ресурса.
2. Контракты: `/api/v1` сохраняется; новое ограничение авторизации — намеренно
   несовместимое изменение поведения для анонимных клиентов.
3. Эволюция: `ClinicalContext` версионирован. Новые категории фактов,
   delta, политика отмены согласия, ревизии и отчётные представления требуют
   расширения схемы версии, а не изменения поведения молча.

Ограничения MVP:
- Builder сам не проверяет права: вызывающие сервисы ОБЯЗАНЫ делать это до вызова.
- `created_at` фильтрует записи по моменту сборки, но это пока
  не транзакционный повторяемый снимок при параллельных изменениях.
- Нет журналирования чтений, согласия на передачу LLM, антивируса, CDR,
  шифрования приложением, FHIR-конвертации, ограничения размеров JSON-полей.
- Создание пациента без привязанного аккаунта допустимо; связывание с
  аккаунтом пациента доступно только администратору.
- Не использовать данные настоящих пациентов до промышленной валидации.
