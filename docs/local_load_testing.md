# Локальная проверка соединения AI и нагрузочное тестирование

## Назначение

AIDoctor пока **не подключён к LLM**. Вместо него используется технический локальный HTTP-сервис.
Сервер возвращает подтверждение обмена без диагнозов, назначений, клинического анализа и внешних
запросов. Сервис принимает исключительно технические поля: UUID запроса, SHA-256, версию протокола,
признак синтетического пациента и количества назначений. Полный контекст и Bearer-токен ему не отправляются.

Нагрузочный тест работает **только по `127.0.0.1`** и только когда AIDoctor сообщает
`APP_ENV=local` или `test`. До запуска проверяется, что пациент привязан к синтетической карточке,
видимой тестовому врачу. Тест AIDoctor выполняет исключительно GET-запросы после двух операций входа;
логин создаёт две обычные временные записи сессий авторизации в PostgreSQL.
Назначения, психологические тесты и клинические данные не изменяются.

## Проверка соединения: три PowerShell-терминала

В корне проекта, с активной `.venv`:

Терминал 1 — PostgreSQL и AIDoctor:

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini upgrade head
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

Терминал 2 — имитатор:

```powershell
python -m scripts.mock_ai_server
```

Терминал 3 — проверка связности:

```powershell
python -m scripts.smoke_ai_connection
```

Клиент запросит пароль `doctor_ui1`, найдёт синтетического пациента, при необходимости
создаст AI-запрос **только в AIDoctor**, прочитает неизменяемый snapshot и передаст в
имитатор только техническую квитанцию. Итог:

`ГОТОВО: транспорт работает. LLM НЕ вызывалась`.

Опции:
```powershell
python -m scripts.smoke_ai_connection --fresh
python -m scripts.smoke_ai_connection --patient-id "<UUID>"
```

## Нагрузочный тест приложения

Запусти FastAPI без `--reload` для корректного измерения; останови прежний сервер
через `Ctrl+C` перед новым стартом:

```powershell
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Открой второй PowerShell-терминал:

```powershell
python -m scripts.load_test_local --mode app --levels 2,5,10,20 --duration 15 --think-ms 400 --doctor-share 0.3 --profile "ПК-разработка" --output "reports/load_local.json"
```

Вводятся пароли `doctor_ui1` и `patient_ui1`. Соотношение потоков по умолчанию 30% врачей,
70% пациентов. У врача моделируются списки пациентов, назначения и история AI-запросов;
у пациента — карточка, назначения, тесты и опубликованные сведения.

**Важно:** потоки используют по одному токену каждой роли. Это одновременные виртуальные
клиенты, но **не** измерение нагрузки 20 *различных* врачебных и пациентских аккаунтов.
Тест не измеряет рендеринг браузера и постоянные websocket-соединения.

Для длительного устойчивого измерения:

```powershell
python -m scripts.load_test_local --mode app --levels 10,20,40,80 --duration 90 --think-ms 500 --doctor-share 0.3 --p95-limit 800 --error-limit 1 --profile "VM-4vCPU-8GB" --output "reports/load_vm_4cpu.json"
```

Название `VM-4vCPU-8GB` — **метка эксперимента**, скрипт не подтверждает фактическую
конфигурацию. Пользователь должен отдельно записать железо и системные метрики.
Нагрузка увеличивается ступенями, без параллельных сценариев записи или авторизации
каждого виртуального пользователя. Максимальное значение — 100 потоков.
Выполнять нагрузку **только на отдельной локальной синтетической БД разработки**,
не на реальной production и не во время pytest, пересоздающего таблицы.

## Нагрузка только на локальный AI MOCK

При работающем имитаторе:

```powershell
python -m scripts.load_test_local --mode mock --levels 5,10,20,40 --duration 15 --think-ms 200 --profile "AI MOCK" --output "reports/load_mock.json"
```

Это измеряет HTTP-заглушку. Не является измерением задержки, стоимости или пропускной
способности настоящей LLM.

## Метрики и критерии

В отчёте доступны:

- `virtual_clients`: одновременно работающие потоки;
- `rps`: выполненные запросы в секунду;
- `p50_ms`, `p95_ms`, `p99_ms`: распределение задержки успешных ответов;
- `error_rate_pct`, `errors_by_kind`: доля и тип ошибок;
- разрез по ролям `doctor`, `patient`;
- технические сведения тестового клиента и параметры запуска.

Начальные целевые пороги (их можно изменить): p95 не более 800 мс и ошибки не более 1%.
**Это инженерные критерии теста, а не норматив или гарантия качества.**
За устойчивую ёмкость можно принимать только ступень, которая держится минимум
10–15 минут с приемлемым p95/p99, без роста очередей и ошибок, при CPU менее примерно
80%, RAM без постоянного роста, отсутствии переполнения пула соединений БД и
с запасом на всплески. Более короткие прогоны — только поиск очевидных узких мест.

Ошибки 401/403/404 до начала ступени означают проблему подготовленных аккаунтов/маршрутов,
а не предел производительности. HTTP 429/5xx во время ступени считаются ошибками.

## Как получить ответ «какое железо сколько выдержит»

Один и тот же сценарий выполнить для нескольких **предполагаемых профилей сравнения**:

| Профиль для эксперимента | vCPU | RAM | Устойчивая нагрузка |
| --- | ---: | ---: | --- |
| Минимальная ВМ (гипотеза) | 2 | 4 ГБ | измерить |
| Базовая ВМ (гипотеза) | 4 | 8 ГБ | измерить |
| Усиленная ВМ (гипотеза) | 8 | 16 ГБ | измерить |

Значения мощности здесь — **конфигурации, которые следует испытать**, а не утверждения
о числе пользователей, которое они выдержат. На практике многое зависит от PostgreSQL,
диска, сети, размера истории, запросов Context Builder, количества процессов Uvicorn,
очередей обработки, скорости LLM и внешних API.

На Windows посмотреть оборудование:

```powershell
Get-CimInstance Win32_Processor | Select-Object Name,NumberOfCores,NumberOfLogicalProcessors
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
```

Во время теста в другом терминале:

```powershell
docker stats --no-stream
docker compose exec postgres psql -U aidoctor -d aidoctor -c "SELECT count(*) AS connections FROM pg_stat_activity;"
```

Также записать загрузку CPU, память Uvicorn и PostgreSQL, задержку диска из «Диспетчер
задач → Производительность». При тестировании на ВМ повторить измерение на ней; запуск
генератора нагрузки на той же слабой ВМ может ограничивать результат собственным CPU,
поэтому для больших нагрузок потребуется отдельный генератор.

**Не экстраполировать** количество пользователей линейно с числом CPU или размером RAM.
В отчётах сравнивать только устойчивые ступени, достигнутый RPS, p95/p99, ошибки и ресурсы.
Вместимость по активным пользователям/врачам и зарегистрированным пациентам — разные метрики.

## Проверки

```powershell
python -m ruff check backend scripts/mock_ai_server.py scripts/smoke_ai_connection.py scripts/load_test_local.py --fix
python -m ruff format backend scripts/mock_ai_server.py scripts/smoke_ai_connection.py scripts/load_test_local.py
python -m ruff check backend scripts/mock_ai_server.py scripts/smoke_ai_connection.py scripts/load_test_local.py
python -m ruff format --check backend scripts/mock_ai_server.py scripts/smoke_ai_connection.py scripts/load_test_local.py
python -m pytest backend/tests/test_ai_mock_connection.py backend/tests/test_local_load_unit.py -v
```

Полная регрессия только с `TEST_DATABASE_URL`, указывающей на `aidoctor_test`.
В лабораторных условиях система должна стартовать с миграциями, все GET-маршруты
возвращать 200, симулятор отвечать без LLM, а рост нагрузки — фиксироваться метриками.

## Риски и ограничения

- Исключено использование реальных персональных/медицинских данных; порт 8765 не открывать в интернет.
- Время обработки LLM, клиническая валидация, конкурирующие записи врачей и тесты браузерной
  отзывчивости **не** измеряются этим стендом.
- Для достоверных пределов потребуются тесты с большим количеством отдельных синтетических
  аккаунтов и realistic распределением активности, а также отдельно тесты тяжёлых записей,
  долгого Context Builder и обработки событий Safety Alerts.
- На production CI/CD и нагрузочные тесты с этим тестовым имитатором не включать.
