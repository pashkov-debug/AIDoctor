# AIDoctor — этап 6.3.0: подготовка входа из карантина для будущего AV

Дата: 18.10.2026. Статус: **подготовительный инкремент, НЕ завершение AV/CDR**.

## Назначение и границы

В этапе 6.2 хранилище проверяет целостность исходных байтов и фиксирует
`prechecked_quarantined`, но это не антивирус и не разрешение на извлечение.
Этап 6.3.0 добавляет внутренний серверный контракт `capture_quarantined_scan_input`:
администратор может сформировать **иммутабельную копию** ограниченного
файла после повторной проверки на дискриминирующих условиях 6.2, а
операция фиксируется в PostgreSQL-аудите. В будущем этот буфер может быть
передан изолированному AV-движку. Сейчас потребителя буфера нет.

**Не реализованы:** AV, CDR, sandbox-процесс, API запуска сканирования,
очередь сканирования, вердикты `clean`/`infected`, автоматическое извлечение
или помещение содержимого в клинический Context Builder. Выполнение
`capture_quarantined_scan_input` не меняет `antivirus_status=not_scanned`,
`processing_allowed=false`, `quarantine_active=true`.

## Контракт и авторизация

```python
capture_quarantined_scan_input(
    session,
    patient_id=...,
    attachment_id=...,
    actor_id=...,
    storage=AttachmentStorage(...),
) -> QuarantineScanInput
```

Это **внутренний** интерфейс, не HTTP API. Проверяет реальную роль `admin` из
PostgreSQL, отсутствие soft-delete пациента и привязку файла к пациенту;
затем блокирует запись вложения (`SELECT ... FOR UPDATE`). Это не замена
авторизации будущего worker и не разрешение передавать объект через сеть.

Требует:
- `MedicalAttachment.extraction_status == quarantined`,
  `extracted_text_ref IS NULL`;
- запись предварительной проверки со статусом `prechecked_quarantined`;
- совпадение пациента, SHA-256 и размера со снимком 6.2;
- свежую проверку фактических байтов (лимит 20 МиБ, ключ хранения,
  размер, хеш, сигнатура и ограничения DOCX).

При успехе возвращается `QuarantineScanInput` с `content: bytes`.
Содержимое не берётся из JSON клиента. Перед отдачей результата обязателен
успешный commit аудита `attachment_security_events.action=scan_input`.
При изменении/отсутствии файла статус записи проверки становится `rejected`
и фиксируется причина; повторно он не разблокируется даже после
восстановления байтов. При сбое файловой системы возвращается исключение
`InspectionUnavailable`, записывается `error`, выпуск байтов невозможен.
Неавторизованный доступ отвергается до чтения байтов.

`QuarantineScanInput` привязан к **самим скопированным байтам**, а не к
пути — будущий worker не должен переоткрывать оригинал по имени.
Нельзя сохранять сырой буфер в логах, JSON, Outbox или context snapshots.
При эксплуатации ограничивать конкуренцию и потребление памяти (до 20 МиБ
на одновременно обрабатываемое вложение плюс промежуточная копия).

## База данных

Новая ревизия `aiextract_v3_20261018` после `aiextract_v2_20261018`.
Она расширяет только допустимые действия прежней таблицы аудита:
`read`, `precheck`, `scan_input`. Новых таблиц, AV-статусов, колонок и
изменений HTTP-контрактов нет. Downgrade запрещён во избежание утраты
или недостоверной интерпретации событий аудита.

## Три типа конфликтов

1. **Владение данными:** PostgreSQL хранит статус проверки и журнал,
   хранилище владеет байтами. Проверенный снимок не меняет источник истины.
2. **Контракты:** API этапов 0–6.2, результаты `precheck`, `download`,
   миграции и `require_processing_clearance` не изменены. Для успеха
   `scan_input` надо применять новую миграцию ДО использования модуля.
3. **Эволюция:** будущие сканеры должны возвращать отдельный проверяемый
   verdict с идентификатором движка/версии сигнатур и хешем именно входных
   байтов; решение о допуске должно быть отдельным, только после реального
   сканирования и надёжной изоляции worker.

## Невыполненные требования для полноценного 6.3

- Согласовать локальный AV/CDR-движок и лицензирование, исполняемый процесс
  / контейнер, ограничение ресурсов, обновление сигнатур и реакцию на сбой.
- Разделить worker и API по правам ОС; запретить worker доступ к БД
  и оригиналам сверх минимально необходимого.
- Реализовать аттестуемый вердикт на конкретный SHA-256, защиту от
  `unknown`, `timeout`, ошибок движка; политику удаления и очистки CDR.
- Не снимать карантин без отдельного архитектурного решения и
  отрицательных сквозных тестов.

## Windows / PowerShell

Из корня проекта, после замены файлов:

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini heads
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check
python -m ruff check backend
python -m pytest backend/tests/test_attachment_scan_boundary_unit.py -v

# Только заранее созданная локальная тестовая БД *_test;
# фикстура удаляет и создаёт в ней SQL-таблицы!
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_attachment_scan_boundary_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

Режимы эксплуатации и ACL Windows не проверяются этими unit-тестами.
Из-за локального файлового хранилища операции могут быть уязвимы к
атаке со стороны процессов с правом замены исходных файлов/каталогов:
требуются защищённые ACL, запрет символических ссылок/reparse points
и отдельный контроль перед реальным AV/CDR. Даже чистая сигнатура/хеш
не доказывает безопасность медицинского файла.
