# AIDoctor UI-1A — кабинет врача, профиль и клинический контекст

Дата: 2026-10-22. Реализация рассчитана только на локальную проверку синтетических данных.
Источник: актуальный `AIDoctor-master (6).zip`. Файловый контроль отката до начала
изменений: `224/224`, различий, отсутствующих файлов и временных мостов `0`.
Технические pytest/PostgreSQL/Alembic проверки выполняются отдельно на машине разработчика.

## Что реализовано

- `/` перенаправляет на `/app`; `/app` обслуживает интерфейс на одном origin с FastAPI,
  `/app/assets/*` — локальные JS/CSS. Никакого CDN, нового JS-framework или build-chain.
- Авторизация через существующие `/api/v1/auth/login`, `/auth/me`, `/auth/logout`.
  Токен только в памяти вкладки; после обновления страницы требуется вход.
  Статический HTML **публичный**, медицинские данные грузятся только из защищённого API.
- Реализован только кабинет врача (`doctor`) с обзором доступных пациентов
  через существующий `/api/v1/patients`. Для ролей `patient` и `admin`
  приложение сообщает о незавершённости их кабинетов и отзывает токен
  через действующий `/auth/logout` (при недоступности сервера токен забывается
  в памяти вкладки). Никаких декоративных кабинетов с фиктивными операциями.
  Их авторизация и существующие backend API не меняются.
- Врач: две переключаемые вкладки «Профиль врача» и
  «Клинические настройки / Контекст AI»; серверная валидация, БД и аудит.
- Выход отзывает все текущие bearer-сессии пользователя согласно
  существующей политике backend (не менялась).
- Сформирован минимальный, отдельно разрешаемый будущий `doctor_context.v1`
  **без персональных контактов врача и без медицинских данных пациента**.

## Серверные контракты (относительно `/api/v1`)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/doctors/me/settings` | Оба раздела и единая `version` |
| PUT | `/doctors/me/settings/profile` | Заменить раздел профиля с `expected_version` |
| PUT | `/doctors/me/settings/clinical` | Заменить клинический раздел с `expected_version` |
| GET | `/doctors/me/doctor-context` | Версионированный разрешённый контекст врача |

Только собственный профиль `role == doctor`. Нет маршрута для редактирования
настроек другого врача. Незалогиненный пользователь получает 401; пациент
и администратор — 403. Существует только один источник истины:
`doctor_settings` в PostgreSQL, `doctor_id = users.id`. В неизменяемом
журнале `doctor_settings_audit` сохраняются автор, раздел, версии, время
и **имена изменённых полей**, но не копии email или профессиональных данных.

При первом GET возвращается `version=0` без записи в БД; первый реальный
PUT создаёт строку версии 1. PUT — замена всех полей **одного** раздела,
передавайте полную структуру. При конфликте `expected_version` — HTTP 409,
требуется перечитать данные. Неизменённые данные не увеличивают версию.
Конкурентная первая запись защищена уникальным PK и переводом конфликта в 409.

Пример GET `/doctors/me/doctor-context`:

```json
{
  "schema_version": "doctor_context.v1",
  "doctor_id": "ИД-врача",
  "profile_version": 2,
  "country": "Россия",
  "rki": {
    "scope": "russian_clinical_guidelines_approved_by_minzdrav",
    "mode": "consider_if_verified",
    "source_verification": "required"
  },
  "institution_type": "Амбулаторное учреждение",
  "specialty": "Психиатрия"
}
```

РКИ в данном проекте: **российские клинические рекомендации, утверждённые
Минздравом России** (не термин из методологии исследований). Режимы:
`disabled` (не учитывать, безопасное значение по умолчанию),
`consider_if_verified` (учитывать *только после отдельной проверки* источника,
версии, официального статуса, юрисдикции и клинической применимости).
UI-1A **не проверяет** рекомендации, не объявляет их юридически актуальными,
не передаёт данные в AI и не создаёт назначений. `profile_version` —
общий монотонный номер версии настроек, изменяющийся при любом разделе;
он не идентификатор нормативного документа.

## Запуск на Windows 11 / PowerShell

Из корня проекта, с настроенной Python 3.12 venv:

```powershell
python -m pip install -r requirements.txt -r requirements-dev.txt
docker compose up -d postgres
# Действующий .env не перезаписывать; использовать .env.example только как пример.
python -m alembic -c alembic.ini heads
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current
python -m alembic -c alembic.ini check
$env:PYTHONPATH = "backend"
python -m backend.scripts.create_user doctor_ui1 doctor
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Открыть `http://127.0.0.1:8000/app`; войти под врачом.
Учётные записи создавать только если они ещё отсутствуют. На UI-1A роли
пациента и администратора проверяются на сервере, но их кабинеты в UI ещё
не реализованы. Врачебный список ограничен связями `DoctorPatient`.

Дополнительный smoke-test, в другом терминале:

```powershell
.\scripts\smoke_ui1.ps1
python -m ruff check backend
python -m ruff format --check backend
```

Интеграционные тесты **только на выделенной локальной БД с суффиксом `_test`**:

```powershell
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
# Предварительно создать БД aidoctor_test по scripts/postgres_test_db.ps1
python -m pytest backend/tests/test_ui1_unit.py backend/tests/test_ui1_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

ВНИМАНИЕ: `pg_engine` использует `drop_all/create_all`. Указывать `aidoctor`
или production-БД **запрещено**. На локальной разработческой БД выполнить
`alembic check` после применения миграции; Alembic не запускается здесь
автоматически и никогда не запускается на production в рамках UI-1.

## Границы и конфликтный анализ

1. **Владение данными.** Настройки врача принадлежат `users.id`, изменения
   проходят только через backend. Контекст пациента, snapshots, Safety
   Alerts и файлы не меняются.
2. **Контракты.** Все новые endpoints только `/api/v1/doctors/me/...`.
   Существующие маршруты и модели не переименовываются. UI не допускает
   выдуманных AI-ответов, назначений и тестов.
3. **Эволюция.** `doctor_context.v1` отделён от сохраняемой модели и
   будущего LLM Gateway. В будущем отдельные валидаторы проверят реестр
   и актуальность конкретных РКИ. Изменение формата требует новой версии.

## Дальнейшие этапы

- UI-1B: отдельный кабинет пациента с собственными разрешёнными данными
  поверх существующих API, без публикации неутверждённых назначений.
- UI-1C: отдельный кабинет администратора с ограниченными действующими API.
- UI-2: врач → собственные пациенты → история/контекст/сигналы безопасности
  поверх уже существующих API; клинические записи и назначения только при
  наличии проверенных backend-контрактов.
- UI-3: утверждённые врачебные назначения и опросники пациента.
- UI-4: запросы AI и версионированные черновики с врачебной проверкой.
- UI-5 и UI-6: безопасные синтетические сценарии и полная локальная стабилизация.

Без полной проверки безопасности, согласий, нормативных требований и
политики данных использовать реальные медицинские сведения нельзя.


## Фактические проверки в среде подготовки

Проверено на базе исходного архива: контрольная сверка отката `224/224`;
синтаксис 10 затронутых Python-файлов, `node --check` для нового JavaScript,
контрактные проверки Pydantic, `alembic heads` (одна голова
`ui1_20261022`), `alembic upgrade head --sql` (генерируются обе таблицы).
ZIP собран из новых и изменённых файлов, целостность архива проверяется при выпуске.

**Не проверено здесь:** реальные HTTP-запросы, PostgreSQL, Windows/PowerShell,
полный pytest и Ruff. В текущем окружении отсутствуют `psycopg` и Ruff,
сетевая установка драйвера недоступна. Эти проверки обязательны локально.

## Критерии готовности UI-1A на компьютере разработчика

1. `alembic upgrade head` успешно создаёт обе таблицы на базе разработки,
   а `alembic check` не выявляет незарегистрированных изменений.
2. Врач входит и выходит; чужая/просроченная сессия не проходит проверки.
3. Список пациентов показывает только привязанных врачу пациентов,
   чужая карточка возвращает 404.
4. Обе вкладки сохраняются в PostgreSQL; повторный вход загружает изменения.
5. Параллельная запись с устаревшим `expected_version` возвращает 409;
   успешное изменение появляется в аудите.
6. Маршруты настроек для пациента и администратора возвращают 403,
   а запрос без bearer-токена — 401.
7. `ruff check`, `ruff format --check`, целевые тесты и полный pytest
   проходят на выделенной PostgreSQL `_test`; контуры этапов 4–6 не регрессируют.
