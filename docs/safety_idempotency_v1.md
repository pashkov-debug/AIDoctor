# AIDoctor — этап 5.3: Idempotency-Key для создания Safety Alert

## Назначение и границы

5.2 обеспечивает идемпотентность постановки **одного события Outbox**.
5.3 добавляет идемпотентность **HTTP POST** для ручного создания Safety Alert.
Каналы доставки, worker, почта/SMS/push, автоматический триаж и эскалация
**не реализованы**. `delivery_status` остаётся `not_configured`.

Новая ревизия Alembic: `aisafe_v3_20261018`,
`down_revision = aisafe_v2_20261018`. Старые миграции не меняются.

## Контракт API

`POST /api/v1/patients/{patient_id}/safety-alerts`

Необязательный заголовок: `Idempotency-Key`.

- Допускается ключ 8–128 символов ASCII: первая буква/цифра, далее
  латинские буквы, цифры, `.`, `_`, `:`, `-`.
- Для каждой логической попытки создания клиент генерирует новый случайный
  ключ (рекомендуется UUIDv4); при сетевом повторе отправляет **тот же ключ**.
- Первый корректный запрос возвращает `201` с созданным сигналом.
- Повтор с тем же ключом и теми же значениями `reason_code` и `priority`
  возвращает `201` с **тем же `id`**, без создания второго сигнала,
  клинического события или Outbox. Возвращается **текущее состояние** сигнала:
  если врач уже подтвердил его, ответ покажет `acknowledged`.
- Повтор того же ключа с изменёнными `reason_code` или `priority` возвращает
  `409 Conflict` без новых записей.
- Неправильный формат ключа возвращает `400`.
- Если заголовка нет, контракт остаётся прежним: **каждый POST создаёт
  новый ручной сигнал**.
- Проверка прав на пациента сохраняется до обращения к данным идемпотентности.
  Чужой врач получает `404`; пациент без врачебной роли — `403`.
- Действующие `GET` и `POST .../ack` не меняются.

Пример PowerShell (после получения авторизационного токена):

```powershell
$patientId = "<UUID_СИНТЕТИЧЕСКОГО_ПАЦИЕНТА>"
$token = "<BEARER_ТОКЕН>"
$key = [guid]::NewGuid().ToString()
$headers = @{ Authorization = "Bearer $token"; "Idempotency-Key" = $key }
$body = @{ reason_code = "clinician_review"; priority = "standard" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/v1/patients/$patientId/safety-alerts" -Headers $headers -ContentType "application/json" -Body $body
# Для повторной отправки НЕ меняйте $key.
```

## Владение данными, транзакция и гонки

- `safety_alerts` — состояние ручного сигнала; `safety_alert_events` — аудит
  врачебных действий.
- `safety_outbox` и `safety_outbox_events` — доставка и её технический аудит
  без фактического внешнего транспорта.
- `safety_alert_requests` — отдельная таблица идемпотентности HTTP POST.
  Содержит ссылки на пациента, врача, созданный сигнал и SHA-256-отпечатки
  ключа/семантического тела. Оригинальный ключ и тело запроса не сохраняются.
- Уникальность `(patient_id, actor_id, key_digest)` исключает конкурирующие
  дубли **внутри одного врача и пациента**; ключ в другом контексте
  независим. Запись таблицы хранится бессрочно до появления согласованной
  политики хранения.
- Создание Safety Alert, события `created`, Outbox, события `enqueued`
  и записи ключа — **одна PostgreSQL-транзакция**.
- При гонке один запрос побеждает; конкурент, которому отказал UNIQUE,
  откатывает собственный сигнал/Outbox/аудит и возвращает победивший сигнал
  либо `409` при различном теле.
- Сравнение охватывает значения `reason_code` и `priority`, а не
  буквальный порядок полей JSON.
- API-функция `create_alert` использует собственные `commit`/`rollback`,
  как в 5.2. Не вызывать её внутри более широкой незавершённой транзакции.

Это идемпотентность на уровне **запроса**, а не гарантия внешней доставки.
SHA-256 не скрывает содержимое очень предсказуемых ключей от перебора,
поэтому клиент должен использовать случайные ключи. По возможности
исключите передачу персональных данных внутри `Idempotency-Key`.

## Применение из корня проекта (PowerShell)

До замены: пользователь подтвердил после 5.2, что полный pytest, Ruff
и миграции проходят. Фактическое значение `alembic current -v` в переписке
не предоставлялось, проверьте его перед новым upgrade.

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini heads
```

Ожидаемо до применения 5.3: `current = aisafe_v2_20261018`,
`heads = aisafe_v3_20261018`. Если не так — сначала выясните причину.
Затем:

```powershell
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check
python -m ruff check backend
python -m pytest backend/tests/test_safety_idempotency_unit.py -v

. .\scripts\postgres_test_db.ps1
python -m pytest backend/tests/test_safety_idempotency_pg.py -v -rs
python -m pytest backend/tests -v -rs
```

Тесты, использующие `pg_engine`, удаляют таблицы **только из выделенной
локальной БД `*_test`**. Проверьте `TEST_DATABASE_URL` до их запуска.
`SKIPPED` не подтверждает интеграцию с PostgreSQL.

## Проверки и риски

- Unit: формат/хэш ключей, отпечаток тела и регистрация таблицы в Metadata.
- PostgreSQL integration: повтор, конфликт, два независимых врача/пациента,
  отсутствие ключа, гонка идентичных/разных тел и откат при ошибке Outbox.
- Конкурентный тест выявляет нарушение единственности результата, но не
  является нагрузочным тестом и не доказывает корректность при любых отказах.
- Исторические записи 5.1/5.2 без HTTP-ключа остаются допустимы.
- Миграция создаёт новую таблицу; старые таблицы и схемы API не удаляются.
- `downgrade` запрещён, чтобы не уничтожить сведения о ключах.
- Применяйте миграцию **раньше** запуска новой версии backend.
- Не использовать платформу с реальными медицинскими данными
  или как систему экстренной помощи.
