# AIDoctor 6.3.3 — контроль готовности AV при ручном сканировании

## Назначение

Оператор подтвердил в своей среде (Windows 11 / Docker Desktop) обнаружение
EICAR локальным `clamd`: база в ответе демона датирована 2026-10-18 UTC.
Ранее проверенный smoke-test из 6.3.2 оставался **отдельной командой**:
при запуске `attachment_clamd_once` не было обязательного диагностического
контроля **для конкретного сканирования медицинского вложения**.

Теперь ручной CLI оборачивает `ClamdScanner` объектом `PreflightGatedScanner`.
Это проверка корректности эксплуатации и заявленной свежести баз, а
**не доверенная аттестация ClamAV и не снятие карантина**.

## Последовательность одной операции

1. Сервис 6.3.1 проверяет административную роль, пациента, актуальный
   `prechecked_quarantined`, SHA-256 и байты из карантина; пишет `scan_input`
   в PostgreSQL до передачи байтов сканеру.
2. Гейт отправляет 68 тестовых байт EICAR через тот же **клиент** clamd.
   Требует `infected_reported` и VERSION с датой базы не старше 7 дней.
   При отказе **медицинские байты в clamd не отправляются**.
3. Только после успешной проверки гейт передаёт байты медицинского файла
   через `INSTREAM`. Если ответ `infected_reported`, сообщение немедленно
   передаётся сервису 6.3.1: тот сохраняет аудит и терминальный `rejected`.
4. Если ответ `clean_reported`, гейт проверяет равенство VERSION
   с первоначальным ответом и свежесть даты базы.
5. Перед возвратом `clean_reported` повторно выполняются EICAR и контроль
   VERSION. При любом отказе либо смене версии — ошибка сканера.
6. Сервис 6.3.1 повторно читает исходный файл из карантина, сверяет
   SHA-256 и длину и атомарно сохраняет `attachment_av_scans` и аудит
   `av_scan`; если проверка провалилась — `error`, карантин сохраняется.

Гейт не сохраняет EICAR в БД или на диск и не регистрирует новый HTTP API.
Все старые интерфейсы сервисов сохранены; необёрнутый `ClamdScanner`
**остаётся протокольным клиентом**, его `clean_reported` нельзя трактовать
как результат новых эксплуатационных проверок.

## Права, конфликты и совместимость

- **Владение данными:** `medical_attachments` и
  `attachment_security_reviews` — PostgreSQL; исходные байты — хранилище.
  Антивирусные отчёты — отдельная таблица `attachment_av_scans`.
  Новый гейт не создаёт альтернативного источника истины и не меняет статусы.
- **Контракты:** существующие FastAPI endpoints, ORM-модели, таблицы,
  Alembic head (`aiextract_v4_20261018`), аудиторские события и
  `require_processing_clearance` неизменны.
- **Эволюция:** будущему CDR необходима самостоятельная изоляция и отдельный
  контракт санитизированных **производных** файлов, их SHA-256,
  происхождения, статусов и повторного AV после CDR. `clean_reported`
  не должен автоматически превращаться в `approved`.

## Риски

1. TCP localhost не удостоверяет подлинность демона: локальный процесс может
   подменить ответ и VERSION. Повторный EICAR подтверждает только наблюдаемое
   поведение ответчика и заявленную свежесть сигнатур.
2. Между проверками доступны окна смены состояния демона, а сигнатуры могут
   обновиться в середине операции. При смене VERSION чистый отчёт отвергается.
3. EICAR не является тестом полноты детектирования неизвестного вредоносного
   кода. `clean_reported` **не доказывает безопасность документа**.
4. Завершение процесса вне транзакции может оставить `scan_input` без
   `av_scan`: это диагностируемое событие, но не успешный вердикт.
5. AV не защищает будущие парсеры от уязвимостей форматов; нужен CDR,
   изолированное исполнение, лимиты и явный отдельный этап допуска.
6. Docker Desktop и Windows ACL требуют отдельной эксплуатационной оценки
   для реальных данных пациентов.

**Запрещено**: автоматический выпуск из карантина, OCR, LLM,
парсинг, внешняя передача файлов и имитация «проверенного AV».

## Проверка в PowerShell из корня проекта

```powershell
docker compose -f compose.yaml -f compose.av.yaml --profile av ps
$env:PYTHONPATH = (Resolve-Path .\backend).Path
python -m app.workers.clamd_preflight --check-eicar
Remove-Item Env:PYTHONPATH

python -m ruff check backend
python -m pytest backend/tests/test_attachment_av_policy_unit.py -v -rs
python -m pytest backend/tests/test_attachment_clamd_once_unit.py -v -rs
python -m pytest backend/tests/test_clamd_preflight_unit.py -v -rs
python -m pytest backend/tests/test_attachment_clamd_unit.py -v -rs
python -m alembic -c alembic.ini heads
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check
```

Для PostgreSQL-тестов используйте **только пустую выделенную локальную**
БД, имя которой оканчивается на `_test`. Общая фикстура удаляет таблицы.

```powershell
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_attachment_av_policy_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

Ручное сканирование вложений CLI `attachment_clamd_once` **по-прежнему
запрещено без явного** `ATTACHMENT_CLAMD_ENABLED=true` и `--once`.
Не включать его для реальных медицинских данных до эксплуатационного
аудита и оформления правовых оснований.

## Критерии готовности

1. `ruff check backend` — без замечаний.
2. Изолированные unit-тесты нового гейта и старые ClamAV-тесты зелёные.
3. Новые PostgreSQL-тесты проходят без неожиданных `SKIPPED`.
4. Полный `backend/tests` — зелёный, Alembic без расхождений.
5. EICAR в реальном контейнере обнаруживается, VERSION приемлемая;
   контейнер имеет итоговый статус `healthy`.
6. На отказе EICAR медицинские байты не передаются в AV, но отчёт
   `error` и аудит сохраняются; на `clean_reported` карантин остаётся.
