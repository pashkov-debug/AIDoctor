# Этап 5.8 — аудит чтений и политика хранения Safety

## Границы

Этап закрывает **технический прототип** Safety 5.1–5.8, но не сертификацию
медицинского приложения. Внешней доставки, автоматического SLA реагирования,
LLM-триажа и запуска фоновых процессов нет.

Новый журнал `safety_read_audit` фиксирует **успешные авторизованные GET**:

| Scope | Маршрут | Контекст |
|---|---|---|
| `alerts_list` | `GET /api/v1/patients/{patient_id}/safety-alerts` | `patient_id` |
| `route_read` | `GET /api/v1/patients/{patient_id}/safety-notification-route` | `patient_id` |
| `inbox_list` | `GET /api/v1/safety-inbox` | только актор |
| `followups_list` | `GET /api/v1/safety-followups` | только актор |

Каждая запись содержит только `id`, `created_at`, `actor_id`, необязательный
`patient_id`, фиксированный `scope`, `returned_count`. Ни тела запроса,
ни содержимого ответа, ни `reason_code`, ни диагнозов/контактов/токенов
в журнале нет. Даже чтение пустого результата (`200`, `[]`/`null`)
записывается с `returned_count = 0`.

Проверка прав остаётся в существующих зависимостях и SQL-запросах.
Новый журнал не предоставляет API чтения/изменения журнала.
Нарушения доступа с HTTP `401/403/404` не записываются в
`safety_read_audit`: для них впоследствии понадобится отдельно
защищённый security-log на уровне приложения или шлюза.

## Атомарность и устойчивость

- Сначала выполняется авторизация, затем выборка и сериализация,
  **затем COMMIT аудита, только после него отправляется HTTP-ответ**.
- Если запись или COMMIT аудита не удались, ответ с данными не выдаётся
  (fail-closed; обычно HTTP 500). Это может снижать доступность при
  отказе БД; для безопасности медицинской информации приоритет осознанный.
- Другие рабочие сервисы, создающие/подтверждающие события и управляющие
  Outbox, не меняются. Аудит чтений не отменяет журналы изменений.
- Чтения общего `Context`, вложений и других ресурсов в этом инкременте
  **не** аудитируются. Это отдельная задача сквозного security-аудита.
- Журнал не является криптографически неизменяемым: DBA с достаточными
  правами теоретически может его изменить. На production потребуются
  ограниченные SQL-роли, удалённый защищённый журнал и контроль целостности.

## Retention — решение для локального прототипа

**Автоматического удаления нет**, ни по давности, ни по изменению связи
DoctorPatient/статуса пациента. Таблицы событий Safety, Outbox и
Audit сохраняются; Alembic downgrade, уничтожающий журнал, запрещён.
В тестовой БД только pytest-фикстура удаляет тестовые таблицы.

До production требуется документально определить:
1. юридические основания и сроки хранения по юрисдикции;
2. процедуру удаления/анонимизации и законного сохранения audit trail;
3. роли доступа к аудиту, процедуру экспорта и запрет прямого удаления;
4. защиту данных at rest и шифрование резервных копий;
5. восстановление БД с проверкой журналов, мониторинг ошибок COMMIT;
6. журналирование отказов доступа на API gateway с редактированием PII.

Ни один фиксированный срок (например, 30/90/365 дней) **не принят**
без согласования правового режима. Автоматический purge не реализован,
чтобы не потерять юридически значимый аудит.

## Проверка на Windows 11

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini heads
# До upgrade: current = aisafe_v6_20261018, heads = aisafe_v7_20261018
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check
python -m ruff check backend
python -m pytest backend/tests/test_safety_read_audit_unit.py -v
. .\scripts\postgres_test_db.ps1
python -m pytest backend/tests/test_safety_read_audit_pg.py -v -rs
python -m pytest backend/tests -v -rs
```

В последнем полном pytest не должно быть новых ошибок; интеграционные
тесты `test_safety_read_audit_pg.py` обязаны выполняться без `SKIPPED`.
Тестовая БД должна быть отдельной локальной `*_test` БД:
существующая фикстура удаляет и пересоздаёт в ней все таблицы.

## Контроль конфликтов

- **Владение:** PostgreSQL владеет данными аудита, бизнес-сервис —
  правами доступа, API — обязательным вызовом аудита перед ответом.
- **Контракт:** пути, схемы JSON и HTTP-коды успешных чтений сохранены;
  дополнительная операция записи может повлиять на задержку GET.
- **Эволюция:** новые GET должны явно подключать запись чтений и
  тест на отказ аудита. Не расширять `scope` без новой миграции CHECK.
