# AIDoctor — план фронтенда UI-1–UI-5

Версия: 2026-10-20. Рабочий источник: архив проекта `AIDoctor-master (5).zip`,
модифицированные PHP/Bridge пути не входят в будущую архитектуру.

## Цель

Получить функциональные кабинеты врача, пациента и администратора на
существующем FastAPI API. До отдельного подтверждения безопасности
использовать только синтетические данные. Не добавлять OCR, LLM,
автоматические назначения, внешние сервисы и новое API без оснований.

## Предварительные условия (UI-0)

1. Отработать `audit/check_rollback.py` и разобраться с расхождением
   `aictx_v3_20261017_context_snapshots.py`. **Не заменять миграцию наугад.**
2. Удалить только перечисленные в README временные модули после проверки
   их содержимого. `.env` с секретами, БД, Docker volume и каталоги вложений
   не удалять.
3. Восстановить `.env.example` для действующего backend; `.env` не перезаписывать.
4. Подтвердить `ruff`, `alembic check`, тесты безопасности и полный pytest
   на отдельной `aidoctor_test`.
5. Зафиксировать текущие API-контракты через локальный `/openapi.json`.

## Архитектурные границы

- **UI:** статические HTML/CSS/JavaScript, по тому же origin, что FastAPI.
  На этом этапе не вводить React/Vite и сборочную инфраструктуру.
- **API:** авторизация, проверки ролей и доступа к конкретному пациенту —
  только на backend. UI не создаёт собственный источник истины.
- **Сессия:** действующий Bearer API; на UI-1 токен только в оперативной
  памяти вкладки. Не записывать токены в URL, localStorage, логи и HTML.
  После обновления страницы потребуется повторный вход.
- **База:** PostgreSQL 16 — единственный источник бизнес-данных;
  UI напрямую к БД не обращается.
- **Вложения:** только существующие endpoints, карантин и запрет
  передачи непроверенных медицинских данных в Context Builder сохраняются.
- **Интеграция с ChatGPT/MCP:** выключена. Новая ВМ и её домен ещё не выбраны.

## UI-1 — авторизация и каркас

Действующие маршруты (относительно `/api/v1`):
- `POST /auth/login` — вход, возвращает Bearer-токен;
- `GET /auth/me` — идентификатор, username, role;
- `POST /auth/logout` — завершение пользовательских сессий.

Проверить роли `doctor`, `patient`, `admin`; некорректный токен → 401,
недопустимая роль/объект → backend 403/404. UI не должно отображать
клинические данные до успешного `GET /auth/me`. Обработка истечения
токена и ошибок сети должна быть явной.

**Артефакты:** полные файлы UI + минимальное подключение к FastAPI,
автотесты оболочки/прав и smoke-test входа по ролям.

**Критерии готовности:** три роли попадают в нужные кабинеты;
после logout закрытые разделы недоступны; анонимный запрос не открывает
страницы с медицинскими данными; нет токенов в постоянном хранилище.

## UI-2 — кабинет врача

Действующие API:
- `GET /patients` с поиском и `GET /patients/{patient_id}`;
- `POST /patients` (для врача);
- визиты, опросники, события истории, контекст, Safety Alerts —
  проверить точные схемы в OpenAPI перед реализацией каждого экрана.

Минимальный поток: доступные пациенты → карточка → контекст →
события истории → открытые Safety Alerts. Не придумывать API
лекарственных назначений или рабочего LLM.

**Критерии готовности:** врач видит только разрешённых пациентов;
доступ к чужому пациенту блокируется backend; изменения контекста
не приводят к утечке неразрешённых вложений.

## UI-3 — кабинет пациента

Доступ к собственным данным, разрешённым endpoints истории и вложений.
Операции загрузки сохраняют оригиналы в `quarantined`. Не рисовать
подтверждённые назначения и AI-результаты, которых нет в backend.
Отдельные негативные проверки чужих patient_id.

## UI-4 — кабинет администратора

Использовать только существующие маршруты:
- `POST /access/link`;
- `POST /access/patient-account`;
- действующие административные Safety Follow-up и доступные журналы
  (после сверки OpenAPI).
Пока нет эндпоинта, не подменять его неработающей кнопкой.

Проверить 403 для врача/пациента при доступе к админ-действиям.

## UI-5 — стабилизация и подготовка ВМ

Вынести конфигурацию в переменные окружения, предусмотреть reverse proxy,
TLS, закрытую PostgreSQL и хранилище, регулярный бэкап и наблюдаемость.
До настоящей ВМ не задавать домен и IP. Не переносить рабочие медицинские
данные на внешний сервер без отдельного аудита и юридического основания.

## Конфликты и решения

1. **Владение данными:** только backend/БД; UI не хранит клинические факты
   и не подменяет авторизационные проверки.
2. **Контракты:** UI следует текущему OpenAPI; новые API — только
   отдельными инкрементами с серверными тестами.
3. **Эволюция:** новый frontend можно позже заменить на SPA без изменения
   бизнес-сервисов; будущий LLM Gateway не включается в UI-1.

## Команды контрольного прогона

```powershell
docker compose up -d postgres
python -m ruff check backend
python -m alembic -c alembic.ini heads
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check
python -m pytest backend/tests/test_stage6_final_unit.py -v -rs

$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

**Осторожно:** PostgreSQL-фикстуры могут удалять и пересоздавать таблицы.
Использовать исключительно выделенную тестовую БД.
