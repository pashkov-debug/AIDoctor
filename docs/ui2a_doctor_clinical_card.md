# UI-2A — клиническая карточка врача и постоянная синтетическая история

## Границы инкремента

UI-2A использует существующие `patients`, `encounters`, `history_events`,
`medical_observations` и Context Builder. Новых таблиц, миграций и зависимостей нет.

В кабинете врача (`/app`) можно открыть доступного пациента, просмотреть
визиты, события истории и структурный Digest; новый визит сохраняется через
`POST /api/v1/patients/{patient_id}/encounters` со статусом `draft`.
Создание визита **не назначает лечение** и не публикует запись пациенту.
Исторические события здесь только читаются: коррекции, аудит правок и
врачебное подтверждение фактов — последующий инкремент.

### Изменение доступа (преднамеренная защита)

Чтение внутренних визитов (`GET .../encounters`, `GET /encounters/{id}`)
и событий (`GET .../history-events`) ограничено врачом с подтверждённой
связью с пациентом (или администратором с предусмотренными правами).
Обычному пациенту возвращается `403`, постороннему врачу — `404`.
До появления явной политики публикации нельзя показывать пациенту
внутренние записи через старый API. Личная карточка UI-1B не меняется.

## Постоянная синтетическая история в основной локальной БД

`aidoctor` — БД для **ручных и демонстрационных** сценариев.
`aidoctor_test` — одноразовая БД для автоматических PostgreSQL-тестов.
Настоящая production-БД должна создаваться отдельно и с чистой схемой.
Не переносить в неё локальную базу с учебной историей.

Команды PowerShell из корня AIDoctor (активная `.venv`):

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini upgrade head
$env:PYTHONPATH = "backend"
python -m backend.scripts.seed_ui2a_synthetic
python -m backend.scripts.seed_ui2a_synthetic --apply
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

Первая команда seed — **только проверка** привязки карточки.
Команда с `--apply` добавляет четыре визита, шесть событий, три
учебных субъективных наблюдения (35 дней истории). Повторный запуск
не создаёт дубликатов. Уже существующие записи не удаляются и не
перезаписываются.

Seed разрешён **только** при `APP_ENV=local` и фактической локальной БД
с точным именем `aidoctor`. Он ожидает:
- `doctor_ui1` — активная учётная запись врача, имеющего доступ;
- `patient_ui1` — учётная запись пациента, уже привязанная к активной
  карточке с `demographics.synthetic = true`.

При ошибке нет доступа/неверная БД/нет метки synthetic запись не
выполняется. Никаких реальных ФИО, результатов реальных анализов,
запросов AI или фармакологических назначений seed не создаёт.
«Качество сна» — вымышленная учебная самооценка от 0 до 10, **не**
стандартизированный медицинский тест. Визиты seed имеют статус
`draft`; это не подтверждённая клиническая документация.

## Команды тестов — только на aidoctor_test

```powershell
python -m ruff check backend
python -m ruff format --check backend
node --check backend/app/web/assets/app.js

python -m pytest backend/tests/test_ui2a_unit.py -v

$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_ui2a_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL

python -m alembic -c alembic.ini check
```

`pg_engine` в `backend/tests/conftest.py` делает `drop_all/create_all`.
**Никогда не задавайте** `TEST_DATABASE_URL`, ведущий в `aidoctor`.
В текущей фикстуре дополнительно проверяются локальный хост и суффикс
`_test`. Миграция `upgrade head` работает с текущей основной БД;
в UI-2A новых ревизий нет.

## Критерии готовности

1. UI-1A/1B/1C работают без регрессии.
2. Врач открывает только доступную ему карточку.
3. Четыре синтетических визита и шесть событий видны в интерфейсе.
4. Digest показывает состав записей, исключения и флаг усечения.
5. Новый визит сохраняется в PostgreSQL как `draft`.
6. Обычный пациент не получает доступ к внутренним визитам и истории.
7. Повторная команда `--apply` сообщает нулевые добавления.

## Интеграция / риски

- **Владение:** PostgreSQL — источник истины, UI лишь отображает существующие факты.
- **Контракты:** старые формы визитов и истории сохранены; чтение внутренних
  медицинских данных пациентом *намеренно закрыто*.
- **Развитие:** публикация пациенту, подтверждение врачом, исправления и
  назначения требуют отдельных согласованных backend-контрактов.
- **Тестирование:** UI-2A не отправляет медицинские сведения в LLM и не
  передаёт непроверенные вложения в Context Builder.

Ограничения: без автоматического медицинского анализа, назначения
препаратов, клинической интерпретации, проверки РКИ или публикации
в кабинете пациента. Контур безопасности файлов и Safety Alerts
не изменяется.
