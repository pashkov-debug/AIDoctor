# AIDoctor — 6.6 FINAL: стабилизация технического контура вложений

Дата подготовки: 20 октября 2026 года. Источник кода: локальный архив
`AIDoctor-master (3).zip`, он приоритетнее публичного `master`.

## Область работ

Этап закрывает **техническую ветку 6**, а не вводит медицинский production-допуск.

- Внесено одно локальное исправление:
  `backend/app/services/attachment_av_scan.py` теперь фиксирует `error`
  и `av_scan` при неожиданном исключении, таймауте или некорректном объекте
  ответа AV-адаптера. Данные исключений и байты медицинского вложения
  не сохраняются в аудите.
- Добавлены регрессионные проверки неуспешного AV, аудита, отказа CDR,
  целостности файла, запрета клинической обработки и исключения вложений
  из Context Builder.
- Работающие API, схема PostgreSQL, миграции, Docker-образы, обработчики
  ручных выдержек 6.1 и синтетические CDR-сервисы не изменены.

### Важное разграничение

Технический поток: загрузка в карантин → предпроверка →
ручная передача локальному AV → техническая запись о проверке.
Отдельно доступен **только синтетический** CDR PDF/DOCX →
повторный AV результата. Он не запускается для файлов пациента.

`clean_reported` НЕ означает подтверждённый безопасный документ.
Ни AV, ни CDR в проекте сейчас не дают `processing_allowed=True`.
Результаты CDR не сохраняются в доверенное клиническое хранилище,
не включаются в Context Builder, не используются для OCR/LLM.

## Конфликтный анализ

| Вид конфликта | Инвариант / решение |
|---|---|
| Владение данными | PostgreSQL — статус карантина, AV-отчёты и аудит; файловое хранилище — оригинал; квитанции синтетического CDR не являются постоянной записью |
| Контракты | HTTP API, схема, имена миграций, значения статусов и существующие форматы сохранены; ошибки AV-адаптера нормализуются в уже существующее значение `error` |
| Эволюция | Реальный допуск к обработке потребуется вынести в отдельный проверяемый переход с авторизацией, неизменяемым результатом CDR, provenance, аудитом и пересмотром угроз; существующий `require_processing_clearance` остаётся закрытым |

## Новые проверки

`backend/tests/test_stage6_final_unit.py`: неизменность клинического
гейта, SHA-256 и защита от подмены файла; недоверенный результат CDR;
фактическое прохождение ошибок стороннего AV до функции записи в БД
(без использования БД).

`backend/tests/test_stage6_final_pg.py`: реальные транзакции PostgreSQL
на `*_test`, отказ при аварии/таймауте/некорректном результате AV;
по одной записи `AttachmentAVScan` и `av_scan`; карантин не снимается,
после ошибки CDR-кандидат недоступен; клинический Context Builder пуст
даже после технического `clean_reported`.

**Тестовые AV-ответы синтетические:** они не подтверждают наличие
сканера или свежесть сигнатур. Реальную связку проверять отдельно
включённым ClamAV.

## Windows / PowerShell — критерии закрытия

Из корня проекта, после распаковки ZIP:

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini heads
python -m alembic -c alembic.ini current -v
python -m alembic -c alembic.ini check
python -m ruff check backend
python -m pytest backend/tests/test_stage6_final_unit.py -v -rs
```

Ожидаемый Alembic head: `aiextract_v5_20261019`.
Новых миграций на этапе 6.6 нет; `upgrade head` требуется только
если рабочая БД фактически отстала.

Для интеграции использовать **только локальную отдельную БД**
с суффиксом `_test`. Фикстуры удаляют и создают таблицы:

```powershell
$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_stage6_final_pg.py -v -rs
python -m pytest backend/tests -v -rs
Remove-Item Env:TEST_DATABASE_URL
```

`SKIPPED` для PostgreSQL-тестов без БД не засчитывается.
Для Docker/ClamAV при необходимости:

```powershell
docker compose -f compose.yaml -f compose.av.yaml --profile av ps
$env:PYTHONPATH = (Resolve-Path .\backend).Path
python -m app.workers.clamd_preflight --check-eicar
Remove-Item Env:PYTHONPATH
```

Дополнительная проверка реальных *синтетических* CDR-контейнеров
PDF и DOCX — согласно `docs/cdr_pdf_synthetic_v10.md`,
`docs/cdr_docx_synthetic_v11.md` и
`docs/cdr_output_repeat_av_v12.md`. Ни одну из команд CDR
не направлять на медицинские файлы.

## Подтверждено / не подтверждено

В окружении подготовки: 209 изолированных unit-тестов из выборки
этапов хранения/AV/CDR и 6.6 прошли. Синтаксис новых Python-файлов
проверен. Не проверены: Ruff, Windows/Python 3.12, PostgreSQL-интеграция,
полный pytest и реальный Docker smoke-test в этом запуске.

Завершение 6.6 подтверждается только после успешной локальной
проверки Ruff, Alembic, нового PostgreSQL-теста без пропусков, полного
pytest и smoke-тестов двух Docker CDR-образов/ClamAV (если контейнеры
не изменились, допустим повторный протокол уже проведённых проверок).

## Остаточные риски и границы

- `clamd` на loopback не имеет криптографической аттестации.
- Docker Desktop не эквивалентен изоляции уровня gVisor/microVM.
- Windows ACL, подмена файлов процессом с правами к хранилищу,
  управление версиями и обновления сигнатур требуют отдельной
  эксплуатационной политики.
- Хранение PHI, шифрование, retention, согласия пациентов и
  соответствие законодательству не проверены.
- Нет клинической валидации, OCR/LLM, медицинских рекомендаций,
  автоматически допущенных вложений и производственного CDR-контура.

**После зелёных проверок этап 6 считается технически закрытым.**
Следующая предметная работа — UI врача/пациента (этап 3).
Возвращаться к обработке реальных медицинских файлов — отдельная
функциональность и отдельное решение о безопасности.
