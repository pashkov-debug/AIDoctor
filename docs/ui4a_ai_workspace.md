# UI-4A — рабочая область врача, подготовка запросов без LLM

## Границы этапа
Реализован локальный интерфейс с тремя областями: вопрос врача,
вложения и ответ AI. Последняя область **не содержит AI-ответа** и
показывает, что провайдер отключён. Ни ответы модели, ни назначения,
ни медицинские рекомендации системой не создаются.

Сохранение запроса выполняется только авторизованным врачом с действующей
связью с пациентом. В одной транзакции PostgreSQL фиксируются:
- `context_snapshots` — отдельный неизменяемый snapshot существующего Context Builder;
- `ai_requests` — вопрос, ключ идемпотентности, ссылки на snapshot, его SHA-256,
  копия `doctor_context.v1`, список метаданных выбранных вложений;
- `ai_request_audit` — факт подготовки запроса с ID автора.

РКИ — российские клинические рекомендации, утверждённые Минздравом РФ.
`doctor_context.rki` содержит только настройки врача, которые сами по себе
не подтверждают актуальность или применимость конкретной рекомендации.

Все файлы остаются в контуре действующего карантина. Выбор файла сохраняет
только `id`, имя, SHA-256 и статус `excluded_unverified`; содержимое не
попадает в snapshot и не передаётся AI. Не создаётся обходной канал чтения
документа. Проверка отсутствия вредоносного содержимого **не означает**
автоматического разрешения передавать медицинский текст модели.

## Важные ограничения

- Снимок `Context Builder 1.0` сохраняет контракт текущей версии,
  включая статус исходных клинических записей. Это *подготовленная* версия,
  а не медицински подтверждённый AI-контекст для автоматической передачи.
- При усечении источников или неверной контрольной сумме snapshot не сохраняется.
- Статус запроса — строго `prepared`, версия — `1`, ответ AI отсутствует.
- Список запросов доступен только врачу-автору. Ни пациент, ни администратор
  не получают доступ через новый API.
- Повтор с тем же `(doctor_id, request_key)` и тем же содержимым
  возвращает исходный запрос; несовместимый повтор получает HTTP 409.
- Никакой кнопки утверждения ответа нет до появления валидируемого
  структурированного черновика. UI-4B будет утверждать только отдельные
  структурированные элементы с журналом изменений врача.

## Конфликты

1. **Владение:** клинические факты принадлежат профильным модулям, запрос
   хранит только immutable-ссылку и копию разрешённого контекста;
   нет права превращать AI-текст в факт.
2. **Контракты:** новые маршруты `ai-workspace` и `ai-requests` не меняют
   существующие маршруты `context`, `attachments`, `clinical-orders`.
3. **Эволюция:** дальнейшие AI-провайдеры, валидируемые ответы и врачебные
   решения связываются с ID запроса, но не меняют его исходную версию.

## Установка (PowerShell)

Из корня AIDoctor после распаковки ZIP:

```powershell
docker compose up -d postgres
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini check

python -m ruff check backend --fix
python -m ruff format backend
python -m ruff check backend
python -m ruff format --check backend
node --check backend/app/web/assets/app.js

$env:PYTHONPATH = "backend"
python -m pytest backend/tests/test_ui4a_unit.py -v

$env:TEST_DATABASE_URL = "postgresql+psycopg://aidoctor:aidoctor_dev@127.0.0.1:5432/aidoctor_test"
python -m pytest backend/tests/test_ui4a_pg.py -v -rs
python -m pytest backend/tests -q -rs
Remove-Item Env:TEST_DATABASE_URL -ErrorAction SilentlyContinue

python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

Для ручной проверки открыть `http://127.0.0.1:8000/app` под `doctor_ui1`,
выбрать «Запросы AI», пациента и сохранить вопрос. Обновить страницу,
войти повторно: история сохранённых запросов должна остаться.
Утверждённых назначений и ответов AI это действие не создаёт.
Для проверки изоляции повторить вход под `patient_ui1` и `admin_ui1`:
доступ к новым API должен быть закрыт.

**ВНИМАНИЕ:** `backend/tests/conftest.py` использует `drop_all/create_all`.
Все интеграционные тесты — только с `TEST_DATABASE_URL`, указывающим на
выделенную локальную базу `aidoctor_test`. Не запускать их на `aidoctor`.

## Критерии готовности

1. Врач видит три панели и может выбрать одного из своих пациентов.
2. Вложения загружаются в карантин, сохраняются только ссылками/метаданными.
3. Запрос и snapshot сохраняются атомарно; UI показывает статус `prepared`.
4. Настройки врача фиксируются с версией и режимом РКИ.
5. Пациенту, чужому врачу и администратору доступ запрещён.
6. Повторное сохранение с тем же ключом не создаёт новых запросов.
7. Результаты Ruff, Alembic и PostgreSQL-регрессии подтверждены локально.
