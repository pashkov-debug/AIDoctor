# AIDoctor 6.4.1b — недоверенный результат будущего CDR

## Назначение

Добавлена **исключительно локальная** функция
`app.services.cdr_output_boundary.capture_untrusted_cdr_output`.
Она принимает уже созданный `UnexecutedCDRPlan` из 6.4.1a и бинарный
поток **потенциального** выхода будущего CDR-worker.

**Сейчас CDR-worker отсутствует.** Данный этап не запускает Docker,
не проверяет фактическое выполнение CDR и не подтверждает очистку файла.

## Граница и инварианты

1. Источник — `UnexecutedCDRPlan` с неизменным SHA-256, размером не более
   20 МиБ и разрешённым исходным PDF/DOCX. Хеш повторно сверяется.
2. Выход — **только PDF**, не более 20 МиБ. Поток читается ограниченными
   порциями, не логируется, не передаётся во внешние сервисы.
3. Проверяются лишь магические байты `%PDF-` и наличие `%%EOF` в последнем
   1 КиБ; эти эвристики **не выявляют** вредоносные PDF-объекты.
4. Полностью одинаковые исходные/выходные байты отклоняются как возможный
   passthrough; различие байтов **не доказывает** CDR.
5. Результат `UntrustedCDROutput` неизменяемый, его `content` не попадает
   в `repr`, а `sanitized`, `trusted`, `processing_allowed` всегда `False`.
6. Нет БД-записи, статуса «обработано», HTTP-маршрута, изменения
   `extraction_status`, файлового хранилища, клинического Context Builder.

Внешний будущий worker должен **сам** обеспечивать подлинность образа,
изоляцию, timeout, ограничения stdout/stderr, аудит обработки, создание
и безопасное хранение нового артефакта, проверку PDF полноценным
валидатором, AV-сканирование выхода и последующее независимое решение
о клиническом допуске. Эта функция не заменяет ни один из перечисленных шагов.

## Архитектурные конфликты

- **Владение данными:** PostgreSQL и прежнее защищённое файловое хранилище
  не меняются. Новые байты только в памяти; источник истины по статусам
  остаётся в существующих таблицах.
- **Контракты:** 6.4.0 и 6.4.1a без изменений. Новый тип предназначен
  для внутренней границы, не для API и не для сериализации пациентских данных.
- **Эволюция:** смена CDR-движка не должна изменять правило «нет допуска
  без полного доказуемого конвейера». Отдельный входной/выходной тип
  предотвращает смешивание оригиналов и потенциально преобразованных байтов.

## Остаток этапа 6 — ориентир, а не гарантия сроков

После 6.4.1b предлагаем **три контрольных блока**:

1. **6.4.2:** согласованный реальный CDR-движок, воспроизводимый Docker-образ
   и испытания исключительно на синтетических PDF/DOCX.
2. **6.5:** provenance, повторная AV-проверка выхода, карантин нового
   артефакта, аудит и отдельное решение о безопасном использовании данных.
3. **6.6:** закрывающие негативные, конкурентные и PostgreSQL-проверки,
   документирование границ безопасности.

Это не означает, что AI/OCR, сохранение машинного текста или клиническое
использование файлов автоматически включатся: для них нужны отдельное
согласование требований и проверки. Пока нельзя обещать, что 6.4.2
возможно завершить без дополнительных промежуточных задач.

## Границы

На этапе 6.4.1b **нет** реального CDR, внешнего вызова, сохранения
«очищенного» файла, OCR, LLM, медицинских рекомендаций или допуска
вложений в Context Builder. Наличие PDF-подписи и нового SHA-256 ничего
не говорит о безопасности файла. Таймаут чтения потока должен вводить
будущий исполнитель, не этот синхронный валидатор.
