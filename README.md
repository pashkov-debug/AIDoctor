## 1. Назначение и область применения

**AIDoctor** — кроссплатформенная система поддержки врачебных решений с персональной историей пациента, самоотчётами, результатами обследований, перепиской и внешним LLM-агентом.

**Продукт не ограничивается тревогой и депрессией.** Структура данных, вложения, анализ и интерфейс должны работать с произвольными медицинскими направлениями: лабораторные показатели, инструментальные исследования, заключения врачей, история лечения, симптомы, аудиозаметки и другие медицинские сведения. При этом **конкурсный демонстрационный и проверочный набор** обязательно охватывает тревожно-депрессивную симптоматику и все специальные условия чемпионата.

Ключевой процесс:

```text
Пациент / врач
    │ история, жалобы, результаты тестов, PDF/DOC/DOCX/аудио
    ▼
AIDoctor API + защищённое хранилище
    │ проверка прав, версий, целостности, антивирус/лимиты, PII-контроль
    ├──────────► независимое выявление критических признаков и алерт врачу
    ▼
History Digest + Context Snapshot + подготовленные вложения
    ▼
LLM Gateway → внешний LLM-агент (выбираемый провайдер)
    │  медицинские гипотезы, выбор уточняющих тестов,
    │  интерпретация, варианты терапии, риски, маршрутизация,
    │  ссылки на источники
    ▼
Валидация формата + сохранение результата + интерфейс врача
    ├── Утвердить → утверждённый план
    ├── Скорректировать → новая версия врача
    └── На доработку + комментарий → повторный запрос LLM
                                  → новая версия на утверждение
```

Врач окончательно решает, что применять. LLM не имеет прямых прав назначать, отменять, изменять лечение, отправлять направление или редактировать подтверждённый план.

**Важно:** даже самый сильный LLM не обеспечивает математической или клинической гарантии корректности медицинских ответов. Клинические знания, подбор препаратов и дозировок находятся **вне backend**, однако независимая обработка критических сигналов, контроль доступа, происхождение информации и подтверждение врачом обязательны.

## 2. Конкурсный кейс и продуктовые границы

### 2.1. Обязательные восемь функций

1. Стандартизированные методы оценки пациента (опросники/шкалы).
2. Справка и рекомендации по возможным вариантам терапии — формирует внешний LLM.
3. Учёт индивидуальных рисков и нежелательных явлений.
4. Динамика состояния пациента.
5. Интерфейс пациента для самоотчёта и самостоятельного просмотра динамики.
6. Каналы коммуникации врача и пациента для сопровождения.
7. Учёт и оценка приверженности лечению.
8. Выявление поводов для обращения к психиатру и маршрутизация **«обязательно»/«желательно»** — предложения LLM подтверждает врач; критические сигналы обрабатываются независимо.

### 2.2. Дополнительные обязательные условия чемпионата

- Минимум две раздельные роли: **врач** и **пациент**, с проверкой прав на сервере.
- У пациента есть ведущий врач; самоотчёты поступают в его карточку **без ручной передачи третьими лицами**.
- Любое клиническое действие — только после явного подтверждения врача.
- Синтетические клинические сценарии с препаратом **«Авиандр»**, включая профиль пациента, терапевтические предложения и маршрутизацию.
- Критический алерт: независимое определение утверждённых признаков, отправка врачу, подтверждение получения и заданное действие/эскалация.
- Визуально выделенные предупреждения и различимые уровни направления **«обязательно»/«желательно»**.
- Лекарственные предложения только с учётом регистрации в РФ, действующих показаний, противопоказаний и дозировок; решение вне инструкции — исключительно врач. **Источник медицинского предложения — LLM; соответствие источникам подтверждается клиническим review, а не объявляется гарантированным от наличия LLM.**
- Действующие КР Минздрава РФ, инструкции из ГРЛС, валидированные русскоязычные шкалы с соблюдением лицензий; международные источники помечаются отдельно.
- Конфиденциальность и применимые требования российского законодательства; конкурсное демо — только на синтетических/надлежаще обезличенных данных.
- Апробация на сценариях и измеримые технические показатели.

### 2.3. Новые требования продукта сверх кейса

- **Универсальный медицинский профиль**, а не специфическая БД тревоги/депрессии.
- **Приём PDF, DOC, DOCX, аудиофайлов** в качестве результатов обследования, заключений или записей.
- Сохранение исходного файла и извлечённого/транскрибированного представления с указанием источника.
- Возможность передать содержимое и, если поддерживается провайдером, оригинальные вложения **внешнему LLM-агенту на выбранной платформе**.
- Замена LLM через адаптер без миграции пациентской истории.
- Итеративное согласование: **утвердить / скорректировать / отправить на доработку с комментарием**.
- Мультимодальная история как нормальная часть пациента, а не разовый чат.

### 2.4. Что не является реализованной возможностью по одному этому README

README описывает **целевой контракт**, а не гарантирует, что Flutter, Android, все API, шифрование, загрузка файлов, агент и оповещения уже работают. Для приёмки нужны результаты запуска и тестов. Не заявляется медицинская или регуляторная готовность для реальных пациентов.

## 3. Архитектура

**Рекомендовано:** серверный источник истины, защищённый клиентский кэш для offline-просмотра; stateless по медицинской логике внешний AI Gateway, но сервер приложения **хранит** историю и метаданные вложений.

Это сознательное изменение ТЗ v1.1 и старого README: прежняя схема «Flutter владеет пациентской БД; Gateway ничего не хранит» несовместима без дополнительного механизма синхронизации с обязательной связью врача и пациента и появлением самоотчётов на устройстве врача.

```text
Flutter (Windows / Android; iOS по мере готовности)
    ├── Врач: пациенты, история, документы, анализ, подтверждения, алерты
    └── Пациент: самоотчёты, файлы, динамика, переписка
                     │ HTTPS + токен пользователя
                     ▼
FastAPI Application
    ├── Auth / RBAC / clinician-patient link
    ├── Patients / Encounters / Observations / Questionnaires
    ├── Attachments (upload/download, metadata, retention)
    ├── Messages / Adherence / Alerts / Review
    ├── History Store → Digest → Context Snapshot
    ├── Media processing (PDF/DOC/DOCX/audio) → extracted evidence
    ├── Safety: rule-based alerting + technical guards
    ├── Audit / idempotency / outbox
    └── AI Gateway → LLM Provider Adapter → внешний LLM
                     │
              валидированный JSON
                     ▼
             AgentRun + Review history
```

**Источник истины:** серверные записи и файлы; локальный мобильный кэш только производный. При конфликтах offline-изменения получают отдельную версию, сервер не перезаписывает подтверждённые записи «последней записью победителя».

**Хранилища:**
- Для разработки допустим SQLite с миграциями и проверенными ограничениями доступа.
- Для многопользовательского развёртывания предусмотрена миграция на PostgreSQL.
- Вложения — файловое/объектное хранилище с приватными ключами объектов, проверкой прав доступа при выдаче.
- Большие медиа не помещаются в JSON-поля истории и логи.

**Safety:** LLM определяет медицинское содержание рекомендаций; отдельно работают только согласованные детерминированные правила экстренных сигналов, контроль обязательных полей, техническая валидация и запрет несанкционированного исполнения.

## 4. Медицинская логика и ответственность

| Операция | Ответственный |
|---|---|
| Хранить симптомы, заключения, документы, шкалы и историю версий | Backend |
| Подсчитывать значения стандартизированных шкал по опубликованной спецификации | Детерминированный код (без медицинской интерпретации) |
| Выбирать нужные уточняющие тесты и вопросы | Внешний LLM; врач утверждает назначения и план обследования |
| Интерпретировать анализы, симптомы, записи и динамику | Внешний LLM |
| Формировать клинические гипотезы, лекарства, дозировки, риски, противопоказания и маршрутизацию | Внешний LLM; врач принимает решение |
| Проверять структуру ответа, права, наличие источников, версию контекста | Backend |
| Поднимать экстренный алерт по утверждённым красным флагам | Независимый safety-модуль backend |
| Утверждать, менять или возвращать рекомендации с комментарием | Врач |
| Оценивать правильность медицинских выводов для кейса | Клинический эксперт / врач при апробации |

**Запрещено:** выдавать неподтверждённый вывод LLM за назначение; автоматически применять скорректированный агентом план; объявлять ссылку «проверенной» лишь потому, что её предоставил LLM. При отсутствии медицинских источников агент должен указывать недостаток данных/доказательств; UI показывает статус проверки.

**Рекомендуемый контракт агента:** `OK | NEEDS_DATA | ABSTAIN | URGENT_ESCALATION | MODEL_REFUSAL | TECHNICAL_ERROR`; поля включают `summary`, `hypotheses`, `requested_assessments`, `recommended_next_steps`, `treatment_options`, `risks`, `routing`, `follow_up`, `evidence`, `missing_data`. Структура согласуется с выбранным агентом до подключения реального API.

## 5. Документы, анализы и аудио

### 5.1. Поддерживаемые типы и обработка

| Вход | Базовая подготовка | Передача агенту |
|---|---|---|
| PDF (`application/pdf`) | Парсинг текста/страниц; для сканов — отдельный OCR, если нужен | Извлечённый текст + страницы/цитаты; оригинальный PDF только если API провайдера поддерживает |
| DOCX | Чтение параграфов/таблиц через поддерживаемую библиотеку | Извлечённый текст, структура и метаданные; оригинал при поддержке провайдера |
| DOC (старый Word) | Конвертация в изолированном процессе поддерживаемым конвертером; при отсутствии конвертера — явный статус `UNSUPPORTED_CONVERSION` | После успешной конвертации |
| Аудио (список форматов определяется адаптером: например WAV/MP3/M4A) | Транскрипция с пометкой модели, языка и ошибок распознавания | Текст с временными метками или оригинальное аудио, если API допускает |
| Ручной ввод / числовой анализ | Нормализация даты, единицы, источника и явное сохранение значения | Структурированные наблюдения |

**Передача «на эту платформу» не означает автоматического доступа backend к этой переписке ChatGPT.** Для программной отправки вложений нужен **официальный API выбранного провайдера** или отдельно настроенный внешний агент с HTTP/MCP-контрактом. Возможность передать *непосредственно* файл, а не его содержимое, зависит от конкретного API/модели. ChatGPT UI и OpenAI API не следует считать одним и тем же каналом.

### 5.2. Пайплайн файла

1. Клиент отправляет файл через авторизованный API; связь с `patient_id` и, при необходимости, `encounter_id`.
2. Backend ограничивает размер, длительность аудио, количество страниц и общий объём, проверяет MIME **по содержимому**, расширение, вредоносный файл и формат; не доверяет имени файла.
3. Сохраняет оригинал в защищённом хранилище, SHA-256, автора, время, тип, статус обработки и версию.
4. Извлекает текст / конвертирует DOC / транскрибирует аудио, не выполняя вложенные макросы и программы.
5. Создаёт `DocumentExtraction` с привязкой фрагментов к страницам/таймкодам, уверенностью и ошибками извлечения.
6. Позволяет врачу просмотреть, при необходимости исправить **отдельной версией** извлечённый текст, особенно ошибки в дозах/единицах.
7. Context Builder выбирает необходимые фрагменты и `source_refs`, формирует immutable snapshot, выполняет PII-проверку и передаёт агенту.
8. Результат LLM хранит ссылки на конкретные документы/версии/фрагменты. Исходные файлы остаются доступными пользователям с разрешённым доступом.
9. Удаление/сроки хранения регулируются политикой; удаление оригинала не должно оставлять действующей ссылку или несогласованный кэш у провайдера.

**Обязательные edge cases:** зашифрованный PDF; скан без текстового слоя; пустая транскрипция; аудио с шумом; DOC с некорректной кодировкой; огромный документ; дубликаты; некорректные единицы; несколько пациентов в одном документе; таймаут извлечения; частично завершённая загрузка; несовместимость API с файловым типом. Невозможно извлечь/проверить → **не выдумывать содержимое**, вернуть понятный статус и запросить ручную проверку.

### 5.3. Необязательные детали для выбора позднее

Провайдер LLM, лимиты вложений, нужные аудиокодеки, OCR и STT, длительность хранения, формат передачи оригинала или extraction-only — **параметры адаптера**, а не клинического ядра.

## 6. Контракты, данные и версионирование

**Минимальные сущности:**
`User`, `DoctorPatientLink`, `Patient`, `Encounter`, `Observation`, `QuestionnaireDefinition`, `QuestionnaireResponse`, `MedicationEvent`, `RiskEvent`, `AdherenceEntry`, `ClinicalHistoryEvent`, `Attachment`, `DocumentExtraction`, `ClinicalMessage`, `Alert`, `AlertDelivery`, `HistoryDigest`, `ContextSnapshot`, `AgentRun`, `Recommendation`, `RecommendationReview`, `DecisionTrace`, `EvidenceCitation`, `AuditEvent`.

История append-oriented: исправления — новая версия с `supersedes_id`/`correction_reason`. Планы врача и оригинальные ответы LLM не перезаписываются. Ссылки `source_ref` указывают на локальные данные, а не дают модели прямой доступ к хранилищу.

**Контракт анализа (логическая схема):**
```json
{
  "schema_version": "2.0",
  "request_id": "uuid",
  "context_snapshot_id": "uuid",
  "history_digest": {"digest_version": 1, "facts": []},
  "current_encounter": {},
  "questionnaire_results": [],
  "observations": [],
  "attachments": [
    {
      "attachment_ref": "att_uuid",
      "kind": "pdf",
      "extraction_ref": "ext_uuid",
      "selected_excerpt_refs": []
    }
  ],
  "clinician_feedback": null
}
```
Это **проект контракта**, не утверждение о существующем API и не полный JSON Schema. Для обратной совместимости старые DTO `v1.1` поддерживаются через явный mapping/адаптер или новый версионированный endpoint. Реальный outbound payload **не должен** передавать прямые идентификаторы, приватные URL или локальные абсолютные пути; содержимое фрагментов и/или бинарные вложения добавляются только после проверки политики.

**Предполагаемые endpoint-группы (целевые; не все существуют сейчас):**
```text
/api/v1/auth/*
/api/v1/patients/*
/api/v1/encounters/*
/api/v1/questionnaires/*
/api/v1/observations/*
/api/v1/attachments/*
/api/v1/messages/*
/api/v1/adherence/*
/api/v1/alerts/*
/api/v1/clinical/analyze
/api/v1/recommendations/{id}/reviews
/api/v1/context/{id}/preview
/api/v1/config
/api/v1/health
```
Конкретные методы и DTO публикуются в OpenAPI после реализации. Сохранять действующие `/api/v1` пути; не переименовывать их без миграции и тестов.

**Модель согласования:**

```text
DRAFT_BY_AGENT
  ├─ approve → APPROVED
  ├─ edit → MODIFIED (с отдельной версией врача)
  └─ request_revision(comment) → REVISION_REQUESTED
                              → новый AgentRun → DRAFT_BY_AGENT
```

Каждая версия содержит автора, время, `source_snapshot_hash`, `model_id`, `policy_version`, `schema_version`, исходный JSON и комментарий врача. Только врач с доступом к пациенту может менять status. Повторный запрос с комментарием учитывает предыдущий ответ и неизменный snapshot либо явно создаёт новый snapshot, если история изменилась.

## 7. Роли, рекомендации, согласование и алерты

**Врач:** создаёт и читает доступных пациентов, просматривает вложения и самоотчёты, запускает агент, подтверждает/изменяет рекомендации, отправляет на доработку с комментарием, получает алерты.

**Пациент:** видит только свои данные и разрешённую часть плана, отправляет жалобы/шкалы/аудио/документы, фиксирует приверженность и нежелательные явления, общается со своим ведущим врачом. Не видит неутверждённые гипотезы и не утверждает назначения.

**Система:** проверяет реальные server-side права на каждый запрос и каждое вложение, включая доступ к кэшированным и скачиваемым файлам. События критического риска приводят к `Alert` даже при недоступном LLM. `AlertDelivery` сохраняет попытки доставки, время поступления, подтверждение врача и повторную попытку по настроенной политике. Доставка не считается успешной по одной записи в БД.

**Критический конфликт требований:** если критическая ситуация есть, обычный агентский анализ не должен скрывать/заменять экстренный маршрут; врачу показывается алерт, не зависящий от результатов LLM. Клинические пороги должны быть утверждены специалистом; без этого — только ясно маркированные демо-правила.

## 8. Стек и структура проекта

**Рекомендуемый стек:** FastAPI + Pydantic v2 + SQLAlchemy/Alembic; SQLite для разработки, PostgreSQL при многопользовательском развёртывании; Flutter/Dart для Windows/Android; API-провайдер LLM через `LLMProviderAdapter`; pytest + flutter test; защищённое файловое хранилище; фоновая обработка вложений и оповещений. ## 9. План этапов 0–9

Нумерация сохраняется для совместимости с прежним планом. **Прохождение этапов 0–4 со слов команды не означает, что весь перечисленный функционал был найден в исходниках.** Реальную готовность определяют тесты и аудит дерева проекта.

| Этап | Цель / обязательный проверяемый результат |
|---|---|
| 0 | Windows/Python/Flutter toolchain; окружение и версия зависимостей |
| 1 | FastAPI, DTO, версии контрактов, OpenAPI, health |
| 2 | БД пациента/визитов/истории, миграции, seed, сохранность данных |
| 3 | UI врача: пациенты, визиты, опросники; проверить фактическое наличие Flutter |
| 4 | History Digest, delta, immutable Context Snapshot, provenance |
| **5** | RBAC, doctor–patient link, PII/technical guard, независимые алерты и тесты |
| **6** | Загрузка PDF/DOC/DOCX/аудио, extraction/STT, LLM Gateway, структурированные ответы, mock provider |
| **7** | UI врача и пациента, динамика, приверженность, сообщения, review: approve/edit/request revision |
| **8** | Демосценарии чемпионата, в т.ч. «Авиандр», eval harness, алерты, reset, метрики |
| **9** | Сквозные тесты, офлайн, безопасность, backup/recovery, Windows/Android build при наличии toolchain, отчёт покрытия |

**Этап не закрывается**, пока не работают соответствующие API, UI и минимальные негативные тесты. Конкурсная готовность определяется **отдельно** от завершённости инженерных этапов.

### Конкурсные демонстрации

Обязательно показать хотя бы: первичный опрос и рекомендованный LLM дополнительный тест; документ/аудиорезультат с источником и интерпретацией; изменение динамики; предложение терапии с «Авиандром» на синтетическом кейсе; направление к психиатру «обязательно»/«желательно»; критический сигнал с фактической доставкой врачу; отправку плана на доработку с комментарием и последующее подтверждение.

## 10. Запуск, конфигурация и тесты

**Ниже типовой способ запуска, требует наличия соответствующих файлов.** Нельзя утверждать, что скрипты/клиент созданы, не проверив рабочее дерево.

Из корня репозитория в PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

Тесты:

```powershell
.\.venv\Scripts\python.exe -m pytest backend\tests -q
```

Клиент (после создания Flutter project):

```powershell
cd client
flutter pub get
flutter test
flutter run -d windows
```

Конфигурация должна быть представлена в `.env.example` без реальных секретов:

```dotenv
APP_ENV=development
DATABASE_URL=sqlite:///./data/aidoctor.db
AI_PROVIDER=mock
AI_MODEL_ID=SET_MODEL_ID
AI_API_KEY=
AI_BASE_URL=
AI_REQUEST_TIMEOUT_SECONDS=60
MAX_UPLOAD_MB=25
MAX_AUDIO_SECONDS=600
STORAGE_DIR=./data/attachments
ALERT_DELIVERY_MODE=demo
```

`AI_PROVIDER=mock` — режим воспроизводимых тестов без медицинских утверждений и расходов API. Переменные — **целевой контракт конфигурации**, внедрение подтверждается тестами. Никаких ключей в Flutter или Git.

Рекомендуемый минимум проверок:
- авторизация на чужого пациента / скачивание чужого файла возвращает отказ;
- изменённый файл/вложение инвалидирует релевантный snapshot;
- битый PDF, DOC без конвертера, пустое аудио и таймаут STT не создают фиктивных результатов;
- один `request_id` не создаёт дубли при повторной отправке;
- LLM invalid JSON/refusal/timeout даёт безопасное состояние;
- врач может approve, edit, request revision; пациент не может;
- новая версия LLM после комментария **не** получает auto-approval;
- критический алерт создаётся без подключения LLM, доставляется и подтверждается врачом;
- сбой фонового обработчика не теряет файл/сообщение/критическое событие;
- все конкурсные сценарии воспроизводимы только на synthetic data.

## 11. Проверка требований чемпионата

Ниже **матрица приёмки**, не заявка о текущем статусе реализации.

| Требование | Проверяемое доказательство |
|---|---|
| 2 роли | Тесты RBAC + оба пользовательских экрана |
| Ведущий врач и передача самоотчёта | Пациент отправляет данные → они автоматически появляются у связанного врача |
| Стандартизированные шкалы | 2 валидированные русскоязычные шкалы, источники и лицензии, детерминированный score |
| Клинические рекомендации/терапия | Структурированный ответ LLM, ссылки на действующие КР и инструкции, review специалиста |
| Риски и нежелательные явления | Записи, уведомление, история и видимость врачу |
| Динамика | Графики по измерениям + история |
| Коммуникация | Обмен сообщениями с проверкой прав |
| Приверженность | Самоотчёты, история, аналитическое отражение в контексте |
| Психиатрическая маршрутизация | Разные уровни «обязательно/желательно», врачебное подтверждение |
| «Авиандр» | Синтетические кейсы + проверка соответствия актуальной инструкции из ГРЛС специалистом |
| Экстренный алерт | Контроль времени от критических данных до получения/подтверждения врачом |
| Неприменение решений без врача | Негативные тесты невозможности автоматических назначений |
| Конфиденциальность и закон | Privacy assessment, доступы, шифрование, отсутствие реальных данных в демо |
| Технические метрики | Отчёт latency, reliability, recovery, throughput, coverage, security |
| Дополнительный продуктовый scope | PDF/DOC/DOCX/аудио → извлечение → выбранный внешний LLM → source-linked ответ |

**Целевые критерии готовности:**
1. Все обязательные условия кейса имеют работающий сценарий и минимум один автоматический тест.
2. Врач и пациент выполняют workflow из разных сессий, без доступа к чужой истории.
3. Вложения доступны для анализа агентом с воспроизводимым `source_ref` и контролем ошибок извлечения.
4. Каждая медицинская рекомендация имеет решение врача либо статус ожидания.
5. Новая версия рекомендаций не заменяет исходный документ/ответ.
6. Алерт не зависит от внешней LLM и сопровождается измерением доставки.
7. Отчёт показывает **фактические** результаты тестов; непроверенное явно маркируется.

## 12. Безопасность, ограничения и решения

- **Данные:** для чемпионата только синтетические или корректно обезличенные. Реальные идентифицируемые медицинские данные и аудиозаписи — только после отдельной юридической, ИБ, регуляторной и клинической оценки, включая условия конкретного LLM-провайдера.
- **Медиа:** запрет публичных ссылок на вложения; шифрование в хранении и передаче; антивирус/лимиты/защита от архивных бомб и макросов; удаление с учётом политики и резервных копий.
- **LLM:** обработка непредсказуемого вывода; prompt injection внутри PDF/аудио трактуется как недоверенное содержимое, не как команда агенту. Врач видит, какие сведения отправляются провайдеру.
- **Наличие платформы:** фактические возможности загрузки PDF/документов/аудио, хранение файлов, регионы и retention проверяются **после выбора API**. При отсутствии поддержки оригиналов используем extraction/transcription fallback с подтверждением потерь.
- **Владение:** база и файлы — источник истины backend; `HistoryDigest`, `ContextSnapshot`, extracted texts и отображения UI — версионированные производные.
- **Контракты:** существующие API не ломать молча; новые поля через versioned DTO и миграции. Устаревший `/v1/*` из первоначального README не считать автоматически совпадающим с действующим `/api/v1/*`.
- **Расширяемость:** специализированные профили/опросники добавляются как конфигурации, а не как условие `if anxiety/depression` в ядре.
- **Границы:** README не является медицинским заключением, сертификацией или обещанием точности LLM.

### Архитектурные решения, которые нужно подтвердить перед production

1. Конкретный провайдер и API агента; поддержка `file upload`/multimodal/structured output и допустимый формат вложений.
2. Серверное развёртывание и политика синхронизации мобильных клиентов.
3. Провайдер хранения файлов и требования к ключам шифрования.
4. OCR/STT/конвертер DOC и разрешённые форматы/размеры.
5. Канал доставки критических алертов и правила повторных оповещений.
6. Правовая модель обработки/передачи медицинских данных и клиническое утверждение safety rules.

---

**Главное архитектурное решение:** AIDoctor хранит медицинскую историю, документы, тесты и решения врача; **внешний LLM** ведёт клинический анализ по доступному контексту, рекомендует уточняющие тесты и варианты лечения; **врач утверждает, корректирует или возвращает предложения на доработку**; критические предупреждения и контроль исполнения независимы от модели.
