# AIDoctor — серверная медицинская платформа

**Статус:** разработка; не предназначено для эксплуатации с реальными медицинскими данными.
**База данных:** только **PostgreSQL 16+**, через `psycopg` 3. SQLite в проекте не поддерживается.
**API:** `/api/v1` (сохранённый контракт).

## Назначение

AIDoctor — универсальная система сопровождения пациента с ролью врача и пациента.
Поддерживает продольную историю визитов, опросники, медицинские наблюдения,
привязку ведущего врача и пациента.
Целевой функционал: загрузка PDF, DOC/DOCX, аудио и изображений, внешний LLM-агент
для клинического анализа, согласование рекомендаций врачом (утвердить, скорректировать,
вернуть с комментарием), коммуникация и тревожные сигналы.
**Целевой функционал не означает, что он уже реализован.**

Для чемпионата обязательны сценарии тревожно-депрессивной симптоматики,
в том числе «Авиандр», раздельные роли и связь пациента с врачом, мониторинг,
приверженность, критические оповещения, подтверждение клинических действий врачом,
научные источники и проверка условий использования шкал.
Все медицинские решения формирует внешний LLM; backend их не исполняет автоматически.
Независимые технические проверки, права доступа и экстренное уведомление
должны работать вне LLM.

## Реализовано в текущем пакете

- FastAPI, SQLAlchemy, Pydantic, Alembic.
- Пациенты, визиты, опросники, события истории.
- Учётные записи врачей/пациентов, серверные bearer-сессии, права на просмотр истории.
- Модели медицинских наблюдений и метаданных вложений.
- Локальный файловый API загрузки, списка и скачивания вложений через проверку прав.
  Загруженные файлы имеют статус `quarantined`; сканирование и анализ не реализованы.
- Конфигурация PostgreSQL-only и PostgreSQL-тестовая база.
- Существующие Alembic-ревизии; данные прежней тестовой SQLite не переносятся.

## Запуск на Windows / PyCharm (PowerShell)

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
docker compose up -d postgres
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current
python -m uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
```

После запуска Swagger: http://127.0.0.1:8000/docs

Для вложений используются маршруты `/api/v1/patients/{patient_id}/attachments`.
Оригиналы сохраняются в каталоге `ATTACHMENTS_DIR` (по умолчанию `data/attachments`).
Описание контрактов, ограничений и проверок: [docs/attachments.md](docs/attachments.md).

**Пароль из `compose.yaml` предназначен только для локальной разработки**.
До доступа через интернет нужны выделенная защищённая БД, новые секреты, TLS,
ограничение входов, устойчивые сессии и юридическая/ИБ-проверка.
Не открывать PostgreSQL в интернет и не публиковать каталог файлов как static.

## Тесты

Создать отдельную БД `aidoctor_test`:

```powershell
.\scripts\postgres_test_db.ps1
python -m pytest backend\tests -v -rs
python -m ruff check backend
python -m alembic -c alembic.ini check
```

Интеграционные тесты требуют `TEST_DATABASE_URL` на локальный PostgreSQL с именем,
заканчивающимся `_test`. Во время запуска тесты очищают **только эту выделенную БД**.
Без переменной они будут пропущены, а не засчитаны как успешная интеграционная проверка.

## Схема владения данными

`врач/пациент → HTTPS API → PostgreSQL → Context Builder → внешний LLM → предложения → подтверждение врача`.

Backend является единственным владельцем оригиналов и событий.
Метаданные вложений хранятся в PostgreSQL, оригиналы — в частном хранилище.
LLM возвращает структурированные результаты, но не пишет напрямую в БД.
Версии истории и решений врача должны сохраняться независимо от ответов модели.

## Архитектурные инварианты

1. Единственная серверная БД — PostgreSQL; не смешивать локальные копии с источником истины.
2. Не нарушать `/api/v1` без версионирования и тестов.
3. Новые типы обследований и LLM-провайдеры — через расширяемые контракты.
4. Пациент не видит чужих данных; врач видит только разрешённых пациентов.
5. Предложения LLM требуют врача: утверждение / редактирование / доработка.
6. Критические уведомления не должны зависеть от доступности LLM.
7. Для конкурсного демо — только синтетические или надлежащим образом обезличенные сведения.

## Проверка готовности этапа 2

- Установлен `psycopg` 3, конфигурация не допускает других драйверов.
- `alembic upgrade head` проходит на чистой базе PostgreSQL.
- `pytest` проходит **на PostgreSQL**, включая тесты прав доступа и вложений.
- Данные сохраняются после перезапуска backend и PostgreSQL.
- Конфигурация и README не предлагают альтернативный локальный SQL-движок.

**Ограничения:** локальная разработка и автоматические тесты не являются медицинской
или юридической сертификацией. Работа с настоящими историями запрещена до отдельной проверки.
