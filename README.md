## 1. Назначение проекта

**Clinical Compass Agent** — локально-ориентированная кроссплатформенная система **поддержки клинических решений** для врача: скрининг тревожно-депрессивной симптоматики, ведение истории визитов, отслеживание динамики, обнаружение критических сигналов и получение структурированных предложений от LLM.

Цель — **не чат с ИИ**, а воспроизводимый workflow:

```text
Пациент → новый визит → шкалы и клинические события
        → локальная история → History Digest → Delta
        → Context Snapshot → PII Guard → Safety precheck
        ├── критический риск → URGENT_ESCALATION (без обычного LLM вызова)
        └── допустимый запрос → FastAPI Gateway → LLM API
                → строгий JSON → post-safety → результат врачу
                → сохранение AgentRun / DecisionTrace
```

Врач остаётся ответственным за решения. LLM формирует **гипотезы и варианты тактики на проверку**, а не автономно ставит диагноз или назначает лекарства.

**Критическое условие:** в конкурсном MVP используются **только синтетические или надлежащим образом обезличенные данные**. Реальные идентифицируемые медицинские сведения запрещены до отдельной клинической, юридической, ИБ и регуляторной подготовки.

### Ценность

- Врач видит изменения с прошлого визита и динамику шкал.
- Клинический эксперт видит provenance, версии правил и историю решений.
- Демонстратор показывает три сценария с одной кнопкой сброса.
- Разработчик может заменить LLM-провайдера без переписывания UI.

## 2. Границы MVP

### Рекомендованный порядок

**Сначала Windows MVP**, сервер FastAPI и клиент Flutter работают **на одном домашнем ПК**. Затем — сборка Android как отдельный этап. Это рабочее сокращение исходного конкурсного объёма: **ТЗ v1.1 требует Windows + Android к полному релизу**, а наш первый контрольный результат — именно Windows.

**Нужно реализовать в Windows MVP:**

1. Локальных синтетических пациентов, визиты и события.
2. Две конфигурируемые шкалы: PHQ-9 и GAD-7, детерминированный подсчёт.
3. Локальное шифрованное хранилище, timeline и графики.
4. History Digest, Context Builder, Context Snapshot и delta.
5. Safety precheck/hard-stop, ABSTAIN/NEEDS_DATA, проверку приватности.
6. AI Gateway, хранение секретов на сервере, строгий JSON.
7. Результат анализа с гипотезами, источниками, маршрутизацией и missing data.
8. AgentRun, DecisionTrace, версионирование и подтверждение врачом.
9. Трёх демонстрационных пациентов, reset, тесты и краткий eval-отчёт.

**Не входит в первый релиз:** iOS/macOS, пациентский кабинет, МИС/FHIR, production-SSO, on-prem LLM, настоящий мультипользовательский сервер, полноценный MCP/plugin adapter, работа с реальными пациентами.

**Оценка одного разработчика с помощью ИИ:** **60–90 часов**, ориентир **80 часов**, при условии рабочего окружения. Android дополнительно ориентировочно **20–35 часов**. Это **инженерные оценки, не цифры ТЗ и не гарантия**. Полный клинически размеченный eval pack требует отдельного времени клинического эксперта.

## 3. Технологический стек и обоснование

| Направление | Решение | Почему | Ограничение |
|---|---|---|---|
| IDE | **PyCharm**, PowerShell | Редактор Python, Git, Run Configurations; Flutter запускаем из встроенного терминала | Dart/Flutter-плагины должны подходить к версии IDE |
| Backend | **Python 3.12** | Быстрая разработка логики, тестов, моделей данных | Версию и совместимость пакетов фиксируем |
| API | **FastAPI** | Простые маршруты, OpenAPI, интеграция с Pydantic | Не заменяет аутентификацию и safe logging |
| Схемы | **Pydantic v2 / JSON Schema / OpenAPI 3.1** | Строгие DTO, enums и contract tests | Версионировать изменения |
| UI | **Flutter stable + Dart** | Нативный Windows desktop, последующий Android, одна кодовая база | Нужна Windows C++ toolchain |
| DB | **SQLite** | Не нужен отдельный сервер БД; offline история | Обязательны миграции, транзакции |
| Шифрование | **SQLCipher / поддерживаемый OS-encrypted container** | Privacy из ТЗ, local-first | Проверка реальной Windows/Android совместимости на этапе 0 |
| Слой данных | **Drift (предложено)** | Типизированные SQL-запросы, миграции | Связку с шифрованием предварительно тестируем |
| Графики | **fl_chart** | Готовые line charts для шкал | Нельзя дорисовывать отсутствующие измерения |
| LLM | **Внешний API + provider adapter** | Не требует мощной GPU на домашнем ПК | Нужен интернет и безопасная отправка контекста |
| Тесты | **pytest, flutter test** | Низкий порог, unit/contract/integration | Не доказывают клиническую эффективность |
| Версии | **Git, lockfiles** | Откат и воспроизводимость | `.env` и БД не в Git |
| Evals | **Python CLI + synthetic JSON fixtures** | Измеримые результаты без тяжёлой платформы | Gold labels утверждает эксперт |

### Почему именно Flutter, а не Python GUI?

PyCharm не ограничивает язык приложения. Для Windows + Android исходное ТЗ рекомендует Flutter. Он эффективнее для интерфейсов карточек, форм, графиков и переносимости. Python разумно оставить для Gateway, клинических интеграций и eval harness. Использование, например, PyQt дало бы удобный Windows GUI, но осложнило последующий Android и изменило исходную стратегию одной кодовой базы.

### Почему FastAPI, а не Django/Flask?

Нам нужен **тонкий stateless API Gateway**, а не большой портал с серверной БД и административной панелью. FastAPI + Pydantic дают формализованные контракты, валидацию и документацию при меньшем количестве инфраструктурной работы.

### Почему SQLite, а не PostgreSQL?

Владельцем истории является **клиент**, не сервер. На одном компьютере SQLite исключает отдельный процесс БД, сеть и сложное сопровождение. PostgreSQL понадобится только при сознательном изменении архитектуры на серверное хранение и синхронизацию.

### Почему не Docker и не локальная LLM?

Для Windows-only разработки **Python venv + Flutter** достаточно; контейнеризация сейчас увеличивает сложность. Местная LLM зависит от CPU/GPU/RAM и потребует отдельной проверки качества. В MVP модель вызывается через облачный API, но **только с допустимыми синтетическими данными**.

**Допущение:** окончательные версии пакетов выбираем после `flutter doctor` и раннего теста совместимости DB encryption. Нельзя считать неподтверждённую связку Drift/SQLCipher уже работающей.

## 4. Архитектура

```text
┌────────────────────── FLUTTER WINDOWS ──────────────────────┐
│ UI: Patients / Encounters / Scales / Timeline / Result      │
│                                                            │
│ SQLite (шифрование): events, visits, scales, runs, traces   │
│       ↓                                                    │
│ Domain: Digest Builder → Delta Builder → Context Builder   │
│       ↓                                                    │
│ Client PII Guard + Safety Precheck                          │
└───────────────────────────┬────────────────────────────────┘
                            │ JSON → 127.0.0.1:8000
                            ▼
┌───────────────────── FASTAPI GATEWAY ───────────────────────┐
│ Auth / size & schema validation / PII recheck               │
│ Safety recheck / Policy / LLM Adapter / Structured Output   │
│ Postvalidator / telemetry БЕЗ clinical payload              │
└───────────────────────────┬────────────────────────────────┘
                            │ HTTPS
                            ▼
                        LLM Provider
```

### Границы ответственности

- **Flutter + SQLite**: единственный источник истины по пациентам, визитам, лекарственным событиям, шкалам и сохранённым результатам.
- **History Digest**: производный и пересобираемый из локальных событий.
- **Context Snapshot**: неизменяемый пакет фактически отправленного контекста, с идентификатором, hash и версиями.
- **Gateway**: без хранения медицинского содержания запросов в БД/логах, выполняет валидацию, safety postcheck и вызов внешнего провайдера.
- **LLM**: помогает с семантическим анализом, не управляет правилами безопасности.

### Жизненный цикл запроса

1. Сохранить новый визит локально.
2. Инвалидировать старый Digest, если изменились исходные события.
3. Сформировать актуальные Digest и delta.
4. Собрать минимальный Context Snapshot: демография без идентификаторов, текущий визит, активные лекарства, риск, последние шкалы и нужные факты.
5. Выполнить локальный safety precheck и PII guard.
6. При hard-stop **не отправлять обычный запрос в LLM**.
7. Вычислить детерминированный `input_hash` от канонического JSON.
8. Передать версионированный запрос через Gateway.
9. Валидировать Structured Output и проверить невозможные противоречия.
10. Создать **новый** AgentRun, сохранить решение врача отдельно.

### Режимы работы

- **Windows online:** UI → локальный Gateway → внешний API.
- **Windows offline:** пациент, шкалы, timeline, сохранение визита доступны; LLM-анализ выдаёт понятное техническое состояние.
- **Android позже:** телефону нельзя использовать `127.0.0.1` как адрес ПК; нужен адрес ПК в LAN и **HTTPS с проверкой сертификата**.
- **Интернет-доступ к домашнему Gateway:** не требуется и в MVP не открывается.

## 6. Windows и PyCharm

### 6.1. Что установить

1. **Git** — для версий кода.
2. **Python 3.12** — рекомендуемый interpreter backend; проверить совместимость пакетов.
3. **PyCharm** — открыть корень проекта, настроить Python interpreter.
4. **Flutter SDK stable** — на `PATH`; Dart входит в поставку Flutter.
5. **Visual Studio Desktop development with C++** — компилятор/средства сборки для Flutter Windows desktop. Это **Visual Studio**, а не Visual Studio Code.
6. **Android Studio/Android SDK** — только перед этапом Android, если понадобится.
7. Опционально: Flutter/Dart плагины PyCharm, если они поддерживаются установленной версией IDE. В любом случае `flutter` запускается из встроенного терминала.

**Проверка в PowerShell:**

```powershell
python --version
git --version
flutter --version
flutter doctor -v
flutter devices
```

`flutter doctor` для Windows toolchain должен стать рабочим **до** разработки UI. При ошибке сборки сначала чинить окружение, потом писать клинические модули.

### 6.2. Создать проект

В терминале PowerShell, открытом в родительской папке:

```powershell
New-Item -ItemType Directory -Force clinical-compass-agent
Set-Location clinical-compass-agent
New-Item -ItemType Directory -Force backend, contracts, policies, evals, scripts, docs
git init
py -3.12 -m venv .venv
```

Если `py -3.12` не находится, запустить `py --list` и использовать **проверенный** установленный Python. Для обновления pip не требуется активировать окружение:

```powershell
.\.venv\Scripts\python.exe -m pip install --upgrade pip
```

Позже, когда будут созданы файлы `backend/requirements.txt` и Flutter project:

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
flutter create --platforms=windows,android client
```

Если `flutter create` показывает, что каталог `client` уже существует и содержит файлы, **не перезаписывать его без проверки**.

### 6.3. PyCharm Run Configurations

- `Backend — Dev`: Python module `uvicorn`; параметры `app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000`; рабочая папка — корень репозитория.
- `Client — Windows`: встроенный терминал → `cd client` → `flutter run -d windows`.
- `Tests — Backend`: Python module `pytest` с аргументами `backend/tests -q`.
- Flutter tests: терминал в `client` → `flutter test`.

### 6.4. Настройки и секреты

Создать **`.env.example`** с примером полей:

```dotenv
APP_ENV=development
AI_PROVIDER=openai
MODEL_ID=SET_MODEL_ID
OPENAI_API_KEY=SET_SECRET_LOCALLY
GATEWAY_AUTH_TOKEN=SET_DEMO_TOKEN_LOCALLY
REQUEST_TIMEOUT_SECONDS=30
LOG_LEVEL=INFO
```

Настоящие значения размещаем только в локальном `.env` (и исключаем его из Git). Модель определяется по реально доступному API перед этапом 6. Клиент **не** должен содержать `OPENAI_API_KEY`; демо-токен клиента не считается полноценной production-аутентификацией.

`.gitignore` должен защищать `.env`, `.venv`, `build`, `.dart_tool`, локальные SQLite/SQLCipher файлы, временные логи и другие артефакты.

**Не изменять системную PowerShell execution policy без необходимости.** Всегда можно вызывать `.\.venv\Scripts\python.exe` напрямую.

## 7. Контракты и инварианты

### 7.1. REST API (из ТЗ v1.1)

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/v1/health` | Проверка доступности Gateway |
| `GET` | `/v1/config` | Версии policy/schema, feature flags |
| `POST` | `/v1/clinical/analyze` | Запуск AI-анализа snapshot |
| `POST` | `/v1/context/preview` | **Опционально:** валидация outbound context |
| `POST` | `/v1/review` | **Опционально:** de-identified экспертная оценка |

Ориентируемся на `ClinicalAnalysisRequest v1.1` и `ClinicalAnalysisResponse v1.1` из **раздела 9 ТЗ**. Изменение полей — с явной версией и контрактными тестами.

**В запросе:** `schema_version`, `request_id`, `context_snapshot_id`, сведения текущего визита, минимальная демография, `history_digest`, `scales`, `active_medications`, `critical_context`, `delta_summary`, `risk_inputs`, `source_refs`, client metadata.

**В ответе:** `analysis_id`, `request_id`, `schema_version`, `status`, `summary`, `safety`, `hypotheses`, `missing_data`, `recommended_next_steps`, `routing`, `treatment_options`, `follow_up`, `evidence`, `decision_trace`.

Полные схемы не придумывать по README: реализуем их по оригинальному ТЗ, сохраняем в Pydantic и экспортируем в `contracts/openapi.json`.

### 7.2. Статусы

| Статус | Поведение |
|---|---|
| `OK` | Структурированный результат и кнопка подтверждения |
| `NEEDS_DATA` | Конкретный список необходимых данных |
| `URGENT_ESCALATION` | Видимый hard-stop, обычный анализ блокирован |
| `ABSTAIN` | Отказ от вывода с причиной |
| `MODEL_REFUSAL` | Безопасная обработка отказа модели |
| `TECHNICAL_ERROR` | Сохранить локальные данные, сообщить о сбое |

**HTTP 200 != клинический OK:** состояние определяется `status` внутри проверенного контракта.

### 7.3. Локальные сущности

`Patient`, `Encounter`, `Observation`, `QuestionnaireResponse`, `MedicationEvent`, `RiskEvent`, `ClinicalHistoryEvent`, `HistoryDigest`, `ContextSnapshot`, `AgentRun`, `DecisionTrace`, `EvidenceCitation`.

**История append-oriented:** старые события не перезаписываются тихо; исправления через `supersedes_id` / `correction_reason`. `Digest` — производная версия истории; каждый клинически значимый факт имеет `source_ref`, дату и происхождение. `ContextSnapshot` неизменяем после отправки.

### 7.4. Совместимость и инварианты

- `schema_version = "1.1"` в базовом API; обновление требует новой версии или доказанной обратной совместимости.
- `source_state_hash` меняется при изменении исходной истории; Digest становится `stale`.
- Одинаковые события и одинаковая версия builder дают эквивалентный Digest; hash вычисляется из **канонизированного** содержимого без случайных полей времени.
- `input_hash` связывает `AgentRun` с точным отправленным snapshot; старый snapshot **не переписывается**.
- `request_id`/`Idempotency-Key` предотвращает случайный двойной учёт повторных вызовов.
- `*_is_calibrated = false` явно показывается рядом с любой оценочной вероятностью, если калибровки нет.
- Существование JSON Schema **не гарантирует медицинскую правоту**. Safety и evidence нужны отдельно.
- Недостающие значения — `null`/`unknown`, не произвольный текст.
- Критический risk flag нельзя понизить ответом модели.
- Клинические пороги берём **только из согласованного с врачом ruleset**. ТЗ задаёт категории рисков, а не самостоятельно утверждённые численные пороги.

## 9. Подробные этапы реализации

Каждый этап заканчивается **артефактом, smoke-тестом и явным «готово»**. Если тест не проходит — следующий этап не начинаем.

### Этап 0 — Окружение и ранние риски (4 часа)

**Цель:** на Windows реально собираются Flutter desktop и backend, а защита локальной БД технически достижима.

**Шаги:**

1. Установить Python, Git, Flutter stable, Visual Studio C++ Desktop Toolchain.
2. Настроить `python.exe` из `.venv` в PyCharm.
3. Выполнить `flutter doctor -v`, `flutter devices`.
4. Проверить запуск шаблонного Flutter Windows приложения.
5. Провести небольшой **spike на SQLite encryption**: выбрать реально поддерживаемый драйвер/подход (SQLCipher либо защищённый OS-encrypted container, как разрешено ТЗ) и попробовать открыть/закрыть БД в Windows. Если невозможно — зафиксировать блокер, а не заявлять выполненное требование.
6. Создать Git и `.gitignore`.

**Почему сначала:** Flutter toolchain/шифрование — зависимость нескольких следующих этапов; позднее обнаружение несовместимости сломает график.

**Файлы/артефакты:** `.gitignore`, `docs/decisions/0001-toolchain.md`, проверочный Windows build.  
**Smoke:** `flutter doctor -v` не показывает критических проблем Windows toolchain; тестовая Flutter desktop app запускается.  
**Краевые случаи:** Python не в PATH; несовместимость зависимостей/нативных DLL; недостаточный доступ Windows; визуальная сборка без C++ toolchain.  
**Готово:** окружение воспроизводимо; выбранная стратегия хранения не требует полного переписывания БД позже.

### Этап 1 — FastAPI skeleton и единый контракт (6 часов)

**Цель:** отделить UI от backend ещё до появления клинической логики.

**Шаги:**

1. Создать `backend/app/main.py`, `api/health.py`, `api/config.py`.
2. Подключить FastAPI, Pydantic v2, переменные окружения.

7. Добавить unit и smoke-тесты в `backend/tests/`.

**Почему FastAPI + Pydantic:** один контракт определяет и API, и серверную валидацию; Flutter использует те же fixtures. Так избегаем дрейфа DTO между языками.

**Артефакты:** запускаемый Gateway без LLM, OpenAPI, тесты.  
**Smoke:** `GET /v1/health` успешно; валидный JSON проходит; неправильные enum/`schema_version` отклоняются.  
**Краевые случаи:** пустые массивы, `unknown`, timezone offset, лишние поля, превышение размера.

### Этап 2 — SQLite, сущности и синтетические данные (9 часов)

**Цель:** получить настоящий **локальный источник истины**, не зависящий от Gateway.

**Шаги:**

1. Реализовать минимальные `Patient`, `Encounter`, `QuestionnaireResponse`.
2. Добавить `Observation`, `MedicationEvent`, `RiskEvent`, `ClinicalHistoryEvent`.
3. Сразу предусмотреть `HistoryDigest`, `ContextSnapshot`, `AgentRun`, `DecisionTrace`.
4. Создать миграцию схемы v1 с индексами, внешними ключами, ограничениями.
5. Внедрить транзакции/репозитории, единый код работы с БД.
6. Исправления события записывать отдельно через `supersedes_id / correction_reason`.
7. Подключить проверенное шифрование и безопасное хранение ключа.
8. Наполнить локальную БД только синтетическими seed-данными; проверить перезапуск.

**Почему SQLite + event-based history:** автономно, быстро, хранит точные факты и изменения, позволяет пересобирать Digest. Прямая перезапись истории ломает аудит и запрещена требованиями.

**Артефакты:** DB migrations, repositories, demo seed и DB tests.  
**Smoke:** добавленный визит виден после рестарта; правка старого факта создаёт новую версию; внешние ключи соблюдены; файл БД защищён выбранным механизмом.  
**Краевые случаи:** две записи с одинаковым временем; повреждённая транзакция; несуществующий patient ID; повторный seed; обновление версии схемы.  
**Готово:** локальная продольная история надёжно сохраняется.

### Этап 3 — Windows UI, формы визита и две шкалы (9 часов)

**Цель:** врач может работать с пациентами **без LLM**.

**Шаги:**

1. Flutter Windows: маршруты и начальная навигация.
2. Экран списка пациентов, поиск по alias/local ID.
3. `Patient overview`: последний визит, последние баллы, предупреждения, кнопки действий.
4. Формы создания нового Encounter с локальным черновиком.
5. Конфигурируемые `PHQ-9` и `GAD-7` с суммированием по явным правилам.

7. Русские UI-строки вынести в localization resources.

**Почему Flutter:** один UI-код для будущего Android; готовые формы, состояние, навигация. **Почему баллы без LLM:** итоговые числовые шкалы детерминированы и должны одинаково вычисляться на любом запуске.

**Артефакты:** `patients`, `encounters`, `questionnaires` features.  
**Smoke:** создать пациента, визит и две шкалы; закрыть/открыть приложение; получить те же данные и суммы.  
**Краевые случаи:** пустая анкета, частично заполненная шкала, нулевые баллы, повторное сохранение, даты вне диапазона.  
**Важно:** до публикации проверить право использования форм/текста шкал.  
**Готово:** базовый clinical data entry работает offline.

### Этап 4 — History Digest, Delta и Context Snapshot (10 часов)

**Цель:** реализовать **ключевое преимущество** проекта — воспроизводимую краткую историю и минимальный outbound context.

**Шаги:**

1. Создать `HistoryStore`: выборка нормализованных событий, provenance.
2. Реализовать rule-based `DigestBuilder`:
   - всегда включать активные препараты, аллергии и актуальные риски;
   - включать последние значения шкал и значимые изменения;
   - сохранять нерешённые побочные эффекты;
   - **все** критические долгосрочные факты — независимо от возраста.
3. Для каждого факта сохранять `source_ref`, `occurred_at`, `category`, `priority`.
4. Версионировать Digest: `digest_id`, `digest_version`, `builder_version`, `source_state_hash`, `generated_at`.
5. Помечать Digest `stale`, если история поменялась.
6. Реализовать `DeltaBuilder` относительно предыдущего завершённого визита.
7. Собрать `ContextSnapshot`: текущий визит + Digest + последние шкалы + delta + критические факты + ссылки на источники.
8. Ограничить размер: ориентир 3 последних визита и окно 90 дней **кроме critical facts**.
9. Применить local PII scan до отправки; создать immutable snapshot и его SHA-256.
10. Добавить экран «Что отправится модели».

**Почему rule-based, а не LLM-суммаризация:** детерминированный Digest легко пересобирается и проверяется. Для safety нельзя зависеть от того, что модель «не забудет» критический факт.

**Артефакты:** `digest_builder.dart`, `context_builder.dart`, `delta_builder.dart`, golden fixtures.  
**Smoke:** одинаковые события дают одинаковый состав Digest; каждый факт раскрывается до источника; изменение MedicationEvent инвалидирует Digest; старый Snapshot не переписывается.  
**Краевые случаи:** отсутствует прошлый визит, противоречащие события, критический факт 2-летней давности, дубликаты, timestamp/timezone, лимит размера payload.  
**Готово:** можно показать конкретный snapshot и его hash, не пересылая всю карту.

### Этап 5 — Safety Engine и PII Guard (8 часов)

**Цель:** критические решения не зависят от интернет-сети и поведения LLM.

**Шаги:**

1. Создать `policies/safety_rules.yaml` с version ID.
2. Согласовать с клиническим экспертом категории и **конкретные** пороги перед их реальным применением.
3. Реализовать клиентский precheck для `URGENT_ESCALATION`, `NEEDS_DATA`, `ABSTAIN`.
4. Реализовать серверный safety recheck для запрета обхода клиента.
5. Обеспечить, чтобы `URGENT_ESCALATION` блокировал обычный AI flow и показывал отдельный UI.
6. Проверять Context Snapshot на прямые идентификаторы; при вероятной PII — блокировать вызов, предложить исправление.
7. Добавить postvalidator противоречий: `urgent=false` недопустим при hard-stop.
8. Написать unit-тесты на нормальные, неполные и критические случаи.

**Почему версия правил нужна отдельно от prompt:** изменения аудируемы, тестируемы, могут быть утверждены специалистом и совпадают на клиенте/сервере.

**Клиническая граница:** само ТЗ не утверждает численные клинические пороги. Пока нет эксперта — только **условные демонстрационные флаги**, явно обозначенные как невалидированные. Не выдавать такие правила за клинический стандарт.

**Артефакты:** rule engine, local/server safety checks, UI hard-stop, PII test pack.  
**Smoke:** критический синтетический кейс **не вызывает LLM**; при отсутствии интернета hard-stop работает; PII блокируется; конфликтующая модель не снимает флаг.  
**Краевые случаи:** неизвестное значение риска, отсутствие обязательных полей, ложноположительная PII, конфликт версий ruleset.  
**Готово:** ни клиент, ни сервер не пропускают критический сценарий через обычный анализ.

### Этап 6 — LLM Gateway и Structured Outputs (10 часов)

**Цель:** получить первый end-to-end анализ пациента.

**Шаги:**

1. Определить интерфейс `LLMProviderAdapter`, затем подключить конкретного провайдера.
2. Прочитать API-key **только из backend environment**.
3. Добавить versioned `clinical_policy.yaml` по требованиям ТЗ, без хранения скрытых рассуждений модели.
4. Подключить Structured Outputs / strict JSON Schema **если выбранная модель поддерживает**.
5. Ограничить размер и содержание запроса, валидация `schema_version`.
6. Реализовать bounded timeout и retry только для допустимых временных ошибок; отдельно обработать 429/5xx.
7. Выполнить validation Pydantic, проверку источников и safety postcheck.
8. Возвращать статусные состояния; не показывать invalid JSON как медицинский результат.
9. Сохранять `AgentRun` в клиентской БД с `model_id`, `policy_version`, `schema_version`, `safety_rules_version`, `input_hash`.
10. Логировать только latency/status/model/стоимость и технические идентификаторы **без clinical text**.

**Почему адаптер и strict schema:** модель можно заменить через конфигурацию, Flutter получает предсказуемый JSON, ошибки можно обработать отдельно. Structured Output — это **форматная**, а не клиническая гарантия.

**Артефакты:** `/v1/clinical/analyze`, provider adapter, Pydantic/post-validation, integration tests.  
**Smoke:** синтетический запрос → валидный результат; отказ провайдера → `MODEL_REFUSAL`; timeout → `TECHNICAL_ERROR`; ключ отсутствует в Dart и HTTP payload клиента.  
**Краевые случаи:** `429`, сброс подключения, несовместимая модель, отказ модели, несуществующий DOI, ответ с urgent contradiction, повтор `request_id`.  
**Готово:** тестовый пациент проходит путь `Flutter → Gateway → LLM → Flutter`.

### Этап 7 — Result UI, timeline, графики и аудит (9 часов)

**Цель:** показать законченный врачебный процесс, а не набор API вызовов.

**Шаги:**

1. Экран анализа: **safety → краткий вывод → недостающие данные → маршрутизация → гипотезы → источники**.
2. Подпись «оценка модели, не калибровано» непосредственно рядом с вероятностями.
3. Timeline: визиты, шкалы, MedicationEvent, RiskEvent, HistoryEvent.
4. `fl_chart`: линия PHQ-9/GAD-7 только по фактическим датам измерения.
5. History Digest preview, stale/fresh и provenance.
6. DecisionTrace: сравнение нового и предыдущего AgentRun, причины изменения.
7. Врачебный статус `accepted / modified / rejected`, не меняющий исходный вывод модели.
8. Блок evidence с пометкой verified/unverified и реальными проверяемыми ссылками.
9. Экран диагностических версий API/policy/model.

**Почему важна визуализация:** динамика и explainability — ключевые отличия от простого LLM wrapper. Разделение AgentRun/DecisionTrace сохраняет контроль врача.

**Артефакты:** экраны результата, timeline, trends, audit trail.  
**Smoke:** значения на графиках совпадают с БД; два анализа дают две записи; решение врача сохраняется отдельно; UI явно различает ABSTAIN и OK.  
**Краевые случаи:** единственная точка шкалы, совпадающие даты, отсутствие доказательств, длинный ответ, старый run, отказ сети.  
**Готово:** клиницист может выполнить законченный workflow.

**Цель:** подготовить воспроизводимый финальный сценарий и честные показатели.

**Шаги:**

### Этап 9 — Релиз, ошибки, безопасность (8 часов)

**Цель:** демо работает на домашнем Windows ПК и не разваливается при типичной ошибке.

**Шаги:**

1. Прогнать pytest, Flutter unit/contract tests и основной UI smoke.
2. Проверить потерю интернета, остановку Gateway, `5xx`, timeout, invalid schema, отказ модели.
3. Проверить, что UI продолжает работать с историей offline.
4. Проверить локальное шифрование, reset, миграции и восстановление после рестарта.
5. Убедиться, что `.env`/ключи не в Git и клиентском bundle, clinical body не в обычных логах.
6. Собрать `flutter build windows` и проверить необходимые DLL/assets.
7. Пройти три demo сценария за ≤4 минуты, подготовить резервную видеозапись.
8. Зафиксировать версии пакетов и завершить release checklist.

**Почему отдельно от разработки:** основные риски на защите — сеть, сборка и расхождение состояния, а не отсутствие ещё одной функции.

**Артефакты:** Windows release build, checklist, результаты тестов.  
**Smoke:** приложение стартует, seed доступен, данные сохраняются offline, API/LLM отказы показываются безопасно, тестовый demo flow воспроизводится.  
**Краевые случаи:** неправильный Windows пользователь, повреждённая БД, завершённый процесс Gateway, заблокированная сеть, отсутствующая DLL.  
**Готово:** Windows-first MVP готов к демонстрации, но **не к использованию на реальных пациентах**.

**Внимание:** команды этого раздела заработают **после создания соответствующих файлов на этапах 1–3**. README — план, а не готовая программа.

### 10.1. Backend в терминале PyCharm

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
```

- `127.0.0.1`: backend доступен **только на этом ПК**, безопасный для локальной dev-связи.
- `--reload`: режим разработки; убрать при релизном запуске.
- `http://127.0.0.1:8000/docs`: Swagger UI при стандартных настройках FastAPI.

В **другом** терминале:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/v1/health
```

### 10.2. Flutter Windows

```powershell
Set-Location client
flutter pub get
flutter run -d windows --dart-define=GATEWAY_URL=http://127.0.0.1:8000
```

URL не хардкодим: Dart берёт его из конфигурации. HTTP на `127.0.0.1` — **только локальная dev-связь между двумя процессами на одной машине**. При передаче данных по сети используем HTTPS без отключения проверки сертификата.

### 10.3. Тесты и сборка

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m pytest backend\tests -q
```

```powershell
Set-Location client
flutter test
flutter build windows
```

Релизная Windows-сборка включает не только `.exe`, но и необходимые нативные зависимости/assets. Путь внутри `client\build\windows\...` уточняется по фактическому выводу Flutter. Не называть одиночный `.exe` готовым универсальным установщиком без проверки.

### 10.4. Когда появится Android

В телефонном клиенте `localhost` — **сам телефон**, а не домашний ПК. Для связи с домашним FastAPI потребуется:

1. Фиксировать адрес ПК в локальной сети (или найти его по LAN hostname).
2. Настроить безопасный **HTTPS** endpoint с доверенным для телефона сертификатом.
3. Ограничить Windows Firewall нужными клиентами; не открывать порт на публичный интернет.
4. Передавать `GATEWAY_URL` через конфигурацию запуска.
5. Проверить Android physical-device build, сетевые отказы и сохранение offline.

**Нельзя** просто открыть backend на `0.0.0.0`, выключить TLS checks и назвать это готовым безопасным Android-решением.

### 11.1. Три пациента из ТЗ

### 11.2. Пирамида тестов

| Уровень | Что проверяем | Инструмент |
|---|---|---|
| Unit | Подсчёт шкал, digest, delta, provenance, правила | `flutter test`, `pytest` |
| Contract | JSON schemas, enum, version mismatch, null/unknown | Pydantic tests + golden fixtures |
| Integration | Flutter ↔ Gateway ↔ mock provider; таймауты/ошибки | pytest, integration test |

### 11.3. Целевые показатели из ТЗ, **не измеренные значения**

- **100%** срабатываний hard-stop на фиксированном утверждённом critical test pack.
- **100%** accepted responses соответствуют JSON schema.
- **0** критических противоречий вида `urgent=false` при deterministic hard-stop.
- Appropriate abstention **≥90%** на заранее размеченных неполных случаях.
- Routing concordance **≥85%** на однозначных synthetic случаях.
- Citation validity **≥98%**, цель demo curated set — 100%.
- Unsafe recommendation rate — **0 на demo set** по клинической экспертной оценке.
- Локальная карточка пациента: целевой `p95 < 2 с` на демо-оборудовании.
- AI analysis: целевые `p50 < 12 с`, `p95 < 30 с` — зависят от сети/модели.
- Возврат исходного demo dataset одной командой менее чем за 30 секунд.
- Демонстрация трёх возможностей укладывается в ~4 минуты.

Это **целевые критерии**, а не доказательство безопасности или эффективности системы. Любая метрика в отчёте должна происходить из фактического запуска с dataset version.

## 12. Безопасность домашнего сервера

### 12.1. Реальное размещение

| Часть | Где |
|---|---|
| Flutter Windows | Домашний ПК |
| Python FastAPI | Тот же домашний ПК |
| SQLite / шифрование | Локальный каталог приложения на ПК |
| LLM-модель | Удалённый API (по выбранному провайдеру) |
| Хранение истории на Gateway | **Нет** |
| Постоянное подключение к интернету | **Не нужно** для локальных экранов |
| Открытый сервер в интернете | **Нет** |

### 12.2. Обязательные ограничения

1. **Нет реальных идентифицируемых медданных** в конкурсном MVP.
2. Не хранить provider API-key в Flutter, Git, открытом конфиге.
3. Не отправлять всю историю, только сформированный минимальный Context Snapshot.
4. Прямые идентификаторы маскируются/удаляются **до outbound request**.
5. PII guard не гарантирует идеальное обезличивание: свободный текст с сомнительным содержанием должен блокировать запрос и требовать исправления.
6. Клинический hard-stop выполняется до вызова LLM и не отменяется его ответом.
7. Не хранить prompt/clinical payload в стандартных HTTP/application logs.
8. Шифровать локальную историю и хранить ключ в механизме ОС, а не в константе Dart.
9. Android LAN соединение — HTTPS + cert verification. Не отключать TLS для обхода ошибки.
10. Не открывать порт FastAPI на домашнем роутере (port forwarding).
11. Не выдавать demo PIN/token за полноценную авторизацию production.
12. До реальных данных требуется отдельная юридическая/ИБ/регуляторная оценка и клиническая валидация.

### 12.3. Риски конкретно домашнего ПК

- **ПК выключится / уснёт:** отключить сон на время защиты, обеспечить питание.
- **Пропадёт сеть:** локальная история продолжит работать; кэшированный ответ явно помечать как предзаписанный.
- **API лимиты:** заранее проверить доступность провайдера и размер квоты.
- **Windows Firewall:** не менять правила для Windows-only localhost; для Android ограничивать доверенными устройствами.
- **Сбой приложения:** сохранять визит до LLM-вызова.
- **Проблемы SQLCipher:** выявить на этапе 0; unencrypted SQLite не считать удовлетворяющей MUST по безопасности.
- **Сбой нативной сборки:** проверить release build до финального дня.

## 13. Интеграция, конфликты и развитие

### 13.1. Три архитектурных конфликта

**Конфликт владения данными.**  
Если SQLite и backend одновременно становятся владельцами истории, появится два источника истины. **Решение:** история принадлежит клиентской БД; Gateway stateless; Digest производный; Snapshot immutable.

**Конфликт контрактов.**  
Если FastAPI меняет JSON или правила на сервере расходятся с клиентом, UI может показать неправильное состояние. **Решение:** Pydantic → versioned OpenAPI/fixtures, contract tests, явный `schema_version`, единый versioned ruleset. Несовместимые версии отклоняются, а не обрабатываются «как получится».

**Конфликт эволюции.**  
Позднее Android/новый LLM/новые шкалы не должны требовать переписывания всех экранов. **Решение:** UI → domain → repository, provider adapter, конфигурируемые scales, миграции и versioned DTO.

### 13.2. Интеграция с другими направлениями

- **Frontend ↔ Backend:** JSON Schema и статусы фиксируются прежде разработки result screen.
- **Data ↔ Clinical:** source events не изменяются тихо; provenance и hash позволяют проверить вывод.
- **Security ↔ Mobile:** для LAN отдельно нужны HTTPS, auth, контроль доступа и безопасные ключи.
- **QA ↔ Clinical:** программный hard-stop test pack — не замена экспертной проверки порогов и evidence.
- **DevOps ↔ Release:** сборка на собственном ПК не гарантирует запуск на чужой Windows; необходим smoke на целевой машине.

### 13.3. Предложение улучшения (не реализуем без отдельного решения)

**После Windows MVP** упаковать Gateway в запускаемый сервис и добавить простой installer/launcher, чтобы PyCharm не требовался для демонстрации. **Плюсы:** удобство, меньше ручных команд. **Минусы:** дополнительные этапы упаковки, подписи, обновлений. **Риски:** антивирус, не найденные runtime DLL, неправильные переменные окружения. **Оценка:** дополнительно ~6–12 ч. Код для этого улучшения создаём **только после явного решения**.

### 13.4. После чемпионата, не в текущем плане

FHIR/МИС, пациентский режим, авторизация/SSO, secure sync, on-prem LLM, расширенный клинический eval set и экспертный review, HA, production backups, юридическая и регуляторная работа. При появлении реальных пациентов архитектура потребует **новой** модели угроз и правового согласования.

## 14. Порядок совместной работы

**Принцип:** работаем строго **Этап → полные файлы → команда запуска → тест → исправление → принятие этапа**.

1. Выбираем один этап из раздела 9.
2. Формулируем 3–7 проверяемых критериев готовности.
3. Создаём только необходимые файлы с относительными путями.
4. Запускаем на Windows из терминала PyCharm.
5. При ошибке фиксируем реальный traceback / команду / версии.
6. Исправляем проблему **не ломая уже принятые контракты**.
7. Запускаем smoke-тест повторно и отмечаем этап закрытым.
8. Только затем переходим дальше.

**Пример полезного запроса на следующем этапе:**

```text
Проект: Clinical Compass Agent.
Среда: Windows, PyCharm.
Этап: 1 — FastAPI skeleton и контракты.
Что уже есть: Python 3.12, venv, Flutter doctor пройден.
Задача: создать рабочий backend /v1/health, /v1/config
и тесты, строго согласно README.md и ТЗ v1.1.
Отдать полные файлы, пути и PowerShell команды.
Результат моего запуска/ошибка: ...
```

**Правила разработки:**

- Не добавлять функции вне текущего этапа «заодно».
- Не менять API/БД без контракта/миграции и тестов.
- Не присылать в чат `.env` с ключами.
- Не утверждать «работает» без запуска и проверяемого результата.
- Не выдумывать клинические пороги, рекомендации, диагнозы или ссылки.
- Если решение временное/гипотеза — явно маркировать.
- При дефекте повторно проверить влияние на соседние слои.
